# 실시간 메시지 프로토콜 (Unity ↔ 백엔드 계약서)

## 연결

1. REST 로그인: `POST /auth/guest` — body `{ "nickname": "철수", "deviceId": "기기고유값" }`
   → 응답 `{ "userId": 1, "nickname": "철수", "accessToken": "eyJ..." }`
2. WebSocket 연결: `ws://localhost:8080/ws/game?token={accessToken}`
   - 토큰이 없거나 유효하지 않으면 핸드셰이크 거부 (401)
   - 배포 서버는 `https`·`wss` 를 쓴다 (`wss://j15b202.p.ssafy.io/ws/game?token=...`)

## 매치 진입 확인 (게임 서버 전용)

`POST /auth/verify` — **사람이 부르는 API 가 아니다.** 게임 서버(Mirror)가 접속해 온
플레이어의 신원을 확인할 때 쓴다.

```json
요청  { "token": "eyJ...", "roomId": "K7M2QX" }
응답  { "userId": 1, "nickname": "철수" }        // 200
      (본문 없음)                                // 401
```

- 게임 서버는 로비를 모른다. 누가 어느 방 사람인지 아는 곳이 Spring 뿐이라 접속 시점에 물어본다
- **토큰이 유효해도 그 방 참가자가 아니면 거절**한다. 토큰만 보면 남의 방에 들어갈 수 있다
- 실패 사유(토큰이 틀렸는지, 방이 없는지, 그 방 사람이 아닌지)는 구분해서 알려 주지 않는다 —
  알려 주면 남의 방을 더듬어 볼 수 있다

## 메시지 형식

모든 메시지는 텍스트(JSON), `type` + `data` 구조:

```json
{ "type": "JOIN_ROOM", "data": { "roomId": "K7M2QX" } }
```

## 방 코드 (roomId)

방 참가는 **코드 초대 방식**이다. 호스트가 받은 코드를 친구에게 전달하고, 친구가 그 코드로 입장한다.
공개 방 목록은 제공하지 않는다.

- 형식: **대문자·숫자 6자리** (예: `K7M2QX`)
- 사용 문자: `23456789ABCDEFGHJKMNPQRSTUVWXYZ` — 눈으로 헷갈리는 `0/O`, `1/I/L`은 쓰지 않는다
- **입력 시 대소문자를 구분하지 않는다.** 앞뒤 공백도 무시한다 (서버가 정규화)
- 서버가 응답에 담는 값은 항상 대문자다. 클라이언트는 받은 값을 그대로 보관해 쓰면 된다

## Client → Server

| type | data | 설명 |
|---|---|---|
| `CREATE_ROOM` | `{}` | 방 생성. 생성자가 방장 |
| `JOIN_ROOM` | `{ "roomId": "..." }` | 방 입장. WAITING이면 일반 입장(정원 미달일 때만), PLAYING이면 **복귀**(그 판에 참가했던 유저만) |
| `LEAVE_ROOM` | `{}` | 방 퇴장. 방장이 나가면 자동 위임 |
| `READY` | `{ "ready": true }` | 준비 상태 변경 |
| `START_GAME` | `{}` | 게임 시작 (방장만, 전원 준비 시) |
| `GAME_END` | `{}` | 판 종료 (방장만, 게임 중일 때만). 방이 `WAITING`으로 돌아간다 |
| `HOST_TAKEOVER` | `{ hostAddress }` | 매치를 이어받는다 (새 방장만, 게임 중일 때만). 전원에게 `GAME_STARTED`가 다시 간다 |
| `PLAYER_MOVE` | `{ "x": 1.0, "y": 0.0, "z": 3.5, "yaw": 90.0 }` | 자기 위치·방향 전송 (게임 중에만). `yaw`는 생략 가능 |

## Server → Client

| type | data | 설명 |
|---|---|---|
| `ROOM_CREATED` | `{ "roomId": "..." }` | 방 생성 완료 (생성자에게만) |
| `ROOM_STATE` | 아래 예시 참고 | 방 상태 변화 시 방 전원에게 브로드캐스트 |
| `GAME_STARTED` | `{ "roomId": "..." }` | 게임 시작 (방 전원에게) |
| `STATE_SYNC` | `{ "roomId", "gameState": { ... } }` | 복귀한 플레이어에게만 현재 게임 상태 전체 전송 |
| `PLAYER_MOVED` | `{ "userId": 2, "x": 1.0, "y": 0.0, "z": 3.5, "yaw": 90.0 }` | 다른 플레이어의 위치. **보낸 사람에게는 오지 않는다** |
| `ERROR` | `{ "message": "...", "reason": "..." }` | 요청 실패 사유. `reason` 은 사유 코드(아래) |

### ROOM_STATE 예시

```json
{
  "type": "ROOM_STATE",
  "data": {
    "roomId": "K7M2QX",
    "hostUserId": 1,
    "status": "WAITING",
    "players": {
      "1": { "nickname": "철수", "ready": true },
      "2": { "nickname": "영희", "ready": false }
    },
    "disconnected": [3]
  }
}
```

- `players`의 키는 userId(문자열), 값은 **닉네임과 준비 여부**다. 로비 화면에 그대로 쓰면 된다
- `disconnected`는 연결이 끊겨 유예 시간을 기다리는 중인 userId 목록이다. 이 사람들도 `players`에는 남아 있다
- `status`는 `WAITING`(대기 중) 또는 `PLAYING`(게임 중)


### ERROR 의 사유 코드 (S15P21B202-413)

`message` 는 예전 그대로다. 옆에 `reason` 을 실어 **클라이언트가 사람이 읽을 문구를 고르게** 한다 — 화면에 보일 말은 화면을 가진 쪽이 정하는 것이 맞고, 그래야 문구를 다듬을 때 서버를 다시 배포하지 않는다.

| `reason` | 언제 | 클라이언트가 띄우는 말 |
| --- | --- | --- |
| `ROOM_NOT_FOUND` | 그 코드의 방이 없다 | 그런 방이 없습니다. 방 코드를 다시 확인해 주세요. |
| `ROOM_FULL` | 정원(4명)이 찼다 | 방 인원이 다 찼습니다. (최대 4명) |
| `ROOM_PLAYING` | 대기 중이던 방이 방금 시작됐다 | 이미 게임이 시작된 방입니다. 끝나면 다시 시도해 주세요. |
| `REJOIN_DENIED` | 이 판에 참가하지 않았던 사람이 진행 중인 방에 들어오려 한다 | 이 판에 참가했던 사람만 돌아올 수 있습니다. |

`reason` 이 없거나 모르는 값이면 클라이언트는 `message` 를 그대로 보여준다. 조용히 삼키면 사용자가 아무 설명도 못 받는다.
## 인게임 위치 동기화

게임이 시작되면(`GAME_STARTED` 수신 후) 각 클라이언트는 자기 캐릭터의 위치를 주기적으로 보낸다.

```
내 게임 ──PLAYER_MOVE──▶ 서버 ──PLAYER_MOVED──▶ 같은 방의 나머지
```

- **권장 전송 주기: 초당 10~20회.** 매 프레임 보낼 필요는 없다
- 서버는 물리를 계산하지 않고 **그대로 중계**한다. 받은 쪽은 값 사이를 부드럽게 이어(보간) 그린다
- 마지막 위치는 서버의 `GameState`에 남는다. 그래서 복귀한 플레이어가 `STATE_SYNC`로 **끊겼던 자리**를 받는다
- 대기 중(`WAITING`)인 방에서 보낸 `PLAYER_MOVE`는 무시된다

> **범위 주의**: 플레이어 위치만 공유한다. 상자 같은 물리 오브젝트는 각 클라이언트가 따로 계산하므로
> 화면마다 다르게 보인다. 오브젝트 공유가 필요해지면 별도 설계가 필요하다.

## 판이 끝날 때 (S15P21B202-316)

클리어 판정은 **호스트**가 한다. 서버는 판정하지 않고 결과만 받아 방을 되돌린다.

```
호스트가 클리어 판정 ──GAME_END──▶ 서버 ──ROOM_STATE(status=WAITING)──▶ 방 전원
```

- 방장이 아닌 사람이 보내면 `ERROR`(`cannot end game`)
- 게임 중(`PLAYING`)이 아닌 방에 보내도 `ERROR`
- **전원의 `ready`가 풀린다.** 다음 판을 하려면 각자 다시 준비를 눌러야 한다
- 그 판의 참가자 명단이 비워지므로, 끝난 뒤에는 아무도 "복귀"로 들어올 수 없다
- 판이 끝난 방에는 **새로운 사람이 코드로 입장할 수 있다** (정원 미달일 때)
- 같은 방에서 전원이 다시 준비하면 `START_GAME`으로 한 판 더 할 수 있다

**끝났다는 사실을 알리는 전용 메시지는 없다.** `status`가 `WAITING`으로 바뀐
`ROOM_STATE`가 그 신호다. 결과 화면에 필요한 클리어 여부·경과 시간은 서버가 아니라
호스트가 Mirror `SyncVar`로 내린다(S15P21B202-54).


## 방장이 사라질 때 (S15P21B202-389)

방장의 PC 가 곧 게임 서버다(`-145`). 그 사람이 사라지면 남은 사람 중 하나가 이어받는다.

```
방장 연결 끊김
   │
   ├─ 자리는 30초 유예로 남긴다 (-150, 돌아올 수 있어야 한다)
   └─ 방장 자리는 기다리지 않고 즉시 넘긴다 ── ROOM_STATE(hostUserId=새 방장) ──▶ 방 전원
                                                            │
                        "게임 중인데 내가 방장이 되었다" ────┘
                                    │
                          ──HOST_TAKEOVER{hostAddress}──▶ 서버
                                                            │
                                            릴레이 세션을 새로 열고
                                            옛 세션을 닫는다
                                                            │
                          ◀──GAME_STARTED (각자 몫)────────┘
                                    │
                    새 방장은 StartHost · 나머지는 StartClient
```

**방장 자리는 유예를 기다리지 않는다.** 자리를 남기는 것과 방장을 넘기는 것은 다른 일이다 — 자리는 그 사람이 돌아올 수 있게 남기지만, 방장을 30초 기다리면 그동안 아무도 게임을 할 수 없다.

**끊긴 사람은 방장으로 고르지 않는다.** 게임 서버가 될 수 없으므로 넘겨도 판이 멈춘다.

**이전용 서버→클라이언트 메시지를 만들지 않았다.** `ROOM_STATE` 가 이미 `hostUserId` 를 싣고 클라이언트가 그것으로 방장 여부를 판단하므로, 방장이 바뀐 `ROOM_STATE` 하나가 곧 "이어받아라" 다. 접속 정보도 `GAME_STARTED` 에 이미 다 들어 있고, 받는 쪽은 **매치 중에 온 `GAME_STARTED`** 를 이전으로 읽는다.

**릴레이 세션은 새로 연다.** 우리 릴레이는 누가 서버인지를 **토큰으로** 가르므로(`metagame_relay.py` 의 `host_token`) 방장이 바뀌면 고쳐 쓸 수 없다. 옛 세션은 닫는다 — 닫지 않으면 릴레이에 세션이 쌓인다(`-298` §5-①).

**아무도 남지 않으면 판을 끝낸다.** 이어받을 사람이 없으므로 `-385` 의 경로가 그대로 쓰인다.

**이어받기가 실패하면 방이 풀린다.** 새 방장까지 함께 죽으면 아무 소식이 오지 않는다. 그때 새 방장의 클라이언트가 `GAME_END` 를 보내 방을 `WAITING` 으로 돌린다 — 그러지 않으면 방이 영구히 `PLAYING` 이라 로비의 시작 버튼이 비활성이 된다(`-385` 가 고친 그 증상).
## 연결 끊김과 복귀

게임 중(`PLAYING`)에 연결이 끊기면 **게임은 멈추지 않는다.**

1. 끊긴 즉시 방 전원에게 `ROOM_STATE`가 오고, 해당 userId가 `disconnected`에 담긴다.
   자리는 유예 시간(기본 30초, `game.reconnect-grace-ms`) 동안 유지된다.
2. 유예 안에 다시 접속해 `JOIN_ROOM`을 보내면 복귀한다 → `STATE_SYNC` 수신 후 `ROOM_STATE` 브로드캐스트.
3. 유예를 넘기면 참가자 목록에서 **제외**되고 `ROOM_STATE`가 브로드캐스트된다.
   **남은 인원으로 게임은 계속 진행된다.**
4. 제외된 뒤에도 `JOIN_ROOM`으로 재입장할 수 있다. 단 **그 판에 참가했던 유저만** 허용된다
   (무관한 유저의 난입 방지). 정원이 이미 찼으면 `ERROR: room is full`.
5. **복귀·재입장한 플레이어는 기절(DOWNED) 상태로 돌아온다.** 팀원이 소생시켜야 한다.

> 클라이언트는 `ROOM_CREATED`/`ROOM_STATE`로 받은 `roomId`를 보관해 두었다가,
> 재접속 시 같은 `roomId`로 `JOIN_ROOM`을 보내면 된다. 별도의 복귀 전용 메시지는 없다.

## 미정 (게임 기획 확정 후 추가)

- `PLAYER_MOVE` — 동기화 방식(이벤트 vs 틱) 결정 필요
- `PLAYER_DOWNED`, `REVIVE_*`, `PARTY_WIPE`, `STAGE_CLEARED`, `STAGE_RESTART` — 소생·체크포인트 규칙 확정 필요
- 재입장 스폰 위치 (끊긴 위치 / 팀원 근처 / 스테이지 시작점)

> 이 문서가 곧 서버-클라이언트 계약이다. 메시지 추가/변경 시 반드시 이 문서를 갱신하고 Unity 팀에 공유할 것.
