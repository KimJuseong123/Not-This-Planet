# METAGAME 개발 워크플로우 (v2.2 · 2026-08-28)

> 우리 팀이 일하는 방식을 처음 보는 사람도 따라갈 수 있게 정리한 문서입니다. 팀원이 각 단계에서 **무엇을 하면** 되는지, 그때 **무엇이 자동으로 일어나는지**, 그리고 실수했을 때 **어떤 장치가 어떻게 받아 주는지**를 씁니다. 세부 규칙과 설정 근거는 팀 리포의 `docs/` 문서에 있습니다.

## 0. 한눈에 보는 흐름 — Jira 이슈 하나가 완료되기까지

| 단계 | 어디서 | 팀원이 하는 일 | 그러면 자동으로 | 이슈 상태 |
| --- | --- | --- | --- | --- |
| ① 할 일 등록 | Jira | **이슈를 만든다.** 유형 Task · 제목 `[파트] 제목` · 상위 Epic · 담당자. 스프린트는 비워 두면 백로그, 생성 화면에서 바로 지정해도 된다 | 설명이 비어 있으면 **설명 템플릿**(목적 · 완료 조건 · 산출물 · 참고)이 채워지고 파트 레이블이 붙는다. 제목 형식이 틀리거나 상위 Epic이 없으면 `needs-fix` 레이블 + 댓글 + Mattermost 🟠 카드 | 해야 할 일 |
| ② 스프린트 계획 | Jira | 이번 스프린트에 할 이슈를 백로그에서 **활성 스프린트로 옮긴다** | 기한 = 스프린트 종료일 | 해야 할 일 |
| ③ 작업 시작 | Jira → GitLab | 이슈 화면 **개발 → 브랜치 만들기**(이름이 `S15P21B202-번호-제목`으로 미리 채워짐, **소스는 기본값 `develop` 그대로**). 로컬에서 직접 만들어도 이름이 이슈 키로 시작하면 똑같이 동작한다 | 이슈가 **진행 중**으로 바뀐다. 백로그 이슈였다면 활성 스프린트에 자동 추가 | 진행 중 |
| ④ 작업 · 커밋 | 로컬 | 코드/에셋/문서를 작업하고 **커밋 → push**. 커밋 메시지는 `type(scope): 요약 (이슈키)`. 새 에셋은 `.meta` 파일과 함께 넣고, 씬·프리팹을 건드릴 땐 팀 채널에 먼저 말해 둔다 | 커밋이 Jira 이슈의 개발 패널에 쌓인다. 이슈 키가 없는 이름의 브랜치는 push 단계에서 로컬 훅이 막는다. develop 이 앞서 나가 있으면 훅이 **최신을 알아서 얹고** 다시 push 하라고 알려 준다(§4 S31) | 진행 중 |
| ⑤ MR 열기 | GitLab | **Merge Request를 만든다**(대상 `develop`. 다른 작업 브랜치 위에 얹는 스택 MR 도 가능 — §4 S27). 템플릿이 자동으로 들어오니 `이슈:` 줄 · 무엇을/왜 · 확인 방법 · 체크리스트를 채운다. 제목은 GitLab 기본값으로 둬도 된다 | 제목이 `[파트] type: 요약 (이슈키)`로 정리되고, **양식 검사 · 파일 위생 검사 · 겹침 검사 · AI 리뷰**가 돌고, 팀장에게 🟢 리뷰 요청 카드가 간다. 다른 열린 MR 과 같은 파일을 다르게 바꿨으면 겹침 검사가 **나중에 올린 쪽**에 고칠 명령을, 양쪽에 머지 순서를 남긴다(§4 S32) | 진행 중 |
| ⑥ 빨간불 고치기 | GitLab → 로컬 | 검사가 실패하면 🔴 카드와 MR 화면의 실패 잡을 보고 **고쳐서 다시 push** | 재검사. AI 리뷰 코멘트는 새로 쌓이지 않고 갱신된다 | 진행 중 |
| ⑦ 리뷰 · 머지 | GitLab | **팀장**이 AI 요약과 리뷰어 확인 항목을 보고 **머지**(squash). 겹치는 MR 이 있으면 코멘트의 **머지 순서**대로 | 작업 브랜치 자동 삭제 · 이슈가 **완료**로 · 담당자에게 🟢 머지 완료 카드 | 완료 |

옆길로 새면: 보드에서 카드를 손으로 옮기면 되돌아오고(🟠), MR을 머지하지 않고 닫으면 이슈는 진행 중으로 남고 🟠 카드가 간다. 매일 아침 09:30에는 정리 안 된 것들(형식 위반 · 기한 초과 · 오래 멈춘 이슈 · 오래 열린 MR · 머지됐는데 완료 안 된 이슈 · 검사가 돌지 않은 MR · 서로 충돌하는 MR)을 모아 담당자를 불러 주는 📋 카드가 온다.

## 1. 다섯 가지 약속

1. **Jira가 먼저** — 코드·에셋·문서·회의 기록까지, 모든 작업은 Jira 이슈에서 시작해 브랜치 → MR로 흐른다. Task는 반드시 상위 Epic 아래에 있고, Epic 담당자가 그 아래 Task들을 책임진다.
2. **상태는 손으로 바꾸지 않는다** — `진행 중`은 브랜치가, `완료`는 MR 머지가 만든다. 손으로 끌면 자동으로 되돌아온다.
3. **develop 머지는 팀장만** — 팀장이 리뷰하고 머지한다. 리뷰 기준은 MR 템플릿의 "리뷰어 확인" 항목.
4. **기계가 먼저 검사한다** — 형식·키·양식·파일 위생은 CI가, 코드 의견은 AI가, 최종 판단은 사람이.
5. **알림은 조치할 사람에게만** — 멘션할 사람이 없는 알림은 보내지 않는다. 등급(🔴 실패 · 🟠 규칙 위반 · 🟢 요청/완료 · 📋 아침 점검)과 표 형식으로 통일.

## 2. 누가 무엇을 하나

| 역할 | 누가 | 하는 일 |
| --- | --- | --- |
| 팀장 | 김수호 | 모든 MR 리뷰·머지. 대표가 정해지지 않은 파트의 Epic 담당. GitLab 설정(Maintainer) |
| Epic 담당자 | 파트 대표 — Network·Infra·Data 금준영, Backend 최재현, 나머지는 당분간 팀장 | 자기 Epic 아래 Task들의 진행·검증 책임 |
| 팀원 | 전원 | 이슈 만들기 → 브랜치 → 작업 → MR. 상태 변경·브랜치 이름·MR 제목은 신경 쓰지 않아도 된다(자동) |
| Infra | 금준영 | Jira 자동화 · GitLab 설정 · CI(검사·AI 리뷰) · 알림 · 러너 운영과 사고 복구. CD(빌드·배포 자동화)는 다음 단계 |

쓰는 도구: **Jira Cloud**(이슈·보드·자동화) · **GitLab**(lab.ssafy.com — 코드·MR·CI) · **Mattermost**(알림 채널 1개) · **Claude**(AI 리뷰, 러너에서 실행).

## 3. 뒤에서 일하는 것들 — 쉬운 말로

| 장치 | 무엇인가 | 하는 일 |
| --- | --- | --- |
| Jira 자동화 | Jira 안에서 돌아가는 규칙 8개 | 설명 템플릿·기한·레이블 채우기(브랜치가 생기면 `has-branch`), 제목/Epic 검사, 브랜치 → 진행 중, 머지 → 완료, 손으로 옮긴 상태 되돌리기, MR 닫힘 알림 |
| 로컬 훅 (`.githooks/pre-push`) | 내 PC에서 push 직전에 실행되는 검사·정리 | 이슈 키가 없는 브랜치 이름이면 push를 막고 안내. **뒤처진 브랜치에는 `develop` 최신을 자동으로 얹어 준다** — `git push` 하면 훅이 알아서 가져와 리베이스하고, 커밋 해시가 바뀌므로 그 push 만 중단한 뒤 다시 push 할 명령을 알려 준다(팀원이 하는 일은 `git push` 한 번 더). 충돌하면 원래대로 되돌리고 경고만 남긴다 — 작업이 사라지지 않는다. 각자 `git config core.hooksPath .githooks` 한 번으로 켠다 |
| GitLab 설정 | 서버 쪽 잠금 | `develop`·`master`는 직접 push 불가, 머지는 Maintainer(팀장)만. 머지되면 작업 브랜치 자동 삭제. squash 머지 기본 |
| 제목 정리 (`mr-title`) | MR이 열리면 도는 CI 잡 | 브랜치 이름의 이슈 키로 Jira를 읽어 제목을 `[파트] type: 요약 (키)`로 고치고 본문의 `이슈:` 줄을 채운다 |
| 양식 검사 (`mr-lint`) | CI 잡 | MR이 "리뷰 받을 준비가 됐는지" — Draft 아님 · 브랜치/제목/본문의 이슈 키가 같음 · 템플릿 섹션이 있음 · 작성자 체크리스트 전부 체크 · Jira 이슈가 실제로 있고 담당자와 상위 Epic이 있음 · 제목의 파트 = Jira 파트. 여기에 **경고**(차단 아님) 세 가지: 브랜치가 develop 이 아닌 곳에서 갈라짐 · 시작점이 develop 보다 많이 뒤처짐 · 다른 이슈 키 커밋이 섞임 |
| 겹침 검사 (`mr-overlap`) | MR 을 올리면 다른 열린 MR 과 실제로 합쳐 봄 | 하나를 머지하면 다른 쪽이 충돌할 두 MR 을 **미리** 찾아 나중 MR 에 고칠 명령을, 팀장에게 머지 순서를 알려 준다. 나중 MR 이 먼저 MR 위에 얹혀 있으면 대상을 그 브랜치로 자동 전환 |
| 파일 위생 검사 (`repo-hygiene`) | CI 잡 | Unity 프로젝트를 망가뜨리는 커밋 차단 — `Library/`·`.csproj` 같은 금지 파일, `.meta` 짝 빠짐, `Assets/` 바로 아래 새 폴더, LFS로 가야 할 바이너리, 5MB 초과, 씬·프리팹을 바꿨는데 본문에 "변경 없음"이라 쓴 경우 |
| AI 리뷰 (`ai-review`) | CI 잡, Claude 실행 | 역할별 리뷰어가 따로 보고(범위·완료 조건 / C#·네트워크 코드 / 에셋·씬·구조) 요약 에이전트가 **팀장용 한 장**으로 합친다: 결론(머지 가능 · 조건부 · 보류) → 팀장이 확인할 것 3개 이내 → 발견 사항 표, 상세는 접힘. 문서만 바뀐 MR은 생략. 참고용(비차단). **판단 기준: 남은 ⚠️가 "사람이 해야 하는 일"(스케줄 등록, 실기기 확인 등)뿐이면 머지해도 된다** — AI는 코드로 증명되지 않는 완료 조건을 끝까지 ⚠️로 남긴다 |
| 이슈 완료 (`jira-complete`) | develop 머지 직후 CI 잡 | 머지된 MR 의 이슈와 **그 위에 쌓였던 스택 자식 이슈까지** 완료로 옮긴다. Jira 자동화(R6)는 대상이 develop 인 MR 만 완료시켜 자식이 남았고, 머지 시점에 `해야 할 일` 이면 놓치는 것도 실측됐다(-159·-133) |
| 알림 | Mattermost 채널 | 위 장치들이 사람이 움직여야 할 때만 카드를 보낸다(§5) |
| 아침 점검 (`mm-digest`) | 매일 09:30 스케줄 CI 잡(스크립트, AI 아님 — 2026-08-28 등록) | Jira·GitLab을 조회해 방치된 것들을 담당자별로 정리: needs-fix · 기한 초과 · 정체 · 담당자 없음 · 오래 열린 MR · **머지됐는데 완료 안 된 이슈**(대상이 develop 인 것) · **스택 자식 MR**(대상이 다른 이슈 브랜치라 자동 완료가 원래 걸리지 않는다. **부모가 develop 에 도달한 것만** — 부모가 아직 안 들어갔거나 폐기 브랜치로 머지된 것은 지금 할 일이 아니라 보고하지 않는다) · **검사가 돌지 않은 MR** · **서로 충돌하는 열린 MR(머지 순서)** |
| 러너 | CI 잡을 실제로 실행하는 컴퓨터 | **EC2 리눅스 도커 러너(24시간)** — 2026-09-01 이전 완료. 팀 PC 러너는 Unity 잡 전용·예비 |

## 4. 실수하면 어떻게 되나 — 시나리오 방어표

| S01 | 제목에 `[파트]` 없이 이슈 생성 | Jira 자동화 | `needs-fix` 레이블 + 담당자 멘션 댓글. 제목을 고치면 레이블이 빠지고 파트 레이블이 붙음 | 🟠 담당자 |

| S04 | 백로그 이슈에서 브랜치 만들기 | Jira 자동화 | 진행 중 + 활성 스프린트에 추가 + 안내 댓글 | — |

| S29 | 검사가 아예 돌지 않은 MR | 아침 점검 | 빨간불이 없다고 통과한 것이 아니다. 러너가 꺼져 잡이 계속 대기 중이거나, 브랜치에 CI 설정이 없어(master 기반) 파이프라인이 만들어지지 않으면 **아무 검사도 받지 않은 MR 이 조용히 열려 있다**. 다음 날 아침 점검이 `🚫 검사가 돌지 않은 MR` 표로 작성자를 불러 준다(대기 2시간 이상이면 Infra 도 함께) | 📋 |
| S30 | MR 없이 브랜치를 **다른 브랜치에 직접 머지** | Jira 자동화 | 그 이슈는 **손으로도 완료할 수 없다.** 완료로 옮기면 '완료는 머지로만' 규칙이 되돌린다 — 개발 패널에 MR 이 0건이기 때문(작업이 develop 에 들어갔는지와 무관하게 MR 기록으로 판단한다). 2026-08-28 실측: -20 이 이 상태로 7번 되돌려졌다. 되살리는 방법은 **그 작업을 실어 간 머지된 MR 본문에 그 이슈 키를 적어** 개발 패널에 연결한 뒤 손으로 완료하는 것. 애초에 **이슈마다 자기 MR 을 만드는 것**이 정답 | 자동 코멘트 |
| S31 | develop 이 앞서 나간 채로 계속 작업 | 로컬 훅 **자동 반영** | `git push` 하면 훅이 `origin/develop` 을 가져와 뒤처진 만큼 **자동으로 리베이스**하고, 그 push 만 중단한 뒤 다시 push 할 명령을 알려 준다(-137). 충돌이면 원상복구 + 경고만 — 그때는 씬·프리팹 충돌을 한 번에 보는 `git merge origin/develop` 로 정리한다. 씬 작업이 많으면 `METAGAME_AUTOREBASE_MODE=merge` 로 처음부터 merge. 끄기는 `METAGAME_AUTOREBASE=0` | 터미널 |
| S32 | 두 MR 이 같은 파일을 다르게 바꿈 — 하나를 머지하면 다른 쪽이 충돌 | 겹침 검사(`mr-overlap`) · 아침 점검 | **MR 을 올리는 시점에 잡는다**(팀장 요청 2026-08-28). 같은 대상을 향한 다른 열린 MR 마다 실제 3-way 머지를 시험해 충돌 파일을 증명한다(추측 아님). **나중에 열린 MR 이 맞추는 쪽** — 텍스트 충돌이면 나중 MR 은 🔴 + 정확한 명령(`git rebase origin/<먼저 MR 브랜치>`, 씬이면 `git merge`)을 코멘트로 받고, 먼저 열린 MR 에는 ⚠ 정보와 **머지 순서**만 남는다. 나중 MR 이 먼저 MR 위에 얹어 push 하면 검사가 그것을 인식해 **대상을 그 브랜치로 자동 전환**(스택 MR) → 팀장이 먼저 MR 을 머지하면 GitLab 이 나중 MR 을 develop 으로 되돌리고 그때 머지하면 충돌이 없다. 같은 씬·프리팹을 만졌지만 텍스트 충돌은 없는 경우도 ⚠(합쳐져도 씬이 깨질 수 있어 나중 쪽이 에디터에서 확인). AI 는 그 위에서 '텍스트 충돌은 없지만 서로 깨뜨리는지'(한쪽이 바꾼 메서드를 다른 쪽이 다른 파일에서 부름)를 판정해 덧붙인다. 아침 점검은 열린 MR 전체 쌍을 매일 새로 시험해 **머지 순서 지도**를 팀장에게 준다 | 🔴 작성자 · MR 코멘트 양쪽 · 📋 |
| S25 | 자동화 규칙 자체가 오류 | Jira | 규칙 소유자(Infra)에게 이메일. 증상(머지됐는데 진행 중인 이슈)은 아침 점검이 표로 잡아 담당자 멘션 | 📋 |

## 6. 자주 나오는 질문

**브랜치를 Jira 버튼 대신 직접 만들면?** 이름이 이슈 키로 시작하면(`S15P21B202-79-workflow-final`처럼) 똑같이 동작한다 — GitLab이 이름 속 키로 이슈에 연결하고, 진행 중 전환도 그대로 일어난다(실측). Jira 버튼은 이름을 대신 지어 주고 소스 브랜치를 develop으로 맞춰 주는 편의 기능이다.

**로컬 훅은 강제되나?** 아니다(그래서 '자동으로 해 주는' 쪽에 무게를 뒀다 — 막는 것이 아니라 대신 해 준다). `core.hooksPath`는 각자 PC의 설정이라 리포가 강제할 수 없다(GitLab 서버 push 규칙은 유료 기능). 그래서 훅은 "빨리 알려 주는 안내"이고, 진짜 방어는 MR의 양식 검사와 "키 없는 브랜치는 Jira에 연결되지 않는다"는 사실이다.

**MR "닫힘"이 뭔가?** 머지하지 않고 MR을 Close한 것. 이슈는 진행 중으로 남고, 담당자에게 🟠 카드가 간다. 다시 열어 머지하면 그때 완료된다.

**검사가 실패하면 이유는 어디서 보나?** 두 곳에서 바로 보인다 — **MR 화면의 `🔴 CI 실패 — 무엇이 왜 실패했는지` 코멘트**와 **🔴 알림 카드의 '이유' 칸**(둘 다 잡 로그의 ❌ 줄을 그대로 옮긴다). 더 자세히 보려면 MR 화면의 파이프라인 → 실패한 잡을 열면 전체 로그가 있고, 로그는 프로젝트 멤버 모두 볼 수 있다.

**아침 점검은 누가 하나?** 사람이 아니다. GitLab의 스케줄 파이프라인이 매일 09:30에 스크립트를 돌려 Jira·GitLab을 조회하고 카드를 보낸다(AI 아님). 스케줄은 팀장이 등록한다.

**왜 squash 머지인가?** develop에 "이슈 하나 = 커밋 하나"로 남기기 위해서다. 히스토리가 읽기 쉽고, 문제가 생기면 이슈 단위로 되돌릴 수 있다. 작업 중 커밋들은 MR 안에 그대로 남는다. 대신 머지된 브랜치에 이어서 push하면 안 되고(S21), 후속은 새 이슈로 간다.

**러너 PC가 꺼져 있으면?** GitLab이 잡을 대기 상태로 붙잡아 두고 러너가 켜지면 자동으로 실행한다. 다만 무한정 기다리지는 않는다 — **약 100분**이 지나면 `stuck` 으로 실패하고, 그렇게 실패한 파이프라인은 러너가 켜져도 **자동으로 되살아나지 않는다**(파이프라인 재실행 또는 새 커밋 push 필요). 밤사이 올라온 MR이 아침에 빨간불이라면 대개 이 경우다. **한 가지 더**: 러너가 멈춘 순간 *실행 중이던* 잡은 대기가 아니라 잡 타임아웃으로 죽는다. 그 잡이 `ai-review`(비차단)라면 **파이프라인은 초록인데 AI 리뷰 코멘트만 없는 상태**가 된다 — 초록인데 리뷰가 안 보이면 러너 중단을 의심하고 파이프라인을 다시 돌리면 된다. Jira 자동화와 Jira 쪽 알림은 러너와 무관하게 계속 동작한다.

**규칙 오류는 어디로 오나?** Jira 자동화는 실패를 규칙 소유자(Infra) 이메일로만 알리고 Mattermost로 돌릴 수 없다. 이메일은 켜 두고, 가장 중요한 실패 증상(머지됐는데 이슈가 완료가 아님)은 아침 점검이 따로 잡아 담당자를 부른다.

- **Unity 컴파일 검사** — Unity 6000.5.4f1이 설치된 러너가 준비되면 켠다.
- **CD(빌드·배포 자동화)** — 아직 시작 전. Infra 다음 단계.
- **master 사각지대 (지금 가장 큰 구멍)** — `master` 는 `develop` 보다 한참 뒤라 CI 설정(`.gitlab-ci.yml`)도 로컬 훅(`.githooks/`)도 **들어 있지 않다**. 그래서 master 에서 갈라진 브랜치는 push 해도 훅이 돌지 않고, MR 을 열어도 **파이프라인이 아예 만들어지지 않아** 검사·AI 리뷰·리뷰 요청 카드가 하나도 나가지 않는다(2026-08-28 MR !74 실측: 파이프라인 0건·코멘트 0건·훅 출력 없음). 겉보기에는 '빨간불이 없는 MR' 이라 오히려 안전해 보이는 것이 위험하다. **해소 방법: 팀장이 `develop` → `master` 릴리즈 MR 을 한 번 머지하면 사라진다.** 그전까지는 브랜치를 반드시 develop 에서 만든다.
- **2026-08-28 반영(develop)** — 아침 점검 완료 누락 감지 · 브랜치 베이스 경고 · Jira 조회 오탐 수정과 담당자 불일치 경고 · 스택 MR 허용 · CI 실패 이유를 카드와 MR 코멘트에 · 경고를 MR 코멘트로 · 머지된 브랜치 재push 경고 · 이 문서와 E2E 점검표.
- **2026-08-28 반영(머지 대기)** — 릴리즈 MR 검사 예외(S28) · 검사가 돌지 않은 MR 감지(S29) · CI 스크립트 회귀 테스트 잡 · AI 리뷰 지적 전수 반영(CI 스크립트·러너 스크립트·네트워크 세션) · push 전 develop 자동 반영 훅(S31) · 열린 MR 사이 충돌 조기 감지와 스택 자동 전환(S32). 팀장 머지 후 적용된다 — CI 규칙은 MR 소스 브랜치의 스크립트로 돌므로, 이미 열린 MR 은 develop 을 받아야 새 규칙이 적용된다.
