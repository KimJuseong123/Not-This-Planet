## 왜 이 문서가 있나

2026-09-08 에 처음으로 서로 다른 LAN 에서 2대 PC 테스트를 했다. 돌아온 피드백은 한 줄이었다 —
**"와이파이 쪽에서 랙이 심하다."** 원인을 찾으려고 `WorldSync`·`NetPlayer`·`RemoteAvatar`·
`OrbitCamera`·씬 설정·Mirror 소스를 다 읽어야 했고, 결국 계산으로 지연 예산표를 만들어
`232ms + RTT` 라는 값을 얻었다(`-328`). **그 값은 아직 재지 않았다.**

다음 테스트는 문장이 아니라 숫자를 내야 한다. 이 문서는 그 절차다.

## 측정 도구는 이미 있다 — 스위치를 켜지 않았을 뿐이다

새로 만들 것이 없다. Mirror 에 다 들어 있고 우리가 전부 꺼 둔 상태다.

| 무엇을 재나 | 어디 | 지금 | 보이는 것 |
| --- | --- | --- | --- |
| **RTT** | `NetworkPingDisplay` 컴포넌트 | 씬에 없음 | `RTT: {ms}` · 연결 품질 막대 |
| **대역폭·패킷 수** | `NetworkStatistics` 컴포넌트 | 씬에 없음 | 클라·서버 각각 `{msgs} msgs @ {bytes}/s` (송·수신) |
| **전송 큐 적체** | `KcpTransport.statisticsGUI` | `0` (Lobby 씬) | `SendQueue`·`ReceiveQueue`·`SendBuffer`·`MaxSendRate` |
| **보간 버퍼** | `NetworkManager.timeInterpolationGui` | `0` (Lobby 씬) | `timeline`·`buffer`(스냅샷 개수)·`DriftEMA`·**`BTM`** |

`BTM` 이 핵심이다. **동적으로 조정된 `bufferTimeMultiplier` 의 실제 값**이라,
`-328` 이 계산으로 주장한 `bufferTime = 2 × sendInterval + 지터` 를 **직접 반증할 수 있다.**

`SendQueue` 도 그렇다. `-328` 이 고친 것은 "신뢰 채널에 실린 연속 상태가 손실 때 줄을 선다" 였는데,
줄이 실제로 서는지는 이 숫자로만 보인다.

> **씬 파일은 건드리지 않는다.** 위 네 가지는 테스트하는 사람이 **에디터에서 켜고 빌드**한 뒤
> **커밋하지 않는다.** 지금 `Lobby.unity` 는 `-328`(MR `!249`)이 이미 고쳐 둔 상태라 여기서 또
> 만지면 충돌한다. 매번 손으로 켜는 것이 번거로워지면 개발 빌드에서만 붙는 오버레이로 만든다 —
> 그때 별 이슈로.

## 무엇을 확정하려는가

가설과 **무엇을 보면 틀렸다고 할지**를 먼저 적는다. 그러지 않으면 숫자를 보고 해석을 맞춰 버린다.

| # | 가설 | 맞다면 | 틀렸다면 |
| --- | --- | --- | --- |
| 1 | 참가자의 체감 지연은 **이동**에만 있다 (시점 회전은 로컬이라 즉각적) | 참가자가 "돌아보는 건 괜찮은데 걸을 때 밀린다" 고 말한다 | 둘 다 늦다 → 지연이 아니라 **프레임률** 문제다. FPS 를 먼저 본다 |
| 2 | 보간 버퍼는 `2 × sendInterval + 지터` 다 (`-328` 예산표의 100ms 항) | `BTM` 이 **2.0 근처** | `BTM` 이 3~4 면 버퍼가 계산의 1.5~2배다. 예산표를 그 값으로 고친다 |
| 3 | 신뢰 채널 적체가 사라졌다 (`-328` ②) | 방장의 `SendQueue` 가 **0 근처에 머문다** | 계속 쌓이면 신뢰 없는 채널로 옮긴 것이 부족했다는 뜻 — `NetworkTransform` 이 아직 Reliable 이다 |
| 4 | `sendRate 30` 으로 충분하다 | 방장 업링크가 `MaxSendRate` 를 여유롭게 넘고 참가자 체감이 나아졌다 | 여유가 없으면 30 을 유지, 여유가 크고 체감이 부족하면 **60 으로 올려 다시 잰다** |
| 5 | 예산표 총합이 맞다 (`232 → 146ms`) | 아래 ⑤의 왕복 측정이 그 근처 | 크게 벗어나면 예산표의 어느 항이 틀렸는지 `BTM`·`SendQueue` 로 좁힌다 |

## 준비

1. **빌드는 develop 최신으로.** `-328`(MR `!249`)이 들어간 뒤에 해야 의미가 있다 —
   그 전 빌드는 고치기 전 상태를 재는 것이다. 빌드에 실린 커밋은 실행 로그에 찍힌다(`-269`)
2. 에디터에서 네 스위치를 켠다 (**커밋하지 않는다**)
   - `Lobby.unity` → NetworkManager → `Time Interpolation Gui` ✔
   - 같은 오브젝트의 `KcpTransport` → `statisticsGUI` ✔
   - NetworkManager 오브젝트에 `NetworkPingDisplay` · `NetworkStatistics` 컴포넌트 **추가**
3. 양쪽 PC 의 **같은 빌드**를 쓴다. 다른 빌드를 섞으면 숫자를 비교할 수 없다
4. 백엔드는 마지막 배포본 그대로. 배포 버튼을 새로 누르지 않는다 —
   누를 때는 **가장 최신** 파이프라인만(`-333`)

## 측정 절차

### ① 환경 기록

| | 방장 | 참가자 |
| --- | --- | --- |
| 회선 | 모바일 핫스팟 / 와이파이 / 유선 | |
| 공인 IP 가 서로 다른가 | | |
| 백엔드 판정 | `direct(same network)` / `relay` — 접속 로그에서 | |
| PC 사양 (CPU·GPU) | | |

`relay` 인지 `direct` 인지가 갈리면 그 뒤 숫자를 같은 조건으로 비교할 수 없다. 먼저 적는다.

### ② 정지 상태 기준선

아무도 움직이지 않는 30초. **가만히 있을 때의 값**이 기준선이다.

| 항목 | 방장 | 참가자 |
| --- | --- | --- |
| FPS | | |
| RTT (ms) | — | |
| `BTM` | — | |
| `buffer` (스냅샷 개수) | — | |
| `DriftEMA` | — | |
| `SendQueue` / `SendBuffer` | | |
| 송신 (msgs/s @ bytes/s) | | |
| 수신 (msgs/s @ bytes/s) | | |

### ③ 움직이는 상태

둘 다 걷고, 부품 하나를 함께 옮기는 30초. **②와 같은 표를 다시 채운다.**
특히 `SendQueue` 와 `bytes/s` 가 ②에서 얼마나 뛰는지가 관심사다.

### ④ 체감 감별 (가설 1)

참가자에게 **따로따로** 묻는다. 한 번에 물으면 "랙" 한 단어로 뭉쳐진다.

- 마우스로 **돌아볼 때** 화면이 바로 따라오는가? (예상: 그렇다 — 시점은 로컬이다)
- **W 를 눌러 걸을 때** 화면이 바로 나가는가? (예상: 아니다 — 서버를 한 바퀴 돈다)
- **부품**과 **내 몸** 중 어느 쪽이 더 늦는가?
  - 부품이 더 늦다 → `WorldSync.Smoothing`(시정수 50ms)
  - 내 몸이 더 늦다 → 예산표 쪽

### ⑤ 조작 지연 왕복 (거친 측정으로 충분하다)

정밀 장비가 없으므로 **화면 녹화**로 잰다. 참가자 PC 를 60fps 로 녹화하고,
**키를 누른 프레임**과 **캐릭터가 처음 움직인 프레임**의 차이를 센다. 프레임당 16.7ms.
5회 재서 중간값을 쓴다. `-328` 예산표는 `146ms + RTT` 를 예상한다 — 약 9프레임 + RTT.

### ⑥ 재접속 재현 (`-150` 과 겹치는 부분)

1. 참가자가 게임 중 강제 종료한다
2. 방장 화면에서 그 캐릭터가 어떻게 되는지 적는다 (남는가 · 사라지는가 · 얼마 뒤)
3. 참가자가 다시 접속한다
4. **적을 것**: 다시 붙는가 · 부품 위치가 맞는가 · 고정쇠 진행도가 맞는가 · 유령이 남는가
   (`-313` 에서 고친 증상이라 재발 확인이기도 하다)

`-150`(끊긴 오브젝트 30초 유지)은 아직 미구현이다. **지금은 "무엇이 깨지는지" 를 적는 것이 목표**고,
그 목록이 `-150` 의 완료 조건이 된다.

## 판정 — 무엇을 보면 무엇을 하나

| 본 것 | 결론 | 다음 |
| --- | --- | --- |
| `BTM` ≈ 2.0 | 예산표의 버퍼 항이 맞다 | 예산표를 신뢰 도구로 쓴다 |
| `BTM` ≥ 3 | 버퍼가 계산보다 크다 = 지터가 크다 | `sendRate` 를 올리는 것이 버퍼도 줄인다 → 60 검토 |
| `SendQueue` 가 계속 쌓인다 | 아직 적체가 있다 | `NetworkTransform` 도 Reliable 이다 — 그쪽을 옮길지 검토 |
| 업링크 여유 있고 체감 부족 | 30 이 부족하다 | `sendRate 60` 으로 올려 ②③⑤ 재측정 |
| 업링크 여유 없음 | 30 이 상한 근처다 | 올리지 않는다. 예산표의 다른 항을 깎는다 |
| 참가자 FPS 가 낮다 | 지연이 아니라 프레임률 | 물리 100Hz·solver 14회(Unity 기본의 4.7배)를 본다 |
| 회전·이동 둘 다 늦다 | 진단이 틀렸다 | `-328` 예산표를 다시 세운다 |

## 남은 것

- **클라이언트 예측이 없는 한 `RTT` 는 남는다.** 이 측정으로 그것을 없앨 수는 없고, 얼마나
  남는지를 알 수 있다. 예측 도입은 `-145`·`-147` 의 "물리는 서버에서만" 결정과 부딪히므로
  팀 결정이 필요하다 — 별 이슈
- 스위치를 매번 손으로 켜는 것이 번거로워지면 **개발 빌드에서만 붙는 오버레이**로 만든다
- `-315` 메모의 "운송 수단 몸체 미복제" 는 코드를 읽어 보면 **클라이언트가 자기 것을 만든다**
  (`PartClamp.ApplyNetworkState` → `Release()` → `PartTractorActivator.Activate()` →
  `AddComponent<TransportVehicle>()`). 그 메모가 틀렸을 가능성이 크고, ③에서 부품을 함께
  옮겨 보면 실측으로 갈린다 — 갈리면 그 메모를 지운다
