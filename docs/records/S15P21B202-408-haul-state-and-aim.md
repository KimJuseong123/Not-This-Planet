## 2. 원인 — 집계가 아니었다

먼저 의심한 것은 "셋이 정확히 같은 방향으로 밀어야 하는데 사람이 그렇게 못 한다"
였다. **실측하니 집계는 이미 관용적이었다.** 실제 파츠 규격(Part_3, 745kg,
발자국 2.16 x 2.55)으로 배치를 훑었다.

| 배치 | 결과 |
| --- | --- |
| 한 면에 나란히 · 같은 방향 | 된다 |
| 파츠를 둘러싸고 각자 파츠 쪽으로 | 된다 |
| 한 면 · 방향이 ±25도로 흩어짐 | 된다 |
| 한 면 · 방향이 ±50도로 흩어짐 | 된다 |
| 잡고 둘러싸서 각자 자기 쪽으로 당김 | 된다 |
| 잡고 방향이 ±50도로 흩어짐 | 된다 |
| 셋이 밀다 한 사람이 0.3초 멈춤 | 유지된다 (0.5초 유예) |
| 인접한 **두 면**에 서서 옆으로 밀기 | **2명만 세어짐** |

방향을 합산한 뒤 정규화하므로 ±50도까지 견딘다. 한 사람이 잠깐 멈춰도
`PartPushReleaseSeconds` 유예로 유지된다.

### 2-1. 원인은 파츠 상태였다

| 상태 | `CanPush` | kinematic | 잡기 | 셋이 밀면 | |
| --- | --- | --- | --- | --- | --- |
| `Locked` (고정못 남음) | false | true | 거부 | 안 됨 | **의도** |
| `Free` (고정못 4개 다 뽑음) | true | false | 허용 | **된다** | |
| **`Placed` (조립대에 올림)** | **true** | false | 허용 | **2초에 0.0000m** | **결함** |
| `Welded` | false | false | 거부 | 안 됨 | 의도(`-250`) |
| 참가자 화면 | false | true | 거부 | 안 됨 | 의도(서버 판정) |

**`Placed` 가 거짓말을 했다.**

```
[측정] Placed + 조립 조인트 · 인원=3 · IsMoving=True
       힘=8843N · 2초 이동=0.0000m → 조인트가 붙잡는다
```

`PartAssembler.Assemble` 이 `Carried` 에서 `Placed` 로 올리면서
`PartAssemblyLink`(FixedJoint)로 아래 파츠에 묶는다. 그래서 `Placed` 파츠는
**밀 수 있다고 답하면서 실제로는 절대 움직이지 않았다.**

즉 실제로 밀 수 있는 것은 **고정못을 다 뽑았고 아직 조립대에 올리지 않은 파츠**
하나뿐이었고, 나머지 네 경우는 화면에서 구분되지 않았다.

## 3. 무엇을 고쳤나

### 3-1. `CanPush` 를 `Free` 뿐으로 좁혔다

```csharp
public bool CanPush =>
    _part != null && _body != null && !_body.isKinematic
    && _part.State == PartState.Free;
```

기획 §13 이 노리는 것은 "약 15m 떨어진 중앙 조립대를 향해 함께 밀기"(상세 5번)다.
그 대상은 고정못을 다 뽑아 바닥에서 떨어진 파츠, 즉 `Free` 다.

**조인트를 힘으로 이기게 만들지 않는다.** 이길 수 있게 하면 위에 얹힌 층까지 끌고
가거나 탑이 무너진다 — §22.4 의 붕괴가 밀기로 일어나면 안 된다. 조립대에 올린 파츠를
다시 옮기려면 견인 빔 경로가 있다(`Placed → Carried` 전이가 허용된다).

**답과 결과가 어긋나는 것이 이 이슈의 핵심이다.** 못 미는 것을 못 민다고 답해야
다음 사람이 같은 조사를 반복하지 않는다.

### 3-2. `PartPushAimDot` 을 0.5 → 0 으로

배치별 실측 dot(`Toward` 와 같은 계산):

| 배치 | dot | 각도 | 0.5 | **0** |
| --- | ---: | ---: | --- | --- |
| 측면에 서서 정면으로 | 1.000 | 0도 | 센다 | 센다 |
| 측면에 45도 비스듬히 | 0.707 | 45도 | 센다 | 센다 |
| **측면에 70도 비스듬히** | **0.342** | **70도** | **안 센다** | **센다** |
| 측면 끝에서 정면으로 | 0.837 | 33도 | 센다 | 센다 |
| 모서리 근처에서 정면으로 | 0.768 | 40도 | 센다 | 센다 |
| 앞면에 서서 옆으로 | −0.226 | 103도 | 안 센다 | 안 센다 |
| 앞면 모서리에서 옆으로 | −0.448 | 117도 | 안 센다 | 안 센다 |
| 측면인데 멀어지는 방향 | −1.000 | 180도 | 안 센다 | 안 센다 |

0 은 §13.1 "**당기기는 제공하지 않으며** 반대편으로 이동해 반대 방향으로 민다" 의
문면을 정확히 지키는 값이다 — 90도를 넘으면 파츠에서 멀어지는 쪽이다.

**그 이상 완화하지 않았다.** "앞면에 서서 옆으로 밀기"(dot −0.226)를 허용하려면
음수까지 열어야 하는데, 그러면 멀어지는 입력(−1.000)까지 함께 열린다. 그리고
**앞면에 몸을 대고 옆으로 걸어서는 파츠에 측면 힘을 줄 수 없으므로 안 되는 것이
물리적으로 맞다.** 실제로 그 사람은 파츠 옆으로 미끄러져 지나갈 것이다.

손으로 잡은 사람에게는 이 검사를 하지 않는다 — 잡으면 어느 쪽으로든 끌 수 있다.

## 5. 남은 것

### 5-1. 왜 안 되는지 화면에 알려주는 것이 여전히 없다

이 이슈는 **거짓말을 없앴을 뿐**이다. 이제 `Placed` 는 처음부터 거절하지만,
플레이어 화면에서는 `Locked` 라서 성립조차 안 한 것인지 인원이 모자란 것인지
여전히 구분되지 않는다.

`-400` 의 밀기 카메라는 "되는 순간" 을 알려주지만 "안 되는 이유" 는 아니다.
연출·표시를 만들 것인지는 별도 판단이 필요하다 — 2026-09-10 에 "셋 이상일 때만
연출을 만든다" 로 정했으므로, 안 되는 이유를 알리는 것은 그 결정 밖이다.

### 5-2. 3인 접속 실측이 0회다

이 이슈의 판정은 모두 서버의 `PartPush` 안에서 끝나므로 EditMode 로 잠글 수 있다.
다만 셋이 실제로 모였을 때의 체감(70도 관용이 충분한가)은 사람 셋이 있어야 안다.

### 5-3. 멀티 — 새로 보낼 상태는 없다

성립 조건을 좁히는 변경이고, 참가자가 알아야 하는 결과(밀고 있는가 · 방향 · 접촉
지점)는 `-400` 이 이미 `NetPlayer` SyncVar 로 보낸다. 조건이 좁아지면 그 값이
저절로 따라 좁아진다. `docs/network-sync-policy.md` §3 표의 "파츠 밀기 상태" 한 줄이
그대로 유효하므로 더할 줄도 없다.

## 6. 배운 것

**"안 된다" 의 원인이 세 겹이었다.**

| 겹 | 이슈 | 무엇이었나 |
| --- | --- | --- |
| 1 | `-394` | 밀기 힘이 지면 마찰의 25% |
| 2 | `-394` 후속 | 콜라이더가 자식에 있어 접촉 판정이 늘 false |
| 3 | **이 이슈** | **밀 수 있다고 답하는 상태가 실제로는 조인트에 묶여 있었다** |

세 겹 모두 **화면에 같은 모습**이었다 — 파츠가 꿈쩍하지 않는다. 그래서 하나를 고쳐도
증상이 그대로였고, "고쳤는데 여전히 안 된다" 가 반복됐다.

그리고 이번 것은 앞의 둘과 성격이 다르다. 1·2 는 **작동하지 않는 코드**였고, 3은
**작동한다고 답하는 코드**였다. 후자가 더 나쁘다 — 진단을 막는다. `IsMoving` 이 참인데
0.0000m 이면 그 위에 무엇을 더 만들어도(카메라 전환 같은) 함께 헛돈다.

> **불리언이 "할 수 있다" 를 답할 때는 그 결과를 실제로 재 본 검증이 있어야 한다.**
> `CanPush` 는 `-250` 부터 `Placed` 를 포함했고 그 기간 내내 아무도 이동 거리를
> 재지 않았다.
