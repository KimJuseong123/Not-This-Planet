# S15P21B202-538 — 저중력장으로 띄운 부품이 참가자 화면에서만 떨리던 것

> 신고: "호스트는 괜찮은데 참가자가 볼 때 저중력장으로 우주선물체를 띄우면 덜덜 떨리는
> 문제가 있다. 이것도 동기화인가?"

## 한 줄

**동기화는 맞았다. "안 보내서" 가 아니라 "받은 것을 어느 시계로 재생하느냐" 가 문제였다.**

## 무엇이 잘못돼 있었나

자세는 제대로 갔다(`docs/network-sync-policy.md` 부품 자세 P2 ✅). 참가자는 그 자세를
`WorldSync.FollowOnClient` 에서 **`Update` 마다 프레임 폭으로** 쫓았다.

```csharp
float t = 1f - Mathf.Exp(-Smoothing * Time.deltaTime);
...
body.position = Vector3.Lerp(body.position, targets[i].Position, t);
```

여기서 서로 맞지 않는 시계가 셋 겹친다.

| 시계 | 주기 |
| --- | --- |
| 서버가 자세를 보내는 주기 | 30Hz |
| 참가자의 프레임 주기 | 기계마다 다르다 |
| 강체 `transform` 이 갱신되는 물리 주기 | 100Hz |

지수보간은 33ms 계단의 **모서리를 둥글릴 뿐 계단 자체를 없애지 못한다.** 자세가 막 도착한
직후 프레임은 남은 거리가 커서 크게 가고, 다음 프레임부터 작게 간다. 33ms 주기의 톱니가
그대로 속도에 나타난다.

호스트에는 이 톱니가 없다. 호스트의 부품은 물리가 100Hz 로 적분한 결과이고 저중력장의
유지 가속이 연속이라 속도가 매끄럽다.

**왜 하필 저중력장인가** — 부품이 느리게·오래·시야 안에서 움직이는 유일한 순간이기
때문이다. 목표가 고정된 부품(바닥에 놓인 것)은 480프레임 중 479프레임이 완전 정지였다.
들거나 던진 부품은 빠르고 짧게 움직여 톱니가 묻힌다.

## 실측

임시 EditMode 프로브로 쟀다(조사용이라 커밋하지 않았다). 실제 `LowGravityField` 가
500kg 부품을 −6m 에서 목표 높이 −4m 로 띄우는 동안, 같은 상승을 호스트 화면과 참가자
화면으로 각각 기록했다.

지표는 **이웃한 두 프레임의 이동량 비율**이다. 1.00배면 옆 프레임과 같은 속도로 간 것이다.

| 참가자 fps | 호스트 화면 | 참가자 화면 |
| --- | --- | --- |
| 60 | 1.70배 | 1.56배 |
| 72 | 1.78배 | 1.53배 |
| 100 | 1.18배 | 1.36배 |
| 120 | 1.20배 | **1.47배** |
| 144 | 1.18배 | **1.98배** |
| 165 | 1.21배 | **2.13배** |

144fps 에서 프레임별 실제 이동량(m):

```
호스트   0.04942 0.05011 0.00000 0.05067 0.05111 0.00000 0.05143 0.05163 ...
참가자   0.05529 0.03101 0.00000 0.05048 0.02044 0.00000 0.08210 0.03325 ...
```

호스트는 0.0494~0.0517 안에 있다(±3%). 참가자는 0.0204~0.0821 로 **4배 넘게 출렁인다.**
`0.00000` 은 그 프레임에 물리 스텝이 없었다는 뜻이고 **양쪽에 똑같이** 생긴다.

**100fps 아래에서는 재현되지 않는다.** 60·72fps 에서는 호스트 쪽이 오히려 더 거칠다 —
한 프레임에 물리 스텝이 2개 들어갔다 1개 들어갔다 하기 때문이다.

### 확인하고 배제한 것

| 의심 | 결과 |
| --- | --- |
| 참가자가 물리를 같이 돌린다 | ❌ `LowGravityField.Tick` 이 `!_physicsAuthority` 에서 반환하고 `FollowOnClient` 이 매 프레임 kinematic 으로 되돌린다 |
| 오래된 패킷이 섞인다 | ❌ `ApplyPoses` 가 `IsNewer` 로 막는다 |
| `body.position` 게터가 묵은 값을 준다 | ❌ 쓴 값을 그대로 준다. 다만 `transform` 은 다음 물리 스텝까지 안 따라온다(이것이 셋째 시계) |
| 세우기(`Upright`)가 공회전한다 | ❌ 12초 동안 기울기 20.0577도 고정, 부호 전환 0회 |
| 씬의 부품에 보간이 걸려 있다 | ❌ `Stage1_Astra.unity` 의 `Part_1~4` 는 전부 `m_Interpolate: 0` |

## 고친 것

**참가자의 추종을 물리 스텝으로 옮기고, `MovePosition` 으로 옮기고, 보간을 켰다.**

| 참가자 fps | 현행 | 고정스텝만 | **고정스텝+보간** | 보간만 |
| --- | --- | --- | --- | --- |
| 60 | 1.56 | 1.97 | **1.34** | 1.92 |
| 72 | 1.53 | 2.03 | **1.37** | 2.35 |
| 120 | 1.47 | 1.38 | **1.27** | 1.41 |
| 144 | 1.98 | 1.34 | **1.27** | 1.60 |
| 165 | 2.13 | 1.28 | **1.24** | 1.51 |

고정스텝+보간만이 모든 프레임레이트에서 1.4배 아래다.

1. `WorldSync.FixedUpdate` 가 `FollowOnClient` 을 부른다. `Update` 는 더는 부르지 않는다.
2. 추종이 `Time.fixedDeltaTime` 으로 밟는다.
3. `body.position =` 대신 `MovePosition`/`MoveRotation` 을 쓴다. 키네마틱 강체에 위치를
   직접 대입하면 **순간이동**으로 취급되어 그 스텝의 보간이 건너뛰어진다.
4. `PrepareClientBody` 가 kinematic 과 `RigidbodyInterpolation.Interpolate` 를 함께 세운다.
   `PrepareClient` · `OnVehicleActivated` · `FollowOnClient` 의 방어선이 모두 이것을 부른다.
5. `SendFromServer` 의 `sendTimer = 0f` 를 `NextSendTimer` 로 바꿨다. 남은 시간을 버리면
   실제 주기가 프레임 시간만큼 늘어난다 — 144fps 호스트에서 10초에 300번이 아니라 288번.
   이번 떨림의 원인은 아니지만 계단을 흔드는 쪽이다.

**회전도 같이 고쳤다.** `Slerp` 도 같은 필터를 타므로 위치만 고치면 회전이 남는다.

운석·도구·운반체도 같은 `FollowOnClient` 을 타므로 한 번에 같이 고쳐진다.

### 물리친 안

| 안 | 왜 안 했나 |
| --- | --- |
| 보간만 켜기 (한 줄) | 잰 결과 부족하다. 72fps 2.35배로 **현행보다 나쁘다** — 불규칙하게 쓰인 두 자세 사이를 매끄럽게 이어도 불규칙은 남는다 |
| 고정스텝 추종만 (보간 없이) | 고프레임은 좋아지나 60·72fps 가 1.97·2.03 으로 나빠진다 |
| 전송 주기 30Hz → 60Hz | 톱니 주기를 줄일 뿐 없애지 못하고 대역폭이 두 배가 된다 (부품 8개 기준 초당 6.7KB → 13.4KB) |
| 스냅샷 보간으로 전환 | **제대로 된 답이다.** 다만 `WorldSync.Pose` 에 속도가 없고 버퍼·시계 동기까지 필요해 이 티켓을 넘는다. 따로 티켓으로 남긴다 |
| 보간을 끄고 `transform` 에 직접 쓰기 | 충돌 판정이 강체 자세와 어긋난다. `-352` 가 방어선까지 넣어 지킨 전제를 깬다 |

## 검증

`WorldSyncFollowCadenceTests` **19개**. 지표를 테스트 안에서 직접 그려 재고, 배선은
따로 지킨다.

- `AboveThePhysicsRate_TheNewCadenceIsSteadierThanTheOldOne` (120·144·165fps)
- `TheNewCadenceStaysSteadyAtEveryFrameRate` (60~165fps, 1.45배 미만)
- `TheOldCadenceWasWorseAtHighFrameRates_WhichIsWhatWasReported` — 이것이 없으면 위의
  둘이 "원래 문제가 없었다" 로도 통과한다
- `TheFrameRateNoLongerChangesHowSteadyItLooks` — 옛 방식의 본질은 프레임레이트가 화면
  품질을 바꾼다는 것이었다
- `PreparingAClientBodyMakesItKinematicAndInterpolated` — 실제 `Rigidbody` 로 확인
- `TheFollowIsWiredToTheFixedStepAndMovesRatherThanTeleports` — 배선 가드
- 전송 타이머 5개

**지표를 잘못 고르면 결함이 지표에 삼켜진다.** 처음에는 전체 구간의 변동계수로 쟀는데,
물체가 가속했다 감속하는 **진짜 속도 변화**가 지표를 채워 호스트와 참가자가 똑같이 나왔다
(둘 다 16배·cv 0.9). "차이 없음" 으로 넘길 뻔했다. "덜덜" 은 국소 현상이라 국소적으로 재야
한다 — 그래서 이웃한 두 프레임만 비교한다.

### 대조 실험

고친 곳을 하나씩 도로 망가뜨려 테스트가 잡는지 봤다.

| 대조 | 잡혔나 |
| --- | --- |
| 1. 전송 타이머를 다시 `0f` 로 되돌린다 | ✅ (아래 참고) |
| 2. 끊긴 프레임의 빚을 안 자른다 | ✅ `ALongHitchDoesNotMakeItSendABurstAfterwards` |
| 3. `FollowFactor` 의 0 이하 방어를 뺀다 | ✅ `AZeroIntervalDoesNotSpinTheTimerIntoNonsense` |
| 4. `FixedUpdate` 를 없앤다 | ✅ 2개 |
| 5. 참가자 부품의 보간을 안 켠다 | ✅ 2개 |
| 6. 추종을 다시 프레임 폭으로 밟는다 | ✅ 배선 가드 |
| 7. `MovePosition` 대신 직접 대입한다 | ✅ 배선 가드 |

**대조 1이 처음에는 안 잡혔다.** 19개가 전부 통과했다. `NextSendTimer` 를 아무리 검증해도
보내는 쪽이 그것을 부르지 않으면 소용이 없었던 것이다 — 함수만 재고 **호출부를 안 봤다.**
배선 가드에 `SendFromServer` 검사를 더해 잡히게 했다.

> 같은 실수를 이번이 처음이 아니다. `bandSpread`(값이 아무 일도 안 했다),
> `ZeroDegreesIsTheOldUprightPin`(축 벡터만 봐서 거울을 통과시켰다) 과 같은 계열이다.
> **중간값을 재는 테스트는 진짜 결함을 통과시킨다.**

### 솔직히 적어 두는 한계

대조 6·7은 **배선 가드(글자 검사)만이 잡았다.** 수치 검증은 두 방식을 테스트 안에서
모형으로 그리므로 제품 코드가 어느 시계에 매달려 있는지는 보지 못한다. PlayMode 테스트
어셈블리가 생기면 그때 실제 경로로 옮겨야 한다(`-448`·`-505`·`-519` 에서도 막힌 자리다).

**보간 효과 자체는 EditMode 에서 잴 수 없다** — 렌더 루프가 없다. 2프로세스 눈 확인이
필요하고, 그때 **참가자 쪽 fps 를 함께 적어야** 이 진단이 맞는지 확정된다.

## 남은 것

1. **스냅샷 보간** — 톱니를 원리적으로 없애는 답. `Pose` 에 속도를 싣는 것부터.
2. **2프로세스 눈 확인** — 참가자 fps 기록 포함.
3. `Part_1~4` 의 `m_Interpolate: 0` 은 그대로 뒀다. 호스트에서는 물리가 직접 적분하므로
   문제가 없고, 씬 에셋을 건드리면 이 변경의 범위가 넓어진다.
