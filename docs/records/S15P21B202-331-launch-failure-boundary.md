# S15P21B202-331 발사 실패가 실제로 일어나는 경계를 측정하고 잠근다

## 결론 — 손잡이를 돌리지 않았다

착수 전 산술 개산은 **"용접률 15% 만 넘으면 §15.2 안에서 만들 수 있는 어떤 탑도
부서지지 않는다"** 였다. 그래서 용접률→강도 매핑을 곡선으로 바꾸거나
`WeldedBreakTorque` 를 낮출 계획이었다.

**측정해 보니 틀렸다.** 실패는 이미 의도대로 일어난다. 상수를 하나도 바꾸지 않고,
지금 동작을 **어느 장치가 무엇을 걸러내는지까지** 검증으로 잠갔다.

## 측정 결과

```
           0.0   0.2   0.4   0.6   0.8   ← 층당 오프셋(m)
   0.00      J     J     J     N     T
   0.15      J     O     J     N     T
   0.30      O     O     J     N     T
   0.50      O     O     J     N     T
   0.75      O     O     J     N     T
   1.00      O     O     J     N     T

O = 통과
J = 발사 중 접합부 파손
N = 카운트다운이 끝나지 않았다
T = 탑승 조건 미달
```

층당 오프셋은 **같은 방향으로 누적**시킨 값이다. 지그재그로 쌓으면 서로 상쇄되어
오히려 안전하므로, 이 배치가 무게중심이 가장 크게 벗어나는 경우다.

## 걸러내는 장치가 셋이고, 플레이어가 보는 장면이 다르다

| 조건 | 결과 | 근거 |
|---|---|---|
| 용접률 15% 이하 · 똑바로 | **발사 중 파손** | §22.3 "실제 용접 길이에서 생기는 하중" |
| 층당 0.4m 어긋남 · **완전 용접이어도** | **발사 중 파손** | §22.3 "비뚤어진 배치에서 생기는 하중" |
| 층당 0.6m 어긋남 | 카운트다운이 취소된다 | §22.3 "카운트다운 중 탑이 무너지면" |
| 층당 0.8m 어긋남 | 문이 열리지 않는다 | §15.1 조립 조건 · §22.3 "자기 무게로 서 있는지 먼저 확인" |

**용접으로 비뚤기를 만회할 수 없다.** 용접은 접합을 강하게 하지만 무게중심을 축으로
되돌려 주지 않는다. 층당 0.4m 어긋난 탑은 완전히 용접해도 부서진다 — 여기서 "자유
적층" 이 의미를 갖는다.

## 개산이 왜 틀렸나

개산은 **최하단 접합부의 정적 축방향 힘**만 봤다.

```
무게      2,000 × 2.8            =  5,600 N
추력      5,600 × 3.2            = 17,920 N
축방향 힘  1,500 × (6.16+2.8)   = 13,440 N
breakForce = Lerp(8,000, 200,000, 용접률) → 3% 만 넘으면 버틴다
```

빠진 것이 셋이다.

1. **토크가 지배적이다.** `breakTorque` 는 `breakForce` 의 1/1.33 수준(5,000 대 8,000)인데,
   모멘트팔이 조금만 생겨도 토크가 힘보다 먼저 한계에 닿는다.
2. **노즐이 무게중심 아래에 있다.** `LaunchNozzleDrop`(1.0m) 만큼 낮은 곳에서 밀어
   올리므로 **추력 자체가 모멘트팔을 갖는다.** 개산은 이것을 0 으로 뒀다.
3. **과도 응답을 무시했다.** 5초 램프 동안 탑이 흔들리며 순간 하중이 정적 값을 넘는다.
   물리는 그것을 그대로 겪는다.

**이것이 §22.3 이 "하중을 계산해서 접합부에 나눠 주지 않는다" 를 정한 이유다.** 계산은
틀렸고 물리는 맞았다.

## 점수제를 쓰지 않았다

§3.4 가 "자동 배치와 **정렬 점수는 제공하지 않는다**" 로, §22.3 이 "**무작위 실패를
사용하지 않는다**" 로 방식을 지정한다.

그리고 점수를 만들면 **진실의 출처가 두 개가 된다.** 점수는 실패라 하는데 물리는
버티는 상황이 생기고, §3.4 때문에 점수를 화면에 못 보여주니 플레이어는 왜 실패했는지
알 수 없다. 물리로 실패하면 **어느 접합이 끊어졌는지 눈에 보인다.**

## 검증

새 `LaunchFailureTests` 7개.

```
develop : 786개 중 759 통과 / 27 실패
331     : 793개 중 766 통과 / 27 실패

331 에서만 실패 : 없음
```

**판정이 아니라 이유까지 확인한다.** 처음에는 `Assert.AreEqual(LaunchState.Failed, ...)`
만 봤는데, 그러면 층당 0.8m 어긋난 탑이 **"탑승 불가" 로 걸러진 것을 "발사 시험이
판정했다" 로 착각한다.** 두 결과는 플레이어가 보는 장면이 전혀 다르다.

```csharp
static bool BrokeUnderLoad(Result result) =>
    result.State == LaunchState.Failed
    && result.Reason != null
    && result.Reason.Contains("접합부");
```

- `AStraightFullyWeldedTower_Passes` — **과잉 교정 방어선.** 손잡이를 돌릴 때 가장 먼저
  깨지는 것이 이것이다
- `ASloppilyWeldedTower_BreaksDuringTheLoadTest` · `AnUnweldedTower_...`
- `ASlightlyOffsetTower_BreaksEvenWhenFullyWelded`
- `ABadlyOffsetTower_IsStoppedBeforeLaunch` — **앞단에서 막혀야** 한다고 못박는다
- `TheSameTowerGivesTheSameResult` — §22.3 무작위 없음
- `MeasureTheFailureBoundary` — 격자를 돌며 위 표를 로그로 남긴다. 판정하지 않는다

`MeasureTheFailureBoundary` 를 남긴 이유는 **손잡이를 돌릴 다음 사람을 위해서다.**
상수를 만지면 이 표가 어떻게 움직이는지 바로 볼 수 있다.

## 남은 것

- **인게임 확인.** 층당 0.4m 어긋난 탑을 실제로 만들어 발사해 보면 부서지는지
- **공중에서 부서지며 떨어지게** — 지금은 접합부가 끊어지는 프레임에 `Fail()` 이
  상태만 바꾸고 `Tick` 이 돌아나가 **추력이 사라진다.** 그래서 "터진다" 가 아니라
  "주저앉는다" 로 보인다. 추력을 짧게 유지하는 것이 다음 작업이다
- **태블릿이 앞단 차단 이유를 알려줘야 한다.** 측정에서 층당 0.6~0.8m 는 발사 시험까지
  가지 않고 문이 열리지 않거나 카운트다운이 취소된다. 지금은 플레이어가 이유를 알
  방법이 없다 — `ShipAssembly.Blocker` 가 문장을 만들어 두고 **읽는 곳이 0곳**이다
