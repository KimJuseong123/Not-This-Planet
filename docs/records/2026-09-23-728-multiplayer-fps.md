# 728 실제 로컬 4인 멀티 FPS 측정

## 결론

**수정 커밋 `9684cb0c28a329b0c43cebbb0718169bc593290c`에서도 60 FPS 유지 실패를 재현했다.** 화면을 직접 조작하지 않고 Windows 게임 실행 파일 4개를 실행하여 실제 Stage1, Mirror 연결, 게임 물리 및 카메라 렌더링을 계측했다. 에디터 단위 테스트의 처리 시간으로 FPS를 환산한 결과가 아니다.

한 참가자만 렌더링하는 조건에서도 1440p 대기 평균 39.33 FPS, 1080p 대기 평균 57.94 FPS였다. 1080p의 용접 가이드가 실제 표시된 342프레임에서는 평균 44.94 FPS였다. 따라서 이전 최적화가 전체 게임의 60 FPS를 보장하지 않는다.

## 환경과 측정 방법

- 2026-09-23, Windows, Unity 6000.5.4f1 Development Windows x64 빌드, Direct3D11.
- Core i7-13700H, 시스템 메모리 32,327 MiB, RTX 4050 Laptop GPU 6,141 MiB, 드라이버 591.44.
- 실제 적용 품질 Ultra(index 5), VSync 0, 제한 120 FPS. 시작 인자의 1920×1080은 게임 설정이 2560×1440으로 덮어썼다. 마지막 실행은 설정 적용 후 1920×1080을 다시 고정하고 로그로 확인했다.
- 같은 PC에 호스트 1명과 참가자 3명, 127.0.0.1 KCP 연결. 백엔드 로그인/로비 대신 검증용 NetworkManager와 자동 입력을 사용했다. 실제 Stage1_Astra 및 게임의 NetPlayer/WorldSync/도구 코드를 실행했다.
- 배경 프로세스로 실행하고 OS 키보드·마우스·화면 조작은 하지 않았다. 카메라 렌더링 완료 콜백을 프레임별로 확인했다. 그래픽 참가자의 측정 프레임은 모두 실제 메인 카메라 렌더링 콜백이 있었다. 모니터의 물리적 화면 제시 간격을 측정한 것은 아니다.
- 로딩 후 준비 대기, 각 단계 25초씩 약 100초. 단계 전환 프레임도 포함. 프레임 시간은 실제 Update 간 경과 시간이며, 평균 FPS는 프레임 수 / 누적 시간이다. 느린 프레임은 16.667ms 초과로 정의했다.
- FrameTimingManager의 GPU/CPU 시간 분해 값은 유효하지 않아 원인 판정에 사용하지 않았다. GPU 사용률은 별도로 실행 중 표본 조회했다.

## 결과

### A. 4명 모두 1440p 렌더링

| 참가자 | 대기 평균 FPS | 이동 평균 FPS | 파츠 근접 평균 FPS | 마지막 단계 평균 FPS |
|---|---:|---:|---:|---:|
| 호스트 | 7.26 | 8.09 | 7.39 | 7.33 |
| 참가자 1 | 7.28 | 8.48 | 9.49 | 11.97 |
| 참가자 2 | 7.60 | 8.21 | 7.76 | 8.47 |
| 참가자 3 | 7.82 | 7.78 | 7.07 | 7.62 |

모든 프레임이 16.667ms를 초과했고, 가장 긴 프레임은 호스트의 316.41ms였다. GPU 사용률 표본 100%, GPU 메모리 약 5.4~5.6GiB. **한 GPU에 4화면의 부하를 겹친 스트레스 조건이며, 별도 PC 4대의 성능으로 일반화할 수 없다.** 가이드 표시와 비드 생성은 확인되지 않아 이 실행을 용접 프리징 재현으로 판정하지 않는다.

### B. 4인 네트워크 유지, 참가자 1만 1440p 렌더링

호스트와 나머지 두 참가자는 `-batchmode -nographics`로 실행했다. 이 세 프로세스의 루프 속도는 화면 FPS 결과에 포함하지 않는다.

| 참가자 1 구간 | 평균 FPS | 16.667ms 초과 비율 | P95 프레임 ms | 최대 프레임 ms |
|---|---:|---:|---:|---:|
| 대기 | 39.33 | 99.80% | 28.86 | 34.32 |
| 이동 | 42.16 | 96.68% | 33.09 | 59.16 |
| 파츠 근접 | 39.64 | 73.60% | 35.53 | 97.99 |
| 마지막 입력 단계 | 41.22 | 99.71% | 30.57 | 42.22 |

GPU 사용률 표본 100%, GPU 메모리 약 1.4GiB. 모든 구간에서 4명 연결을 확인했다. 이 배치에서는 연결부가 이미 접합된 상태여서 가이드 표시가 1프레임에 그쳤고, 실제 비드는 생성되지 않았다. 마지막 단계를 지속 용접 검증 성공으로 해석하면 안 된다.

### C. 참가자 1만 1080p 렌더링, 미접합 파츠 근접

가이드가 이미 연결된 파츠를 제외하는 점을 반영해, 마지막 실행에서는 실제 핵심 파츠 네 개를 미접합 상태로 쌓고 키네마틱으로 고정했다. 자동 배치 과정의 흔들림을 줄이기 위한 검증 조건이며 정상 게임의 조립 조작 전체를 재현한 것은 아니다. 참가자를 발사대에서 2.5m 떨어진 곳에 배치하고 기존 도구 코드로 용접 건을 잡게 했다.

| 참가자 1 구간 | 평균 FPS | 16.667ms 초과 비율 | P95 프레임 ms | 최대 프레임 ms |
|---|---:|---:|---:|---:|
| 대기 25초 | 57.94 | 63.63% | 20.99 | 27.16 |
| 이동 25초 | 63.96 | 37.31% | 23.83 | 37.10 |
| 파츠 근접 전체 25초 | 51.19 | 76.60% | 25.90 | 77.05 |
| 가이드 실제 표시 프레임만 | 44.94 | 95.61% | 27.90 | 34.95 |

가이드 표시 표본은 측정 시작 후 50.758~58.291초 사이의 342프레임이다. 참가자 위치, 도구 소유, local=True, down=False, guide=True를 실행 로그로 확인했다. GPU 사용률 표본은 이 실행에서도 100%였다.

근접 단계 후반에는 전투 상황에서 도구를 놓고 기절했으며 마지막 단계에도 기절 상태가 이어졌다. 따라서 마지막 단계 평균 89.89 FPS는 **용접 성능 수치로 사용하지 않는다.** 모든 실행에서 비드 생성 수가 0이었으므로 용접 성장/절단/상태 덮어쓰기 재현은 여전히 미검증이다. 가이드 표시 구간에서 사용자가 신고한 0~8 FPS 수준의 급격한 프리징은 이번 실행으로 입증하지 못했다.

## 해석과 남은 확인

- 60 FPS 유지 실패 자체는 확인했다. 1440p에서 1080p로 낮추면 대기/이동 속도가 크게 개선되고 GPU 포화가 관측되어, 렌더링 비용이 유력한 추가 병목이다. 특정 셰이더나 패스로 원인을 확정하려면 GPU 프로파일링이 필요하다.
- 참가자가 각자 렌더링해도 로컬 GPU/CPU 작업이 프레임 예산을 넘기면 FPS가 낮아진다. 이번 수치가 호스트가 렌더링 결과를 보내느라 생긴 것이라는 증거는 없다.
- 같은 PC에서 4개의 네트워크/물리 루프가 CPU를 공유하며, 전력 상태·백그라운드 부하를 완전히 통제하지 않았다. Release 빌드, 별도 PC, 실제 인터넷 지연/손실, 장시간 플레이 성능을 보장하지 않는다.
- 이전 최적화 전의 동일 게임 빌드를 이번에 측정하지 않았으므로, 이 결과로 최적화의 실제 FPS 개선 폭을 주장하지 않는다.
- 다음 검증은 GPU 패스별 비용 및 일반 설정에서의 목표 FPS, 별도 PC 4인 환경, 정상 조작으로 지속 용접/절단과 상태 되감김, 장시간/늦참/호스트 이전이다.

## 오류와 보관 자료

- 그래픽으로 실행한 참가자의 계측 중 Error/Exception/Assert는 모두 0이었다. 모든 테스트 프로세스는 완료 로그를 남기고 종료했다.
- 그래픽 없는 호스트에서는 시작 컷신의 `AtmosphereMeteorShower`가 Meteor 셰이더를 찾지 못한다는 오류가 한 번씩 있었다. 그래픽 없는 장치에서 시각 효과를 실행한 검증 구성의 제약이다. 그래픽 실행 A에서는 이 오류가 없었다.
- A의 한 참가자에서 기존 실행 로그 파일명이 초 단위로 겹쳐 공유 위반 경고가 한 번 있었다. 별도 `-logFile`로 지정한 참가자별 원본 로그와 CSV는 모두 보존됐다.
- 로컬 증거: `METAGAME/Logs/Network728/fps-all-render/`, `fps-single-render/`, `fps-1080/`의 `peer-*.csv`, `peer-*.log`, `summary.json`.
- 빌드 로그: `fps-build-final.log`, `fps-build-1080.log`. 분석기: `analyze_fps.py`. 최종 검증 전용 소스는 같은 로그 폴더의 `fps-fixture/`에 보관한다. 로그/실행 파일은 Git에 포함하지 않는다.
- 검증용 소스와 생성 씬은 Assets에서 제거하고 Unity가 자동 갱신한 설정은 원복했다. 이번 후속 기록은 제품 런타임/씬/프리팹 변경을 포함하지 않는다.
