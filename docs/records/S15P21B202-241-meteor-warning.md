# S15P21B202-241 — 운석 낙하 예고 지면 표시

[문서 안내](../README.md) → [작업 기록](README.md) → 운석·환경

운석 착탄 위치와 충격 반경을 지면에 표시하는 예고 표현을 구현했습니다. 계산과 표시의 분리, 원판 표현, 지형 경사를 따르지 않는 한계를 기록합니다.

본문의 “현재”, 검증 수치, 미완료 항목은 **기록 당시 기준**입니다. 후속 변경은 관련 이슈와 [주제별 색인](README.md)을 함께 확인합니다.

운석이 어디 떨어질지 볼 방법이 없었다. 기획 §17.2 의 원형 표시가 구현되어 있지 않았다.

`PendingMeteorDrop`(예고 데이터)을 읽는 코드가 런타임 전체에 <b>하나</b>뿐이었다.

```
Stage1AtmosphereAlert.cs:48
    alert = Mathf.Max(alert, pending[i].Progress01);
    atmosphere.SetAlertIntensity(alert);      // 하늘·조명 경보 강도만 올린다
```

<b>예고 데이터를 화면에 그리는 코드가 구현되지 않았다.</b> 데이터는
S15P21B202-234 부터 정확했다 — 예고 3초와 실제 착탄이 맞는다.

## 먼저 채운 것 — 예고가 충격 반경을 몰랐다

§17.2 는 "<b>실제 충격 범위와 같은 크기</b>의 원형 표시" 다. 그런데
`PendingMeteorDrop`이 가진 것은 셋뿐이었다.

```
ImpactPoint · RemainingSeconds · WarningSeconds
```

S15P21B202-234 가 소형(2m)·중형(3.5m)을 나눴는데 그 값이 예고로 <b>전달되지 않았다.</b>
안 채우면 중형에서 2m 원을 보고 피했는데 3.5m 로 맞는다.

`ImpactRadius`를 더했다. 그리고 크기 → 반경 매핑을 `Meteor.RadiusFor(MeteorSize)`
하나로 모았다 — 스포너가 예고를 만드는 시점에는 운석이 아직 없을 수도 있어, 두 곳에서
각자 분기하면 표시와 실제가 어긋난다.

## 계산과 그리기를 나눴다

`MeteorWarningLook`이 <b>값만</b> 낸다. `MeteorWarningView`가 그 값을 오브젝트에
옮긴다.

나눈 이유는 <b>검증</b>이다. 렌더러와 머티리얼을 세우지 않고 규칙을 잠글 수 있고,
[Art] 가 실제 데칼로 바꿔도 규칙은 그대로 산다.

| 값 | 근거 |
| --- | --- |
| `DiameterOf` = 반경 × 2 | §17.2 "실제 충격 범위와 같은 크기" |
| `RingColorOf` 주황 → 붉게 | §17.2 "주황색으로 시작해 … 붉게 변하고" |
| `FillOf` = `Progress01` | §17.2 "안쪽이 채워진다" |
| `StageOf` / `BlinkOf` | §17.2 "마지막 0.5초 빠른 점멸" + §18.1 "타격 가능한 순간 강한 점멸" |

### 점멸 경계가 방망이와 같은 값이어야 한다

```csharp
if (remaining <= PhysicsScale.MeteorWarningImminentSeconds) return Imminent;   // 0.5초
if (remaining <= PhysicsScale.BatSwingWindowSeconds)        return Strikable;  // 1초
return Filling;
```

<b>`BatSwingWindowSeconds`를 그대로 쓴다.</b> 따로 적으면 "점멸하는데 안 맞는" 구간이
생기고, 플레이어는 이유를 알 수 없다.
`BlinkingStartsExactlyWhenTheBatCanHit`가 그 경계를 잠근다 — 이 검증이 §17.2 와 §18.1 을
잇는다.

차오르는 동안에는 <b>점멸하지 않는다.</b> 예고 내내 깜빡이면 마지막 0.5초의 "빠른
점멸" 이 눈에 띄지 않는다.

## 코드로 만든 원판이다

<b>URP 데칼을 쓰지 않았다.</b> 프로젝트에 `DecalProjector` 사용처가 0곳이고 Renderer
설정에 데칼이 켜져 있지 않다. 켜는 것은 렌더 파이프라인 결정이며 진행 중인 URP 전환과
얽힌다.

`Prim.Pipe`로 납작한 원통을 만들고 `Prim.Ghost` 재질을 준다. 비드를 `Prim.Ball`로
시작한 것과 같은 방식이다(S15P21B202-226). [Art] 가 실제 데칼을 주면 `CreateMarker`
하나만 바꾼다.

`GhostSurface` 셰이더를 고른 이유는 <b>투명이고 `_Pulse`가 있다</b>는 것이다.
`FlatUnlit`은 불투명(`ZWrite On`)이라 지면과 z-fighting 하고 알파가 없다.

### 두 조각으로 만든다

테두리가 <b>충격 범위</b>를, 안쪽이 차오르며 <b>남은 시간</b>을 알린다. 하나로 합치면
둘 중 하나를 잃는다 — 크기로 시간을 표현하면 범위를 알 수 없고, 색으로만 표현하면
얼마나 남았는지가 흐리다.

점멸은 <b>알파에만</b> 곱한다. 색상까지 흔들면 주황 → 붉게 가는 것이 묻힌다.

### 머티리얼을 표시마다 따로 갖는다

`Prim.Dough`는 색별로 캐시하는데, 여기서는 색이 <b>매 프레임</b> 바뀐다. 캐시를 쓰면
프레임마다 머티리얼이 하나씩 늘어난다. `Prim.Ghost`가 부를 때마다 새로 만들어 주므로
그것을 들고 색만 바꿔 쓰고, `OnDestroy`에서 지운다.

### 남는 표시는 지우지 않고 숨긴다

공세 후반에는 동시에 다섯 개가 뜨고 사이사이 0 이 된다. 매번 만들고 지우면 GC가 돈다.
`MarkersAreReused_NotRecreated`가 예고 → 0 → 예고 순환에서 개수가 늘지 않는 것을 본다.

## 지형 경사를 따라가지 않는다 — 안고 가는 한계

납작한 원판이므로 언덕에서는 지면을 파고들거나 뜬다. `MeteorWarningLift`(0.03m)로
띄워 z-fighting만 피했다.

그것이 문제가 될 만큼 기울어진 곳은 아레나 중앙에 적고, URP 데칼로 바꾸면 해결된다.
<b>지금 고치지 않는 이유는 데칼을 켜는 것이 [Level]·[Art] 의 렌더 파이프라인
결정이기 때문이다.</b>

## 검증

`MeteorWarningTests` <b>16개 전부 통과</b>. EditMode 전체 <b>440개 중 427 통과</b>.

실패 13개는 develop에 이미 있던 것이다(S15P21B202-232 건). `origin/develop`만
체크아웃해 13개 전부 거기서 같이 실패하는 것을 S15P21B202-237 에서 확인했다.

| 검증 묶음 | 무엇 |

| 예고가 반경을 갖는다 | 실제 운석의 반경과 같은지 · 매핑이 §17.7 값인지 · 카운트다운에 안 바뀌는지 |

| 표시와 풀 | 예고 개수와 같은지 · 재사용하는지 · 위치·지름·콜라이더 없음 |

   `S15P21B202-215-terrain-data-repair` 브랜치가 있지만 develop에 들어오지 않았다.
