# 플레이 로그 상한과 떠돌이 이미지 보호 — 정한 값과 이유 (S15P21B202-467)

2026-09-12 · 관련: `-443`(플레이 로그) · `-457`(EC2 정리) · `-405`(릴리스 배치)

리뷰 없이 머지된 다섯 MR 의 지적을 반영하면서 **운영 규칙이 되는 값**을 정했다.
값이 코드 상수와 주석에만 있으면, 알파 인원이 늘었을 때 누가 왜 이 값인지 찾지 못한다.
여기가 그 근거다.

## 1. 플레이 로그 업로드 상한

`POST /logs` 는 **로그인 없이도 열려 있는 자리**다. `/auth/guest` 가 `permitAll` 이라
**토큰을 새로 받을 때마다 새 userId** 가 되고, 그래서 사용자별 상한만으로는 아무것도
막지 못한다. 공개 서버에서 그것은 디스크를 채우는 길이다.

| 무엇 | 값 | 넘으면 | 왜 이 값인가 |
|---|---|---|---|
| 한 판의 크기 | 8 MB | 400 | 클라이언트(`RunLog.MaxBytes`)와 같은 값. nginx 상한은 9 MB |
| 사용자별 | 10분에 6개 | 429 | 시작할 때 최대 3개를 보낸다. 그 두 배 |
| **전역 개수** | **시간당 200개** | 429 | 팀원 6명이 하루에 여러 번 켜도 **시간당 수십 개**다. 정상 사용의 몇 배 |
| **전역 바이트** | **시간당 300 MB** | 429 | 8 MB 짜리 37개. 개수만 세면 8 MB × 200 = 1.6 GB/시간이 된다 |
| **디스크 여유 하한** | **5 GB** | 507 | 디스크가 차면 백엔드·MySQL·CI 가 **한꺼번에** 죽는다. 로그를 못 받는 쪽이 싸다 |
| 보관 기간 | 14일 | — | 그보다 오래된 로그를 다시 꺼내 본 적이 없다 |

**200개·300 MB 에 닿으면 그것은 사람이 봐야 할 상황이다.** 그래서 그때 `log.warn` 을
남긴다 — 조용히 거절만 하면 누가 무엇을 하고 있는지 모른 채 로그만 안 모인다.

**알파 인원이 크게 늘면 이 표를 먼저 본다.** 6명 기준이므로, 동시 테스터가 수십 명이
되면 전역 개수부터 부딪힌다.

### 판정 순서 — 디스크 → 사용자별 → 전역

순서에 뜻이 있다.

- **디스크가 먼저다.** 여유가 없으면 누가 보냈든 받으면 안 된다. 못 재면 **받는 쪽**으로
  둔다 — 못 재는 것은 가득 찼다는 뜻이 아니다
- **사용자별이 전역보다 먼저다.** 전역 검사는 세면서 **소비한다.** 전역을 먼저 보면
  어차피 거절될 요청이 시간당 예산을 먼저 태워, 한 사람이 계속 보내는 것만으로
  **다른 사람 전부를 막을 수 있다.** 전역 상한이 막으려던 것과 정반대다

### 같은 초에 온 두 건

파일 이름이 **초 단위**라, 같은 사람이 같은 초에 두 건을 올리고 클라이언트 이름이 비면
이름이 겹친다. 예전에는 `REPLACE_EXISTING` 이라 **먼저 받은 로그가 조용히 사라졌다** —
사라지는 쪽이 보통 더 중요한 쪽(크래시)이다.

지금은 `base-2.log`, `base-3.log` 로 번호를 붙이고, 고른 뒤 실제로 옮기는 사이에 경합이
나면 **이름을 다시 골라 최대 3번 시도한다.** 덮어쓰기도, 500 도 답이 아니다.

## 2. 떠돌이 이미지 — `docker image prune` 을 쓰지 않는다

`-457` 은 `docker image prune -a` 를 막았다. **그것으로는 부족하다.**

`-a` 없이 `--filter until=12h` 를 걸어도 같은 사고가 난다 — `until` 이 보는 것은
이미지를 **만든 시각**이지 **태그를 잃은 시각**이 아니다. Unity 이미지(17.9 GB)는
몇 주 전에 받은 것이라, 새 에디터 버전을 받아 **방금** 태그를 잃어도 그 조건을 그냥
지나가 삭제된다. 지키려던 바로 그 대상이다.

그래서 떠돌이 이미지를 하나씩 보고 **둘 중 하나면 남긴다**:

| 조건 | 어떻게 보나 | 무엇을 지키나 |
|---|---|---|
| 레지스트리에서 받은 것 | `docker image inspect -f '{{len .RepoDigests}}'` 가 0 이 아니다 | 태그를 잃은 **Unity 이미지** |
| 만든 지 `DANGLING_HOURS`(기본 12시간) 가 안 된 것 | `{{.Created}}` | 도는 `docker build` 의 **중간 층** |

지우는 대상으로 남는 것은 **우리가 호스트에서 만든 옛 `metagame-backend`** 뿐이고,
그것이 원래 치우려던 것이다. 12시간으로 잡은 이유는 **배포가 잘못됐다는 걸 아는 데
시간이 걸리기 때문**이다 — 하루 일과 안에서는 직전 이미지로 되돌릴 수 있어야 한다.

받아 온 이미지는 지워도 다시 받으면 되지만, Unity 는 받는 데 7분이고 셰이더 캐시까지
얽히면 릴리스가 40분 길어진다(`-406` 실측). 남기는 쪽이 싸다.

## 3. 되돌리기 파이프라인은 Unity 빌드를 돌리지 않는다

`promote-builds` 되돌리기는 `PROMOTE_VERSION` 을 준 web 파이프라인이다. 그 파이프라인에서
`release-windows` 는 **돌지 않는다** — latest.json 한 줄을 되돌리자고 90분짜리 Unity
빌드를 기다릴 이유가 없고, 되돌리기는 급할 때 쓰는 길이라 그 시간이 곧 장애 시간이다.

리허설(변수 없이 Run pipeline)은 그대로 돈다. 둘을 가르는 것은 `$PROMOTE_VERSION` 하나다.

`PROMOTE_VERSION` 은 사람이 화면에 손으로 적는 값이고 그대로 경로가 되므로
`v?X.Y.Z` 형식만 받는다. 리허설이 쓰는 `v0.0.0-rehearsal` 도 여기서 걸린다 —
리허설 산출물은 올라간 적이 없으므로 사용자를 그리로 보내면 안 된다.

## 넣었다가 뺀 것

- **`tag_sha` 실패 시의 판정 변경.** 태그의 커밋을 못 읽으면 `points_here` 가 거짓이 되어
  정상 재시도까지 막힌다는 지적이 있었다. 다만 `all_tags()` 가 비면 `tag_taken` 이
  애초에 거짓이라 그 경로로는 안 막히고, 태그 목록에 있는데 `rev-list` 만 실패하는 경우는
  진짜로 사람이 봐야 한다. **판정은 그대로 두고 다음에 무엇을 하면 되는지만 적었다.**
