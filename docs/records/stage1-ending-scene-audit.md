# Stage1 엔딩 씬 전환 점검 및 F12 개발 테스트

점검일: 2026-09-13. 범위: `Lobby → Stage1_Astra → Stage1_Ending → Lobby`와 기존 입력·조립·씬 전환·Mirror 연결의 상호작용. 화면 직접 조작 없이 코드 및 격리 Unity 실행으로 검사했다.

## 발견한 문제와 보완

| 위험 | 영향 | 처리 |
| --- | --- | --- |
| 참가자가 연결된 채 엔딩 표시 준비에 실패 | 호스트와 다른 참가자가 준비 화면에서 무한 대기 | 45초 준비 제한, 실패 이유 표시, 로비 복귀 추가. 표시 구성 예외와 누락 프리팹도 처리 |

## 기존 기능과의 연결

- 엔딩 씬에 게임 세션과 물리 파츠를 유지하지 않는다. 성공 순간의 배치·회전·크기·용접·참가자 외형·시간을 복원한다. 엔딩 중 게임 플레이어 재생성과 월드 파츠 재생성은 기존 차단을 유지한다.
- F12는 실제 파츠 네 종류가 모두 있고 참가자 정보가 유효할 때만 진행한다. 파츠를 세워 연결한 후 기존 `TryComplete` 성공 판정, 스냅샷 생성, `EndingSceneFlow` 전환을 사용한다. 디버그 전용 엔딩 재생 경로는 만들지 않는다.
- “아니오”, Esc, F12 재입력은 파츠를 변경하지 않는다. “예” 이후에는 해당 판이 정상 완료되므로 되돌리지 않으며, 엔딩 후 로비로 돌아간다.
- 확인창이 열린 동안 로컬 입력만 막고 게임 시간·다른 참가자의 움직임은 멈추지 않는다. 이미 일시 메뉴/전환창이 열려 있으면 F12 창을 중첩하지 않는다.
- 플레이 타임은 기존 방 생성 기준을 유지하며 확인창을 연 시점이나 엔딩 씬 로드 시점에 다시 시작하지 않는다.

## 남는 제한 및 실제 환경 점검 항목

1. **엔딩 중 호스트 이전을 통한 재생 지속은 지원하지 않는다.** 기존 `HostMigration`은 게임 씬의 물리 월드를 이어받는 구조이고 엔딩 씬에 존재하지 않는다. 호스트 연결이 종료되면 엔딩을 이어가기보다 로비로 복귀한다. 연결 상실 감지 자체는 전송 계층의 타임아웃에 영향을 받는다.
2. **로컬 프로세스 검증은 실제 인터넷 릴레이·백엔드 인증 검증을 대체하지 않는다.** 실제 방에서 준비 중 강제 종료, 호스트 종료, 릴레이 지연/패킷 손실, 종료 후 재입장과 방 타이머 초기화를 확인해야 한다.
3. **동일한 씬·프리팹·프로토콜을 포함한 같은 버전으로 접속해야 한다.** 서로 다른 빌드는 별도 씬 또는 신규 메시지를 모를 수 있다. 현재 변경에 빌드 버전 협상 기능은 포함하지 않는다.
4. **늦은 참가자는 공통 시각의 현재 단계에 합류한다.** 이미 재생이 시작된 뒤 들어온 참가자 때문에 기존 참가자 전체가 엔딩을 처음부터 다시 보지는 않는다.
5. **시각 복원 범위는 스냅샷 필드와 등록된 파츠 프리팹이다.** 향후 임의 런타임 메시 교체나 새로운 외형 항목을 도입하면 해당 데이터의 스냅샷 확장이 필요하다.

## F12 사용법

1. Unity 에디터 Play Mode 또는 Development Build에서 `Stage1_Astra`에 들어간다.
2. 솔로 또는 멀티 호스트가 F12를 누른다.
3. “엔딩 씬으로 넘어가겠습니까?”에서 “예”를 누른다. 일반 참가자는 “예”가 비활성화된다.
4. 실제 파츠가 조립되고 전원이 엔딩 씬을 준비한 뒤 인사·탑승·발사·기념사진·종료 시간·로비 복귀를 진행한다.
5. 취소는 “아니오” 또는 Esc/F12. 일반 배포 빌드에는 단축키 등록과 강제 조립 구현이 포함되지 않는다.

실제 키 입력과 버튼 클릭은 사용자가 이 절차로 확인한다. 자동 검사는 같은 확인창 열기·취소·확정 메서드를 호출하며 화면을 직접 조작하지 않는다.

## 검증 결과

- Unity 6000.5.4f1 격리 프로젝트: 엔딩 판정·씬 교체·F12 확인/취소/권한·45초 준비 제한·90 KB 이상 UTF-8 분할 복원·잘못된 전송 순서·기존 네트워크 직렬화 등 **40개 통과, 실패 0개**. `tmp/demo-ending-validation/debug-final-tests.xml`.
- 검증용 Windows Development/일반 빌드 모두 성공. 일반 빌드의 생성된 어셈블리를 검사해 `EndingDebugShortcut`의 입력·확인 메서드와 `DemoEnding.DebugAssembleAndComplete`가 제외됨을 확인했다. 로그: `tmp/demo-ending-validation/debug-peer-build.log`, `debug-release-build.log`.
- 로컬 TCP 호스트 + 참가자 3개 프로세스: F12 확인창의 실제 확정 메서드로 성공 판정을 실행했다. 한 참가자는 엔딩 준비를 2초 지연하고 다른 참가자는 프로세스 실행 10초 뒤 합류했다. 공통 시작 시각 `3.8415890873015872`, 플레이 타임 3723초, 파츠 4개·참가자 4명이 일치했다. 후발 참가자는 경과 6.650초에 합류했고 전원 `LOBBY_OK`. `.local-validation/ending-peer/{host,client,slow,late}-debug-result.txt`.
- 위 다중 프로세스 테스트는 간소화한 게임 세션·실제 조립 함수·실제 엔딩 씬·실제 Mirror 전송을 사용했다. 실제 Astra 전체 게임 플레이, 키보드/버튼의 수동 사용감, 인터넷 릴레이와 호스트 이전을 통과했다고 해석하지 않는다.
- 로컬 프로세스 동시 실행에서 기존 실행 로그 파일 이름 충돌과 기존 월드 스폰 핸들러 교체 경고가 있었다. 별도 프로세스별 검증 로그는 정상 기록됐으며 엔딩 전송 실패는 없었다. 일반 다중 PC와 동일한 조건은 아니다.
