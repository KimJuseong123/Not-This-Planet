## 0. 결정

**릴레이를 우리가 돌린다.** 외부 릴레이 의존을 걷어낸다.

| | |
| --- | --- |
| 어디서 | EC2, 독립 프로세스(systemd), UDP **17778** |
| 세션 등록 | Spring이 `127.0.0.1:17779` 제어 API로 등록·삭제 |
| Unity 변경 | **없음** — `MatchTransport.UseRelay()`가 이미 주소·포트·토큰을 백엔드에서 받는다 |
| KCP | 그대로 Mirror가 양쪽 끝에서 한다. 릴레이는 내용을 모른다 |

## 1. 왜 되돌리는가

`-145` §2 의 **원래 결정이 EC2 릴레이였다.**

> **EC2 릴레이** | 호스트와 참가자 사이의 **패킷 중계**. P2P 직결을 쓰지 않는다 — NAT 통과 문제를 없애고 트래픽이 우리 서버를 지난다

그 자리에 Edgegap이 들어왔고(Mirror에 전송 계층이 들어 있어서), `-145`의 선택지 표에는 "계정·요금 확인" 으로만 남아 있었다. 팀에 확인한 결과 **특별한 이유는 없었다.**

그리고 `-298`에서 **Edgegap의 서버 검증이 우리 세션에서 동작하지 않고 우리가 고칠 수 없다**는 것을 확정했다 — 300초·260회 응답 내내 `Checking`, 30초 주기 재시도, 25세션 중 1회만 성공.

### `-145` 가 자체 릴레이를 물린 근거는 틀렸다

> **자체 릴레이** | UDP 포워더를 직접 작성 | 가장 통제 가능하지만 **우리가 netcode 를 또 만드는 셈**

**포워더는 netcode가 아니다.** 재전송·순서 보장·혼잡 제어(KCP)는 Mirror가 양쪽 끝에서 그대로 한다. 릴레이는 세션별로 "누가 서버인지" 만 기억하고 바이트를 옮긴다. 실제로 **250줄**이고 하루에 실측까지 끝났다.

같은 이유로 `-139`의 "방 하나 = 물리 세계 하나 → 100명이면 불가능" 비용 논리도 릴레이에는 적용되지 않는다. 물리를 돌리지 않으므로 남는 것은 대역폭뿐이다.

## 2. 와이어 형식

`EdgegapKcpServer.cs` · `EdgegapKcpClient.cs` (우리 저장소에 있다)에서 완전히 읽힌다. **모든 정수 리틀엔디언.**

```
클라이언트 → 릴레이   userId(u32) sessionId(u32) 0x01                      핑
                      userId      sessionId      0x02 payload…             데이터
릴레이 → 클라이언트   0x01 state(u8)
                      0x02 payload…

서버 → 릴레이         userId      sessionId      0x01                      핑
                      userId      sessionId      0x02 connId(i32) payload…
릴레이 → 서버         0x01 state(u8)
                      0x02 connId(i32) payload…

state: 0 Disconnected · 1 Checking · 2 Valid · 3 Invalid · 4 SessionTimeout · 5 Error
```

릴레이가 하는 일은 넷이다. 세션별 **서버 엔드포인트 기억** · 참가자에게 **connId 배정** · 참가자→서버 전달(**connId 삽입**) · 서버→해당 참가자 전달(**헤더 제거**).

## 3. 짜면서 알게 된 것

**포트 하나로 된다.** 프로토콜은 역할을 포트로 구분하지만, 토큰을 우리가 발급하므로 "이 토큰은 방장" 을 알 수 있다. `MatchTransport`에 서버·클라이언트 포트를 같은 값으로 주면 된다.

**핑이든 데이터든 첫 유효 패킷에 등록해야 한다.** 클라이언트는 `TickOutgoing()`의 `if (connected)` 때문에 **kcp 핸드셰이크가 끝난 뒤에야** 릴레이 핑을 보낸다. 즉 데이터가 먼저 올 수 있다. 핑만 기다리면 붙지 않는다.

**모르는 세션·토큰에는 `Invalid`로 분명히 답한다.** Edgegap은 이 경우 `Checking`을 돌려줬고, Mirror의 초기값이 `Checking` 이라 **"답이 없다" 와 구분되지 않았다.** 그것 때문에 원인을 여섯 번 헛짚었다(`-298` §1). 같은 함정을 만들지 않는다.

**양쪽 다 0.5초마다 핑한다**(킵얼라이브). idle timeout은 8초로 잡았다 — 잠깐의 유실로 끊지 않을 만큼 넉넉하고, 나간 사람을 오래 붙들지 않을 만큼 짧다.

## 4. 실측 (2026-09-04)

**포트 개방 권한이 우리에게 있다.** SSAFY 안내(`ufw 포트 설정하기.txt`)가 `sudo ufw allow 포트/udp`로 직접 추가하라고 명시한다 — 별도 보안그룹 확인이 필요 없다.

**외부 도달**: UDP 17778 을 열고 사용자 PC에서 **3/3 왕복 성공.** 공유기 NAT 통과와 복귀 경로 모두 확인.

**자체 시험**(`relay_selftest.py`, 로컬 14/14 통과) 그리고 **사용자 PC → EC2 실제 망 시험 10/10 통과**:

| 확인한 것 | 결과 |
| --- | --- |
| 서버가 붙기 전 참가자 핑 | `SessionTimeout` |
| 방장 핑 | **`Valid`** ← Edgegap이 끝내 못 넘긴 지점 |
| 서버가 붙은 뒤 참가자 핑 | `Valid` |
| 참가자 → 서버 전달 | payload 일치 · **connId 부착** |
| 참가자마다 connId | 서로 다름 (1 · 2) |
| 서버 → 지정 참가자 | payload 일치 |
| 다른 참가자에게 | **가지 않음** |
| 1024바이트 | 일치 |
| 모르는 세션 · 모르는 토큰 | `Invalid` |
| 닫은 세션 | `Invalid` |

## 5. 왜 Spring 안이 아니라 독립 프로세스인가

처음에는 Spring 안에 두려 했다(세션 상태가 이미 거기 있으므로). 짜 보고 바꿨다.

| | 독립 프로세스 (채택) | Spring 내장 |
| --- | --- | --- |
| 패킷 경로 | JVM·GC 없음 | GC 일시정지가 지연에 섞인다 |
| 재시작 | 릴레이만 따로 | 백엔드를 재시작해야 한다 = 게임 중 끊김 |
| 배포 | 백엔드 배포와 무관 | 배포마다 릴레이도 끊긴다 |
| Spring 쪽 변경 | HTTP 호출 대상만 교체(Edgegap → `127.0.0.1`) | 새 코드 |

**Spring 쪽 변경이 작다는 것이 결정적이다.** `EdgegapRelayService.open()`이 이미 "POST 하고 토큰을 받는" 모양이므로, 대상을 `127.0.0.1:17779`로 바꾸면 된다. 그리고 그때 `close()`를 부르게 하면 **세션 누수(`-298` §5-①)도 함께 없어진다.**

## 6. 남은 것

| 순서 | 무엇 | 상태 |
| --- | --- | --- |
| 1 | Spring 이관 — `RelayProvider` 인터페이스 · `LocalRelayService` · 방이 사라지면 `close()` | ✅ |
| 2 | systemd 유닛 설치 | ✅ 2026-09-04 (`active` · `enabled`) |
| 3 | **컨테이너에서 제어 API에 닿게** | ✅ `-303` — 아래 참조 |
| 4 | 다른 망 4인 플레이 실측 | 사람이 필요하다 |
| 5 | 지연 실측 (`-151`) — 직접 접속 대비 릴레이 왕복 | |

> **⚠ 2026-09-04 — 이 기록이 "끝났다" 고 말한 상태에서 backend → relay 경로는 한 번도
> 동작하지 않았다**(`-303`). 배포까지 성공했는데도 그랬다.
>
> 이유 둘. ① `.env` 에 `RELAY_PUBLIC_ADDRESS` 를 넣었지만 compose 의 `environment:` 가 변수를
> 하나씩 명시하는 구조라 **컨테이너에 전달되지 않았다**(`.env` 는 compose 파일 안 `${}` 치환에만
> 쓰인다). ② `LocalRelayService` 의 기본값 `http://127.0.0.1:17779` 에서 **컨테이너의
> `127.0.0.1` 은 컨테이너 자신**이고, 릴레이는 호스트에서 `127.0.0.1` 만 바인딩했다.
>
> **테스트가 왜 못 잡았나** — `LocalRelayServiceTest` 는 같은 JVM 안에 stub 을 띄우고
> `127.0.0.1` 로 불렀다. 필드 이름·타입·방장 표시는 잘 잡았지만 **컨테이너 경계를 넘지 않는다.**
> 통과하는 테스트가 "배포된 곳에서도 된다" 를 뜻하지 않는 전형이다.
>
> 그래서 `-303` 은 코드만 고치지 않고 **부팅 시 제어 API 에 한 번 물어보게** 했다
> (`LocalRelayService.probe()`). 같은 오설정이 이제 기동 로그 한 줄로 드러난다.

### Spring 쪽에서 한 것

`RelayProvider` 인터페이스를 두고 구현을 둘로 나눴다. `relay.provider` 속성이 고른다 —
`local`(기본) 또는 `edgegap`(되돌릴 길). 두 구현이 `@ConditionalOnProperty`로 배타적이라
빈이 겹치지 않는다.

**`RelaySession`이 `sessionId`를 들고 다닌다.** 이것이 없어서 `close()`를 부를 수 없었고
세션이 쌓였다(`-298` §5-①). 이제 `GameWebSocketHandler`가 `roomId → sessionId`를 기억하고,
`removeIfEmpty` 뒤에 방이 실제로 사라졌으면 릴레이에서도 지운다.

**릴레이에 세션 TTL 안전망을 넣었다.** 백엔드가 죽거나 배포로 재시작되면 아무도 `close()`를
부르지 않는다. 30분 동안 아무 왕래가 없는 세션은 릴레이가 스스로 지운다.

**공개 주소는 설정에서 받는다**(`relay.local.public-address`). 제어 API는 자기 포트만 알고
밖에서 어떤 이름으로 보이는지 모른다. 비어 있으면 릴레이를 쓰지 않고 직접 접속으로 간다 —
설정을 잊었을 때 조용히 깨지지 않게.

## 7. 부수 발견 — 백엔드 테스트가 CI 에서 돌지 않고, 플래키하다

`build-backend` 잡은 `./gradlew --no-daemon bootJar`만 돌린다. **테스트를 돌리지 않는다.**
즉 `RoomTest`·`AuthServiceTest`를 포함한 백엔드 테스트 58개가 **CI에서 한 번도 실행된 적이 없다.**

그래서 `./gradlew test`로 바꾸고 싶었는데, 돌려 보니 그럴 수 없다.

| 실행 | 실패한 테스트 |
| --- | --- |
| develop, 1회 | `disconnectDuringPlayKeepsSeatAndGameKeepsRunning` · `roomCodeIsHumanReadableAndJoinIsCaseInsensitive` |
| 이 브랜치, 1회 | `outsiderCannotJoinRoomThatIsAlreadyPlaying` · `rejoiningPlayerStillShowsNickname` |
| 이 브랜치, 2회 | `disconnectDuringPlayKeepsSeatAndGameKeepsRunning` · `rejoiningPlayerStillShowsNickname` · `rejoiningPlayerReceivesGameStateAndComesBackDowned` |

**매번 다른 테스트가 실패한다.** 전부 `GameWebSocketIntegrationTest` 이고 같은 줄(366)에서
떨어진다 — 시간·포트·공유 상태에 기댄 플래키다. 지금 CI에서 테스트를 켜면 **MR이 무작위로
실패 표시이 된다.**

순서가 있다. ① `GameWebSocketIntegrationTest`의 플래키를 고친다 → ② `build-backend`를
`./gradlew test bootJar`로 바꾸고 junit 리포트를 붙인다. 별 이슈로 뺀다.

## 8. 이 기록이 다루지 않는 것

- **부하 한계.** 4인 방 하나는 수십 KB/s 수준이지만 방이 여럿일 때를 재지 않았다. EC2는 CI·백엔드·게임 서버와 함께 쓰므로 `-284`(dev/prod 분리) · `-291`(CI 자원 가중치)와 같이 봐야 한다
- **호스트 이관·재접속**(`-150`) — 방장이 나가면 세션의 서버가 사라진다. 릴레이는 서버 등록을 해제하고 참가자에게 `SessionTimeout`을 돌려주므로, 이관 로직이 붙을 자리는 마련돼 있다
- **Edgegap 문의 결과.** 병행 중이다. 답이 와도 이 결정을 되돌릴 이유는 크지 않다 — 지연이 더 낮고(서울), 한도가 없고, 실패를 우리가 고칠 수 있다
