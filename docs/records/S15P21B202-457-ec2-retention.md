# EC2 에 무엇을 얼마나 남기나 (S15P21B202-457)

2026-09-11

서버 한 대가 CI 러너 · 백엔드 2벌 · MySQL 2벌 · 릴레이 · nginx 정적 배포를 다 맡는다. 쌓이는 것은 늘었는데 치우는 절차가 없었다.

**지금 급하지는 않다** — 디스크 309 GB 중 20% 사용, 여유 250 GB. 그래서 이 기록의 목적은 "지금 치우는 것" 이 아니라 **기준을 정해 두는 것**이다.

## 실측 (2026-09-11)

| 무엇 | 크기 | 회수 가능하다고 보고되는 양 |
| --- | ---: | --- |
| 디스크 전체 | 60 GB / 309 GB (20%) | 여유 250 GB |
| 도커 이미지 | **36.7 GB** | 32.5 GB (88%) ← **믿으면 안 된다** |
| 도커 볼륨 | 15.8 GB | 8.4 GB (52%) ← **믿으면 안 된다** |
| 도커 빌드 캐시 | 1.94 GB | 1.26 GB |
| **journald** | **780 MB** | 상한 미설정 |
| `/var/www/metagame-builds` | 320 MB | zip 164 MB + 런처 저장소 164 MB |
| `/var/www/metagame-site` | 96 MB | 트레일러 88 MB |
| 스풀 jar (prod) | 237 MB | `deploy.sh` 가 3개 보관 |
| `/opt/metagame` | 261 MB | 데디케이티드 서버 잔재 |

## 지우면 안 되는 것 — 그리고 왜 도커가 거짓말처럼 보이는가

`docker system df` 는 **36.7 GB 중 32.5 GB(88%)가 회수 가능**이라고 말한다. 그 말을 그대로 믿고 `docker image prune -a` 를 돌리면:

| 사라지는 것 | 크기 | 대가 |
| --- | ---: | --- |
| `unityci/editor:…-windows-mono` | 17.9 GB | 다시 받는 데 **7분** (2026-09-11 실측) |
| `unityci/editor:…-base` | 15.1 GB | 같이 |

도커가 "놀고 있다" 고 보는 이유는 **그 이미지가 CI 잡이 도는 동안에만 쓰이기** 때문이다. 잡이 없는 순간에 재면 늘 놀고 있다.

러너 볼륨도 같다. `-cache-…-protected` 안에 Unity 의 `Library` 와 **셰이더 캐시**가 있다. 지우면 다음 릴리스 빌드가 **40분 더** 걸린다(`-406` 실측: v1.0.0 의 46.6분 빌드 중 43.0분이 셰이더 컴파일이었고, `Local cache hits 0` × 533 이었다).

**지우는 순간은 공짜고, 대가는 다음 릴리스에 온다.** 그때는 이미 지운 뒤다.

그래서 `ec2-cleanup.sh` 는 다음을 **절대 쓰지 않는다**. `scripts/ci/tests/test_ec2_cleanup.py` 가 그것을 글자로 잠근다.

```
docker image prune -a     docker system prune     docker volume prune     docker rmi
```

## 치우는 것과 주기

`metagame-cleanup.timer` — **매주 일요일 03:00**. 릴리스·배포·CI 가 가장 한가한 시간이다. 빌드 캐시를 지우면 다음 빌드가 조금 느려지므로 아무도 기다리지 않을 때 한다.

| 무엇 | 기준 | 왜 이 기준인가 |
| --- | --- | --- |
| 도커 빌드 캐시 | 7일 넘은 것 | 다시 만들어진다. 잃는 것이 없다 |
| 떠돌이(dangling) 이미지 | 전부 | 백엔드를 새로 빌드할 때마다 옛 `metagame-backend:latest` 가 태그를 잃고 남는다 |
| 끝난 컨테이너 | 24시간 넘은 것 | 러너가 잡마다 만들고 버린다 |
| 릴리스 zip | **최신 3개** | 164 MB 짜리다. 런처 저장소(`files/`·`manifest/`)는 `make_manifest.py --keep 10` 이 회수하지만 **zip 은 그 대상이 아니라** 아무도 치우지 않았다 |
| journald | **상한 500 MB** | 아래 |
| 배포 jar | `deploy.sh` 의 `KEEP=3` 그대로 | 환경이 둘이니 실제로 6개. 되돌릴 여지로 적절하다 |
| nginx 로그 | 지금의 logrotate 그대로 | 이미 걸려 있고 크기도 작다(access.log 100 KB) |

### journald 상한이 이 기록에서 가장 실질적인 항목이다

2026-09-11 실측: 저널이 **780 MB** 인데 `SystemMaxUse` 가 설정돼 있지 않다. 기본값은 **파일 시스템의 10%** 라, 309 GB 디스크에서는 **30 GB 까지 자란다.**

지금은 여유가 많아 보이지 않지만, 디스크가 차기 시작하면 저널이 그 속도를 두 배로 만든다. 줄 하나로 끝나는 일이라 설치 스크립트가 건다.

## 결정 — 정지된 게임 서버 유닛은 **남긴다**

`metagame.service`(데디케이티드 서버)는 `inactive · disabled` 이고 `/opt/metagame` 에 **261 MB** 가 남아 있다. 리슨 서버로 전환했으므로 쓰지 않는다.

**지우지 않는다.** 이유:

- **261 MB 는 지금 문제가 아니다.** 여유가 250 GB 다. 이것을 지우는 것은 "치웠다" 는 느낌만 주고 아무것도 바꾸지 않는다
- **되돌릴 수 없다.** 되살리려면 Unity 로 데디케이티드 빌드를 다시 내야 한다
- **살아나는 것이 진짜 위험이고, 그쪽은 이미 막았다.** 아침 점검이 `metagame.service` 가 `active` 가 되면 알린다(`-458`) — "꺼져 있어야 하는 것" 으로 넣어 뒀다

**언제 지우나:** 디스크가 80% 에 닿아 아침 카드가 울리면, **가장 먼저 지울 것이 이것이다.** 그때 이 문단을 근거로 지우면 된다.

## 정리와 알림은 짝이다

- 이 기록(`-457`)이 **치운다**
- [`-458`](./S15P21B202-458-ec2-health.md)이 **차는 것을 알려 준다** — 아침 점검이 디스크 80%·메모리 2 GB·인증서 30일을 보고, 넘으면 숫자와 함께 말한다

한쪽만 있으면 안 된다. 치우기만 하면 기준을 넘는 순간을 모르고, 알리기만 하면 사람이 매번 손으로 치운다.

## 설치

```
sudo bash scripts/deploy/host/install-cleanup.sh
```

무엇을 지울지만 보려면:

```
sudo DRY_RUN=1 /opt/metagame-deploy/ec2-cleanup.sh
```
