# 작업 기록 (records)

[문서 안내](../README.md) → **작업 기록**

기능 구현의 결정 근거, 실측·조사 결과, 사고 대응, 회의 결정과 외부 도구(Figma·Notion 등)의 결과를 보관합니다. 현재 작업 절차는 [문서 안내](../README.md)의 개발·운영 문서를 먼저 확인하고, 배경이나 재현 근거가 필요할 때 해당 기록을 읽습니다.

## 파일 이름 규칙

```
<이슈키>-<slug>.md      예) S15P21B202-34-e2e-test.md
```

- **이슈키가 앞에 옵니다** — 어느 이슈에서 나온 기록인지 파일 목록만 보고 알 수 있어야 합니다.
- `slug`는 영문 소문자와 하이픈. 짧게(2~4 단어).
- 한 이슈에서 기록이 여럿이면 slug로 구분합니다: `-34-e2e-test.md`, `-34-e2e-followup.md`.

## 무엇을 적나

[templates/work-record.md](../templates/work-record.md) 틀을 씁니다. 핵심은 세 가지입니다.

1. **무엇을 했는지** — 다음 사람이 같은 일을 반복하지 않을 만큼
2. **무엇을 정했는지** — 결정과 그 이유. 나중에 "왜 이렇게 했지?" 의 답이 여기 있어야 합니다
3. **실측값** — 추측과 구분되게. 언제·어디서 측정했는지 함께

## 여기에 넣지 않는 것

- 팀 전체가 지키는 **규칙**은 `docs/*.md`로 (여기는 "그때 그 일" 의 기록입니다)
- 단순 코드 변경 목록은 MR 본문과 커밋 메시지에 적습니다. 기록에는 설계 이유, 재현·측정 결과, 다른 작업에서 참고할 제약을 남깁니다.
- 테스트하며 만든 임시 파일 — 검증이 끝나면 지웁니다

## 주제별 읽기 순서

기록은 이슈 번호순으로 연결했습니다. 같은 기능의 앞선 기록에서 “미구현”으로 남긴 항목이 후속 기록에서 해결될 수 있습니다. 날짜·실측 환경·후속 링크를 함께 확인합니다.

| 주제 | 먼저 읽을 흐름 |
| --- | --- |
| 조립·용접·발사 | 붕괴·하중 시험 → 탑승·상승 → 비드 생성·접합·그래프 → 실패 경계·연출 |
| 네트워크 | 동기화 설계 → 상호작용 규칙 → 릴레이 진단·구현 → 2인 측정·지연·오브젝트 복제 |
| 서버·배포 | EC2 초기 설정 → CD 전략 → 배포 격리·환경 분리 → CI 라이선스·릴리스 |
