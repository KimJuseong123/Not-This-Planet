# 하차·저중력장 사양 및 부양 튜닝 검토

검토 기준: `a5153fa`, 2026-09-10. 화면 직접 조작 없이 코드·이력과 별도 Unity Play Mode로 확인했다.

## 1. 확정 사항

- 사용자 확인: **팀 합의 완료 — 하차 후 착륙 유지**.
- 하차 시 저중력장 종료와 즉시 플레이어 조작 복귀를 유지한다. 빈 기체는 중력으로 내려가 실제 지면·구조물에 착륙한다.
- 기획 §14.2에 합의 내용을 반영했다. §14.5 협동은 조종사가 탑승한 채 용접자를 지원하고, 용접자가 Ctrl로 지지면까지 내려온 뒤 조종사가 하차하는 순서로 명시했다.
- 이 순서는 2인 이상 기준이다. 무인 필드로 역할을 교대하거나 혼자 공중 용접하는 대안은 확정되지 않았다. 솔로 지원이 필요하면 별도 설계가 필요하다.
- `CraftHoverTests.cs`는 현재 삭제되어 있지 않다. 이력상 `4ca8429`에서 무인 호버·필드 유지 기대를 착륙·필드 종료·재탑승 기대로 변경했고 `a5153fa`에서도 수정됐다. 예전 기대를 복원하면 이번 팀 합의와 충돌한다.

## 2. 필드 누락·파괴 재현

별도 임시 프로젝트 `METAGAME/Temp/CraftPhysicsProject`에서 현재 컴파일된 런타임 DLL을 사용했다. Unity 6000.5.4f1을 batchmode/nographics로 실행하고 `Application.isPlaying=True`를 확인했다. 실제 `TryBoard` 후 파괴는 프레임을 넘겨 반영했다. 기체 파괴 후 입력 경로 확인을 위해 컨트롤러의 탑승 참조는 테스트에서 주입했다. 원본 씬의 수동 플레이나 VFX 렌더링 검증은 아니다.

| 조건 | 실행 경로 | 관측 결과 |
|---|---|---|
| 필드 컴포넌트가 없는 기체 | 탑승 → BeginDismount | 정상 하차, 필드 재생성, 동기 예외 0 |
| 활성 필드 컴포넌트를 Destroy한 기체 | 탑승 → 필드 파괴 완료 → BeginDismount | 정상 하차, 필드 재생성, 동기 예외 0 |
| 탑승 중 기체 GameObject 전체 Destroy | 파괴 완료 → TransportAction 입력 | 입력 예외 없음, 탑승 참조 해제, **Doll.Visible=False** |

`TransportVehicle.Field`는 null이면 GetComponent/AddComponent로 필드를 생성하는 프로퍼티다. 따라서 살아 있는 기체에서 `Field.SetActive(false)`는 위 두 조건의 NullReferenceException 원인이 아니었다. 기존 `if (Field != null)`도 프로퍼티를 호출하므로 같은 재생성이 일어난다. **NRE 방지를 위한 기존 null 검사 복원은 필요하지 않다는 판단**이다. 종료 시 불필요한 컴포넌트 생성을 없애려면 생성하지 않는 조회 경로를 별도로 설계해야 한다.

기체 전체가 삭제된 경우 컨트롤러의 Unity 객체 null 검사가 하차 호출을 우회한다. `TransportVehicle.OnDestroy`에는 탑승자 해제·가시성 복원 처리가 없으며, 실제로 숨김이 남았다. 이 문제는 Field null 검사로 해결되지 않는다.

검증 로그: `METAGAME/Temp/CraftPhysicsProject/play-review-results.txt`, `METAGAME/Temp/CraftValidation/play-review-unity.log`. 세 시나리오에서 NullReferenceException은 관측되지 않았다. 단, UnityEditor.Search.SearchDatabase 초기 색인에서 별도의 ArgumentOutOfRangeException 1건이 기록되어 실행 전체를 예외 0건 또는 전체 통과로 판정하지 않는다. 임시 프로젝트 로그는 Git 추적 대상이 아니다.

## 3. 분리 이슈 초안: 플레이어 부양 튜닝

상태: VFX 렌더링 수정과 분리해 검토할 로컬 초안. 최초 요청의 “사람도 들리게”에 대응한 변경이지만, VFX 가시성 수정에 필수인 값은 아니다. 이번 검토에서는 런타임 수치를 되돌리거나 튜닝 합의를 임의로 확정하지 않았다.

| 항목 | 기존 → 현재 | 영향 |
|---|---|---|
| FieldFloatVerticalSpeed | 2 → 3m/s | 수동 상승·하강과 자동 부양 최고 속도 50% 증가 |
| FieldFloatStopSeconds | 0.5 → 0.25초 | 수직 속도 변화율 4 → 12m/s² |
| 동일 시간 상수의 수평 공유 | 수평 최고 속도는 3m/s 유지 | 수평 가속·감속 모두 6 → 12m/s²로 두 배 |
| PlayerRig 자동 부양 | 진입 시 목표 높이 +1.5m | 필드 원점 아래 1.2m로 상한 제한. Space/Ctrl 입력으로 자동 부양 해제 |

코드 근거: `PhysicsScale.cs`의 두 상수, `PlayerRig.UpdateFloating` 및 `DriveMovementVelocity`. 파츠를 끄는 물리는 해당 속도 상수를 직접 사용하지 않지만, 플레이어의 위치·충돌·용접 접근·매달리기 전환·필드 해제 후 낙하에는 영향이 있을 수 있다. “다른 시스템 영향 없음”으로 결론 내릴 수 없다.

추가 불일치: 기획 §14.3과 `Stage1QaAudit.cs`는 아직 상승·하강 2m/s를 기준으로 한다. 코드 주석에도 0.5초 정지 설명이 남아 있다.

완료 조건:

1. 자동으로 사람을 띄우는 목표와 수동 이동 속도 변경을 각각 평가한다. 수평 감속까지 바꾸는 의도가 없다면 수평·수직 시간 상수를 분리한다.
2. 지상 진입, 필드 상단 진입, Ctrl 하강, 필드 재진입, 매달리기, 용접 접근, 필드 종료 후 중력 복귀와 잔여 상승 관성을 검증한다.
3. 2인 협동과 네트워크 권한별 부양 결과를 확인한다. 현재 검토에서는 다중 클라이언트 검증을 수행하지 않았다.
4. 승인한 값으로 기획 §14.3, QA 검사 및 주석을 함께 맞춘다. VFX 가시성 검증은 별도로 진행한다.

## 4. 분리 이슈 초안: 탑승 기체 파괴 시 플레이어 숨김 잔존

상태: 재현 확인, 미수정. 정상 충돌로 기체가 파괴되지 않는 기획과 별개로 오브젝트 제거·씬 정리 경로의 생명주기 결함이다.

재현: 기체 탑승 → 기체 GameObject 삭제 → 프레임 경과 → 탑승/하차 입력. 컨트롤러 탑승 참조는 해제되지만 플레이어 가시성이 복구되지 않는다.

수정 방향: 기체 삭제 시 살아 있는 탑승자의 상태와 가시성을 복구하고 컨트롤러 참조 정리를 보장한다. 플레이어와 기체가 함께 삭제되는 씬 종료에서도 안전해야 한다.

완료 조건: 기체만 삭제, 필드만 삭제, 플레이어 선삭제, 씬 종료의 순서를 검증하고 생존 플레이어가 보이며 이동 가능한지 확인한다. `OnDestroy` 정리는 필드를 새로 만들지 않아야 한다.

위 초안은 저장소 내부 기록이며 외부 이슈 트래커에 등록하거나 팀에 메시지를 발송하지 않았다.
