## 목적

`-139` 는 **배포 대상이 한 벌**이라고 가정하고 쓴 문서다. 2026-09-04 팀 결정으로 그 가정이 바뀌었다.

> EC2 한 대로 **개발과 실유저 배포를 둘 다** 한다.
> `develop` = 개발 과정, `master` = 마일스톤 기반 배포판.
> 팀장이 `develop → master` 를 머지하는 시점이 릴리스이고, 거기서 CD 가 돈다.
> (2026-09-07 정정: 릴리스는 develop 에서 딴 `release/<키>-vX.Y.Z` 브랜치를 master 에 머지하는 것으로 바뀌었다 — git-convention §8, -325.
> "분리 뒤 master 머지 = prod 자동 배포" 는 그대로다.)

이 문서는 그 구조를 적고, 지금 서버가 실제로 어떤 상태인지 실측을 남긴다.

## 0. 결정

| | |
| --- | --- |
| 환경 | **한 대에 두 벌.** prod(`master`) · dev(`develop`) |
| 가르는 것 | compose 프로젝트 · 포트 · **MySQL 볼륨** |
| 배포 방아쇠 | prod = `master` push 후 **수동** · dev = `develop` push |
| 신뢰 경계 | **보호 브랜치 + Protected 러너.** 팀장이 머지한 것만 스풀에 닿는다 |
| 무중단 | 하지 않는다. prod 재시작은 세션을 끊으므로 공지하고 누른다 |

## 1. 자원은 제약이 아니다 (2026-09-04 실측)

| 항목 | 지금 쓰는 양 | 총량 |
| --- | --- | --- |
| RAM | `metagame-backend` 391MB + `metagame-mysql` 374MB = **0.8GB** | 15GiB (여유 13GiB) |
| 디스크 | 28G (도커 이미지 19.2GB, 회수 가능 15.8GB) | 309G (여유 282G) |
| CPU | 0.11% / 0.78% | 4 vCPU |

두 벌을 띄워도 1.6GB다. **한 대로 못 한다는 근거는 자원 쪽에는 없다.**

라우팅 장치도 이미 있다. nginx 가 80/443 을 잡고 `127.0.0.1:8080` 으로 넘긴다. 백엔드는 외부에 직접 열려 있지 않다.

```
0.0.0.0:443   nginx  (Let's Encrypt, j15b202.p.ssafy.io)
0.0.0.0:80    nginx  → 443 리다이렉트
127.0.0.1:8080  docker-proxy → metagame-backend
*:17777/udp   Unity Main Thread (게임 서버)
```

## 2. 배포 대상은 하나가 아니라 둘이다

지금까지 CD 논의는 백엔드만 다뤘다. 실제로는 둘이 돈다.

| | 백엔드 | 게임 서버 |
| --- | --- | --- |
| 무엇 | Spring, 도커 | Mirror, **호스트 systemd** |
| 어디 | `127.0.0.1:8080` (nginx 뒤) | `*:17777/udp` |
| 실행 단위 | `~/metagame/docker-compose.yml` | `metagame.service` → `/opt/metagame/MetaGameServer.x86_64` |
| CD | **있다** (스풀, `-141`) | **없다. 손으로 올린다** |

게임 서버 유닛은 이렇게 백엔드에 묶여 있다.

```
ExecStart=/usr/bin/xvfb-run -a /opt/metagame/MetaGameServer.x86_64 \
  -batchmode -server -port=17777 \
  -verifyUrl=https://j15b202.p.ssafy.io/auth/verify
```

**환경을 나누면 `-port` 와 `-verifyUrl` 도 함께 갈라야 한다.** dev 게임 서버가 prod 백엔드에 인증을 물으면, 개발 중인 클라이언트가 실유저 DB 를 상대로 토큰을 검증받게 된다.

## 4. 정해야 할 것 — 포트는 우리가 연다

> **2026-09-04 정정 (`-301`).** 아래 1·2번을 "SSAFY 보안그룹이 열어 줘야 한다 · 우리가 못 정한다"
> 고 적었는데 **틀렸다. 포트는 우리가 직접 연다.**
>
> - SSAFY 안내(`ufw 포트 설정하기.txt`)가 **`sudo ufw allow 포트/udp` 로 추가하라**고 명시한다.
>   별도 보안그룹 단계가 없다
> - 같은 날 `-299` 에서 **UDP 17778 을 열고 사용자 PC 에서 3/3 왕복**을 확인했다.
>   지금 릴레이가 그 포트로 돌고 있다
>
> 그러므로 1·2번은 **막힌 것이 아니라 그냥 하면 되는 일**이다. 남는 선택은 "포트를 새로 열까,
> nginx 경로로 갈까" 라는 설계 취향뿐이다.

| # | 무엇 | 남은 선택 |
| --- | --- | --- |
| 1 | **dev 백엔드를 밖에 어떻게 내보내나** | 새 포트(예: 8443/tcp)를 우리가 열고 nginx 에 `listen 8443 ssl` 을 더하는 쪽이 단순하다. nginx 경로(`/dev/`)는 포트를 안 늘리지만 앱이 절대 URL 을 만들면 깨진다 |
| 2 | **dev 게임 서버를 띄우나** | UDP 17779… 아니라 **다른 포트**를 열면 된다(17779 는 릴레이 제어 API 가 쓴다 — `127.0.0.1` 전용이지만 헷갈리지 않게 피한다). 안 띄우고 로컬 리슨 서버로만 검증하는 것도 여전히 유효하다 — `-239` 의 호스트 권위 구조라 대부분 그렇게 된다 |
| 3 | **CI 자원 제한** | `-291` 에서 `cpu_shares = 256` 로 처리했다 |

**막고 있는 것이 없다.** 순서만 지키면 된다(§6).

## 5. 같은 기계에서 CI 가 돈다 — `-291` 에서 처리했다

이건 환경 분리와 별개로 지금도 참인 문제였다. **2026-09-04 에 공용 러너에 `cpu_shares = 256`
을 걸었다**(`-291`) — 하드 상한이 아니라 상대 가중치라서, 놀고 있으면 CI 가 기계를 다 쓰고
게임 서버가 일하기 시작하면 양보한다. 아래는 그때의 기록이다.

러너 `config.toml` 에 **자원 제한이 하나도 없었다.** `concurrent = 2` 뿐이었다. `unity-compile` 은 4 vCPU 를 **7분 30초 동안 전부** 쓴다(콜드 기준, `-271` 실측). 실유저가 붙어 있는 동안 그게 돌면 릴레이·매칭 응답이 그만큼 밀린다.

`[runners.docker]` 에 `cpus = "2.5"` 같은 제한을 걸면 된다. 되돌리기도 쉽다. 다만 러너 재시작이 필요하므로 잡이 없는 시간에 한다.

## 6. 왜 `develop` 배포를 없애지 않는가

"실유저 서버니까 `master` 에서만 배포해야 하지 않나" 라는 질문이 먼저 나왔다. 그 방향으로 가지 않는 이유는 셋이다.

1. **백엔드가 마일스톤에만 갱신되면** 클라이언트 작업자들이 한 스프린트 내내 낡은 서버에 붙어 개발한다. 통합 환경을 두는 목적과 정반대다
2. `master` 는 **초기 커밋에 멈춰 있다**(`ed8ad6d`, 08-25). develop 이 382 커밋 앞이고 master 로 간 MR 이 **0건**이다. 지금 `master` 기준으로 배포하면 백엔드가 사라진다
3. 컨벤션의 `master` 규칙([git-convention.md](../git-convention.md) 25–30행)은 **Unity 빌드 이야기**다. 근거로 든 것이 씬·프리팹 오염과 에셋이 얽힌 revert 위험이다. jar 하나는 성질이 다르다

대신 그 질문이 짚은 진짜 문제를 이 문서가 다룬다. **환경이 하나뿐이라 테스트 서버와 시연 서버가 같다는 것.**

## 7. 이 결정이 다루지 않는 것

- **무중단 배포.** prod 재시작은 세션을 끊는다. 필요해지면 별 이슈
- **첫 릴리스.** `develop → master` MR 과 `v0.1.0` 태그가 아직 없다. 컨벤션 19행이 정해 둔 절차인데 한 번도 실행되지 않았다
- **시크릿·운영 값.** `-142` 가 맡는다. 이 문서는 환경을 가르기만 하고, 어떤 값이 어디 있는지는 거기서 정한다
- **게임 서버 CD.** 지금은 손으로 올린다. 이 문서는 "환경별로 갈라야 한다"까지만 정하고, 자동화는 별 이슈

## 남은 것 / 후속

| 순서 | 무엇 | 상태 |
| --- | --- | --- |
| 1 | `-252` 러너 분리 | ✅ 2026-09-04 (4단계까지 실측 완료) |
| 2 | compose 두 벌 + MySQL 볼륨 분리 | 막는 것 없음 |
| 3 | dev 노출 경로 (포트 또는 nginx 경로) | 막는 것 없음 — **우리가 연다**(위 정정) |
| 4 | `deploy-prod` / `deploy-dev` 잡 분리 | 2·3번 뒤 |
| 5 | 게임 서버 환경 분리 | 3번 뒤 |
| 6 | 첫 릴리스 MR + `v0.1.0` | 팀 일정 |

**1번은 끝났다.** 이제 2번부터 순서대로 하면 되고, 바깥에서 답을 기다릴 것은 없다.

> `deploy-dev` 를 **자동**으로 둘지도 함께 정한다. `backend/` 를 건드린 머지는 7일에 7건뿐이라
> 자동으로 해도 재시작이 하루 1~2회다(`-289` 실측). `deploy-prod` 는 수동을 유지한다 —
> 릴리스 시점은 판단이고, 그 판단은 `develop → master` 머지에 이미 있다.
