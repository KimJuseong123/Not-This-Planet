# 718 운석 성능·회귀 검토

후속 구현과 최종 테스트 결과는 [동기화 최적화 기록](2026-09-23-718-meteor-sync-optimization.md)을 참고한다. 아래는 수정 전 조사 기록이다.

2026-09-23. 기준 커밋 `af143761`, 브랜치 `S15P21B202-718-physics-fps-72-41`.
워크트리: 저장소 루트의 `.worktrees/718`. 화면 조작 없이 소스·씬 직렬화·기존 테스트를 검토했다.
이번 변경은 이 검토 문서뿐이다. 실제 FPS/CPU/GPU 프로파일이나 다인 플레이를 실행하지 않았으므로 성능 원인은 확정하지 않는다.

## 결론

현재는 스포너 8개가 아니라 MeteorSpawner 하나와 float 타이머 8개다. A/B/C/D 시간표는 연출과 생성 분산에는 사용할 수 있지만, 동일한 개수의 운석을 만들면 물리·렌더링·착탄·복제 비용은 남는다. 먼저 생성 집중 방지의 실제 프레임 단위 적용, 원격 흔적 처리 오류, 착탄 목록 전체 복제를 조사하는 편이 낫다.

## 공세 후 부하가 유지되는 이유

- `MeteorSpawner.ActiveDropClocks`는 탐색 1개, 공세 8개다. 각 시계는 1~5초이므로 평균 발생률은 약 0.33개/초 → 2.67개/초다. 긴 프레임과 동시 생존 상한에 따라 실제 빈도는 낮아질 수 있다.
- `Stage1Sequence.Tick`은 8초짜리 공세 연출 뒤 Combat으로 이동하지만 AssaultEnabled를 끄지 않는다. 따라서 **컷신이 끝나도 높은 낙하 빈도는 계속된다**. 이는 정리가 안 된 일회성 공세와 구분해야 한다.
- Stage1_Astra의 `_scarDespawnSeconds`는 실제로 13초, `_scarLimit`는 200이다. 모두 정상 착탄한다고 가정하면 평균 착탄 잔존량은 약 4개 → 35개다. 낙하 중 운석은 별도이며 독립 모드 상한은 16개다. 35는 측정값이 아닌 발생률×수명의 근사치다.
- `Meteor.Settle`은 착탄 운석의 Rigidbody를 동적으로 유지하고 Grabbable을 붙인다. 따라서 흔적은 단순 그림이 아니라 집기·밀기·방망이 대상이다. 무조건 Collider를 끄거나 kinematic으로 바꾸면 기존 기능을 깨뜨린다.
- `AdvanceScars`에서 나이가 증가하고 13초 후 Despawn하므로, 코드상 정상 경로에서 흔적이 영구 누적되는 구조는 아니다. 멈춘 뒤에도 계속 악화된다면 실제 오브젝트 수와 렌더러/메모리 측정이 필요하다.

## 발견한 문제와 위험

### P1: 원격 흔적의 비활성 스크립트가 충돌 판정을 차단하지 못함

`MeteorSpawner.CreateGhost(solid: true)`는 콜라이더를 유지하고 `ghost.enabled = false`만으로 판정을 막는다고 설명한다. 하지만 `Meteor.OnCollisionEnter`에는 enabled/원격 표시 전용 상태 검사가 없고, 원격 흔적은 HasImpacted/Rolling/GroundProp도 설정하지 않는다. 따라서 동적 플레이어와 접촉할 때 로컬 넉백·기절 판정 경로로 들어갈 위험이 있다. 실제 다인 접촉 재현은 미실시다.

Unity는 disabled MonoBehaviour에도 충돌 이벤트를 전달한다:
https://docs.unity3d.com/ja/6000.0/ScriptReference/Collider.OnCollisionEnter.html

권장: 표시 전용 상태를 명시하고 충돌/게임플레이 진입점에서 차단한다. 물리적으로 몸을 막는 콜라이더는 유지한다. 컴포넌트 비활성만 신뢰하지 않는다.

### P2: 프레임당 생성 제한이 실제로는 Tick당 제한

`MeteorSpawner.AdvanceSchedule`은 매 호출마다 `launched = 0`을 설정하고 최대 2개를 생성한다. `MeteorClockBridge.FixedUpdate`에서 Tick하므로 한 렌더 프레임에 여러 물리 스텝이 실행되면 최대 2개 제한을 반복해서 사용할 수 있다. 예를 들어 밀린 8개 레인은 4번의 물리 스텝에서 모두 생성될 수 있다. 기존 AssaultFrameCostTests의 단일 Tick 검증만으로는 이를 잡지 못한다.

권장: 실제 렌더 프레임에 공유되는 생성 예산을 두고 시간 진행과 생성 실행을 분리한다. 순수 시간 시뮬레이션 테스트가 프레임 카운터에 묶이지 않도록 프레임 식별자/예산을 주입하는 방식이 적합하다. 일시정지·컷신·상한 도달·리셋 시 밀린 생성 정책을 보존한다.

### P2: 원격 착탄 흔적에 낙하 꼬리 종료가 없음

`Meteor.Initialize`가 TrailRenderer를 생성하고 `Meteor.Settle`이 StopTrail을 호출한다. 원격 흔적은 새 프리팹으로 생성되지만 Settle을 거치지 않으며 CreateGhost의 solid 경로에도 꼬리 종료가 없다. 정지 상태의 실제 GPU 비용은 측정해야 하지만, 움직이는 착탄 돌에 낙하 꼬리가 계속 생길 수 있는 경로다.

권장: 원격 착탄 표시로 전환할 때 꼬리 방출을 중단하고 기존 점을 정리한다. 낙하 고스트의 풀 재사용 시에는 기존 RestartTrail 동작을 유지한다.

### P2: 잦은 전체 흔적 복제와 보간 초기화

`WorldSync.SendScars`는 ID 목록이 바뀔 때마다 전체 흔적 목록을 신뢰 채널로 보내고, 같은 송신 틱의 움직임 패킷은 생략한다. 변화가 없어도 2초 keepalive를 보낸다. 착탄/소멸이 잦은 공세에서는 전체 목록 전송도 잦아지고, 길이가 바뀌면 송신 배열도 재할당된다.

`ApplyNetworkScars(full: true)`는 모든 흔적의 위치/회전을 다시 쓰고 SetScarAtRest로 추정 속도를 0으로 만든다. 움직이는 돌도 포함되어 클라이언트에서 끊겨 보일 후보다. 이는 GPU 병목과 다른 네트워크 보간 문제다.

권장: 생성/삭제 이벤트와 이동 상태를 분리하고, 전체 목록은 재접속·복구용으로 유지한다. 초기 버전은 패킷 형식 변경 없이 불필요한 동일 자세 쓰기를 줄이는 실험부터 한다. 목록만 보고 계속 움직이는 돌을 정지로 처리하는 정책도 별도 검토한다.

## 멀티에서 렌더링이 큰가?

호스트는 권위 물리와 상태 송신을 수행하고, 참가자는 낙하 고스트와 착탄 고스트를 그린다. 화면 렌더링은 각 기기에서 수행하므로 참가자가 늘었다고 호스트가 참가자 화면까지 렌더링하는 것은 아니다. 호스트의 송신량은 수신 인원에 영향을 받는다.

낙하 고스트 풀링은 이미 있지만 권위 운석과 원격 착탄 흔적은 여전히 생성/파괴한다. 경고 표시·낙하 꼬리·잔존 운석이 늘면 렌더링 후보 부하도 증가한다. 그러나 실제 GPU 시간, 드로우콜, 화면 점유율을 측정하지 않았으므로 “운석 렌더링이 주원인”이라고 결론낼 수 없다.

## A/B/C/D 세트 방식 평가

- 시간표를 골라도 동일한 양의 Instantiate/착탄 물리/표시/상태 전송은 발생한다. float 8개 비교를 제거하는 것만으로 큰 개선을 기대할 근거는 없다.
- 생성 시점을 고르게 분산하는 시간표는 스파이크 완화에 도움이 될 수 있다. 다만 랜덤 편차를 줄이는 만큼 플레이 난이도/리듬이 바뀐다.
- 세트 ID만 송신하고 각 클라이언트가 물리를 재현하는 방식은 현재 방망이 반사, 플레이어 주변 조준, 움직이는 파츠/운반체 충돌, 중도 참가, 호스트 인계와 충돌한다. 호스트 확정 위치와 실제 착탄/반사 결과를 여전히 전달해야 한다.
- 권장 순서: 위의 명확한 처리 문제 → 프로파일링 → 권위/착탄 오브젝트 풀링 또는 상태 전송 축소. 시각 경량화는 GPU 병목이 확인될 때 시행한다.

## 실행한 검증과 남은 검증

실제 `MeteorDropSchedule.cs`를 .NET에서 컴파일해 엔진 없이 실행했다.

- seed 661, 0.01초 간격, 300초: 레인별 109/94/90/100/96/97/102/97개, 총 785회 만료.
- seed 19의 동일 스케줄 두 개를 1,000틱 비교: 일치.
- 100초 긴 Tick: 만료 마스크 255, 직후 0.5초 Tick: 0. 밀린 전체 횟수를 반복 생성하는 루프는 없음.

이는 스케줄 동작 검사이며 게임 전체 컴파일·물리 테스트·성능 벤치마크가 아니다. Unity Test Runner, 빌드, 호스트/참가자 실행은 하지 않았다. 기존 테스트 소스를 검토했지만 통과했다고 주장하지 않는다.

다음 실측은 같은 시드/카메라/품질에서 탐색 30초, 공세 60초, 생성 중단 후 20초를 솔로·호스트·참가자별로 비교한다. CPU/GPU 프레임 시간, Physics, GC 할당, 생성 수, live/scar/ghost 수, 송수신 바이트를 기록한다. 전체 게임 틱을 멈추면 수명도 멈추므로 생성만 정지해야 한다.

회귀 확인: 낙하 예고와 착탄 시점, 방망이 반사·리듬, 피해 1회, 착탄 돌 집기/투척/밀기, 파츠·운반체 충격, 컷신 스킵/재생, 팀 리트라이, 중도 참가, 호스트 인계, 패킷 유실 후 흔적 삭제. 원격 흔적에 접촉한 참가자가 로컬 피해를 받지 않는지도 확인한다.

워크트리 생성 시 기존 Mirror 폰트 3개의 LFS 포인터 경고가 있었다. 해당 파일 및 미디어 에셋은 수정하지 않았다. LFS 필터를 비활성화한 status는 정상 스머지된 미디어를 수정으로 표시할 수 있으므로 그 결과를 코드 변경으로 해석하지 않는다.
