# S15P21B202-262 수동 배치 손실 사고 기록 및 재발 방지

- 사고 발생일: 2026-09-02
- 기록일: 2026-09-03
- 대상: `METAGAME/Assets/Scenes/Main.unity` 및 Unity에서 편집하던 자연물 배치
- 책임: 사용자의 수동 편집을 보존하지 않고 작업 범위를 넓힌 AI 작업자의 실행·판단 오류
- 현재 사용자 결정: 복구 중단. 262 브랜치에서 사용자가 직접 재배치한다. 자동 배치·재생성 금지.

## 1. 요약

첫 사고는 저장되지 않은 Unity 편집 세션을 보호하지 않은 상태에서 에디터를 강제 종료하고 자동 배치 작업을 진행한 문제다. 이후 복구 과정에서 Recovery 씬까지 삭제해 남은 복구 가능성을 훼손했다.

두 번째 사고는 저장된 작업을 MR에 올리라는 요청을 씬 재생성 요청으로 확대 해석한 문제다. 최신 develop 병합 과정에서 기존 씬 대신 develop 씬을 사용하고, 임시 배치 도구로 Nature 계층을 새로 생성해 저장했다. 이 결과는 사용자의 수동 배치가 아니라 도구가 정한 배치였다.

두 사고 모두 Unity Save 버튼 자체의 실패나 사용자 잘못으로 설명할 수 없다. 첫 사고에서는 편집 중인 메모리 상태를, 두 번째 사고에서는 디스크에 저장된 씬의 작업 의도를 보호하지 못했다.

### 앞선 설명의 정정

"충돌 전에 커밋이 없었다"는 설명은 틀리다. 16:14 커밋은 실제 존재한다.

"16:14 커밋 이전에 마지막 수동 저장본이 이미 덮어써졌고, 그 커밋은 자동 배치본이다"라는 단정도 현재 증거만으로 확정할 수 없다. 기록으로 확실한 것은 **16:14 커밋 이후 병합 과정에서 16:39경 배치 도구를 다시 실행해 저장했다**는 사실이다. 첫 자동 생성 로그와 커밋 사이의 사용자 저장 여부를 확인하지 않고 사건 순서를 단정한 것 또한 잘못이다.

복구한 일부 계층이 사용자가 원한 화면과 다르다는 사실만으로, 원하는 데이터가 모든 과거 씬·다른 계층·TerrainData에 없다고 결론 내릴 수 없다. 사용자 요청에 따라 더 이상의 복구·후보 적용은 수행하지 않는다.

## 3. 첫 번째 사고: 미저장 편집 세션 손실

### 원인

- 디스크에 저장된 파일과 Unity에서 아직 저장하지 않은 편집 상태를 구분하지 않았다.
- 사용자가 편집 중인 Unity 프로세스를 강제 종료했다. Git 상태가 깨끗해도 미저장 편집은 있을 수 있는데 이를 안전 신호로 잘못 취급했다.
- 작업 전에 사용자에게 직접 Save와 정상 종료를 요청하지 않았다.
- 복구 후보인 `_Recovery/0.unity`를 별도 보존하지 않은 채 삭제했다.

### 방지 방법

- 사용자가 사용하는 Unity 프로세스는 강제 종료하지 않는다.
- 에디터가 열려 있거나 저장 여부가 불명확하면, 씬을 바꿀 수 있는 Git 동작도 중단하고 사용자에게 저장·정상 종료를 요청한다.
- Recovery·Temp 후보는 원본을 삭제하거나 이동하지 않는다. 복구를 명시적으로 요청받은 경우에만 복사본을 격리해 검사한다.
- 에디터의 미저장 상태를 보호하기 위해 자동 Save, 씬 재열기, 재임포트, 빌더 호출로 해결하려 하지 않는다.

## 4. 두 번째 사고: MR 준비 중 무단 재생성

### 원인

- 요청은 커밋·푸시·MR 생성이었지만, AI가 씬 배치 변경까지 허용된 것으로 해석했다.
- 씬 병합 시 원래 작업본을 보존·비교하는 대신 develop 씬 위에 자동 배치를 다시 실행했다.
- 당시 빌더의 `Build()`는 씬 열기 → `ClearChildren(nature)` → 프리팹 재생성 → `SaveScene(scene)` 순서였다. 읽기 전용 검증 함수가 아니다.
- 메뉴용 `Apply()`의 저장 확인을 거치지 않고 `Build()`를 직접 실행했다. 다만 저장 확인이 있었더라도, 사용자 배치를 재생성할 권한이 생기는 것은 아니다.
- 자동 배치 후 오브젝트 수와 Terrain·인공물 Transform만 검증했다. 사용자가 편집한 Nature 자체의 보존 여부는 검증하지 않았다.
- 복구 과정에서도 Nature 일부 계층의 지문 일치를 사용자 원본 전체의 일치로 잘못 설명했다. 메시지에서 기대를 과장했고 사용자 확인 전에 성공을 선언했다.

### 방지 방법

- 커밋·푸시·MR 요청에는 Unity 실행·씬 저장·에셋 재생성·자동 배치가 포함되지 않는다.
- 마지막으로 사용자가 저장한 파일을 먼저 명시적으로 스테이징·커밋해 보존한다. 최신 develop 반영을 핑계로 그 이전에 씬을 수정하지 않는다.
- 충돌은 "재생성하면 해결된다"고 취급하지 않는다. 충돌 파일·양쪽 기준 커밋을 설명하고 사용자가 방향을 정할 때까지 멈춘다.
- 사용자의 저장본 여부는 커밋 시각이나 자동 검증 성공만으로 추정하지 않는다.
- TerrainData, 프리팹 오버라이드, 다른 계층까지 화면에 영향을 준다. 일부 Transform 검사 결과를 전체 화면 보존으로 확대해서 말하지 않는다.

## 5. 앞으로의 작업 절차

### A. 사용자가 직접 배치하는 동안

1. 사용자가 262 브랜치에서 배치한다.
2. AI는 요청받은 문서 파일만 수정한다.
3. Unity 실행·종료·Play·씬 열기·저장·새로고침·배치 도구 실행을 하지 않는다.
4. 브랜치 전환·pull/merge/rebase·restore/reset·clean·stash pop을 하지 않는다.
5. 사용자 저장 파일을 "잘못된 변경"이나 "자동 생성 노이즈"로 간주해 되돌리지 않는다.

### B. 사용자가 마지막 저장본의 커밋·푸시를 요청했을 때

1. 마지막 저장 여부를 확인한다. 에디터의 메모리 상태를 대신 저장하거나 폐기하지 않는다.
2. 브랜치와 변경 파일을 읽기 전용으로 확인한다. Main 씬뿐 아니라 사용자가 저장한 TerrainData·프리팹·머티리얼 변경도 확인한다.
3. 저장된 파일의 해시를 기록하고 관련 파일을 명시적으로 스테이징한다. 복구 도구 폴더·Library·개인 설정을 광범위하게 추가하지 않는다.
4. 자동 배치·Unity 검증을 실행하지 않고 저장본 그대로 먼저 커밋한다. 커밋 전후 파일이 바뀌었다면 동시 저장 가능성이 있으므로 멈춘다.
5. 커밋에 기록된 파일과 사용자 저장본이 일치하는지 확인한다. 줄바꿈 정규화와 실제 내용 변경을 구분한다.
6. 푸시 요청이 있을 때만 푸시한다. 훅이 브랜치를 재작성하지 않도록 아래 C 절의 절차를 적용한다.
7. MR은 요청받았을 때만 만든다. 실제 파일 기준으로 템플릿을 작성하고, 실행하지 않은 Unity 테스트를 통과로 표시하지 않는다.

### C. 푸시 훅의 숨은 작업 방지

현재 `.githooks/pre-push`는 단순 업로드만 수행하지 않는다. 기본 설정으로 develop을 가져오고, 분기 상태에 따라 rebase 또는 merge와 stash 작업을 수행할 수 있다.

- 수동 저장본 그대로 푸시하는 요청에서는 해당 명령의 실행 환경에 한해서 `METAGAME_AUTOREBASE=0`을 설정한다.
- 명령 종료 후 이전 환경 값으로 복원한다. 전역 설정이나 팀 공용 훅은 허락 없이 수정하지 않는다.
- 이 옵션은 훅에 마련된 develop 자동 반영 부분만 끈다. 브랜치명 검사와 LFS 업로드는 유지한다.
- `--no-verify`로 모든 검사를 끄거나 강제 푸시로 우회하지 않는다.
- develop이 갱신됐다는 이유로 자동 병합하지 않는다. 업로드와 통합 작업을 분리해서 사용자에게 알린다.

### D. 최신 develop을 요청했을 때

1. 먼저 원격 커밋만 fetch한다. fetch 완료는 작업 폴더에 develop 반영이 끝났다는 뜻이 아니다.
2. Unity가 열려 있으면 저장·정상 종료를 요청하고, 사용자가 완료했다고 알려줄 때까지 브랜치나 씬을 변경하지 않는다.
3. 로컬 저장 변경이 있으면 먼저 보존할 커밋 범위를 확인한다. 임의 stash·reset·restore로 치우지 않는다.
4. 현재 작업 브랜치에 최신 변경을 병합하는 것과, 브랜치를 develop과 동일한 상태로 다시 맞추는 것을 구분한다. 후자는 기존 작업 이력을 제외하므로 별도 동의가 필요하다.
5. 승인된 범위에서만 Git 통합을 수행한다. 충돌이 생기면 자동 재생성·한쪽 버전 강제 선택을 하지 않는다.
6. 충돌·미완료 병합이 없고 최신 develop을 포함하는지 확인한 뒤에만 "직접 작업을 시작해도 된다"고 알린다.
7. 준비 완료를 알린 뒤에는 사용자가 작업하는 동안 씬·브랜치를 다시 변경하지 않는다.

## 6. 복구와 재발 방지의 경계

- 이 문서는 사고 기록과 앞으로의 실행 절차다. 복구 실행, 자동 배치 코드 수정, 훅 설치·수정, 자동 백업 서비스 설치 요청이 아니다.
- 현재 원본 복구 성공은 확인되지 않았다. 복구 성공을 약속하거나 사용자가 중단한 복구 작업을 재개하지 않는다.
- 향후 별도 승인을 받은 복구가 필요하다면 원본 보존 → 별도 후보 복사본 → 사용자 시각 확인 → 승인된 이식 순서여야 한다.
- 파일 수준 복구 가능성은 저장 방식과 이후 디스크 쓰기에 따라 다르다. "반드시 복구된다" 또는 "완전히 없어졌다"고 증거 없이 단정하지 않는다.

## 7. 이 기록의 완료 기준

- 두 사고의 원인을 미저장 세션 손실과 저장된 씬 재생성으로 구분했다.
- 충돌 이전 커밋이 있었다는 사실과 앞선 설명의 불확실성을 정정했다.
- 자동 배치 금지, 사용자 저장본 우선 커밋, 푸시 훅 통제, 충돌 시 중단을 명시했다.
- 해결책은 실행 절차로만 기록했다. 씬·코드·훅 변경과 복구를 실행하지 않았다.
