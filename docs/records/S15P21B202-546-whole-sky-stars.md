# S15P21B202-546 — 하늘 별을 전천에 깔고 반짝이게 한다

> 신고: "또 하늘에 별이 일부분만 있는거, 이거 전에 고쳐달라고 했는데 제대로 안바뀌었다."
> 이어서: "별이 하늘 전체에 보이게 하는 거 맞아? 전체적으로 다 반짝거려야 해"

## 한 줄

**`-530` 에서 고친 코드는 Stage1_Astra 에서 한 줄도 실행되지 않았다.** 실제로 그려지던
별은 씬에 박아 둔 아트 메시 1000개였고, 그 메시는 하늘의 87.5%를 비워 두고 있었다.

## 왜 `-530` 이 화면을 못 바꿨나

`SpaceBootstrap` 에는 하늘을 만드는 길이 셋 있고, 셋 다 같은 문지기를 지난다.

```csharp
bool authoredLighting = authoredMap != null && authoredMap.preserveSceneLighting;   // :71
bool useAtmosphere = !authoredLighting && atmosphereProfile != null && !배치;        // :103
if (useAtmosphere)          AddComponent<AtmosphereBackdrop>();                     // :121
else if (!authoredLighting) Sky = AddComponent<Vacuum>();                           // :125
if (!authoredLighting && !useAtmosphere && starfield) Starfield.Create(...);         // :203
```

씬에서 읽은 값:

| | Stage1_Astra | Main |
| --- | --- | --- |
| `preserveSceneLighting` | **1** | (컴포넌트 없음) |
| `starfield` | **0** | 1 |

`preserveSceneLighting = 1` 이라 **세 길이 전부 닫힌다.** 씬 스카이박스
`Twilight sky.mat` 은 별이 없는 3색 그라디언트다. 보이던 별은 씬 오브젝트
`Distant star field`(`Art/Stage1Concept/Meshes/Stars.asset`)였다.

### 그 메시를 쟀다

| | 값 |
| --- | --- |
| 별 | 1000개 |
| bounds center | (0.06, 109.77, **270.04**) |
| bounds extents | (339.09, 99.78, **29.83**) |

구가 아니라 한쪽에 걸린 판이다.

```
고도(30도 구간, 아래→위):  0  0  0  887  113  0
방위(45도 구간):           97 394 403 106  0  0  0  0
```

면적이 같은 전천 96칸 중 **84칸이 비어 있다.** 게다가 월드 원점 고정이라 플레이어를
따라오지 않는다 — 실제 씬을 렌더해 세어 보면 원점에서는 8방향 중 1방향이 비는데
**동쪽 80m 에서는 4방향이 빈다**(씬의 실제 범위는 166×237m 다).

## 고친 것

### (1) 문지기를 가른다

"수제 맵의 조명을 보존한다" 와 "하늘에 별을 뿌리지 않는다" 는 서로 다른 결정인데 하나에
묶여 있었다. `AuthoredMapSettings.useCodeStarfield`(기본 켬)를 더해 갈랐다.

- `AtmosphereBackdrop.ApplyStarsOnly` — **별만** 만든다. `BuildSky` 를 건너뛰므로
  `RenderSettings.skybox` 를 덮지 않고, 행성·달도 만들지 않는다(수제 맵에 이미 천체
  아트가 있을 수 있어 겹치면 두 개로 보인다).
- `SpaceBootstrap` 이 수제 맵에서 이 길을 탄다.
- 씬의 `Distant star field` 를 **끈다**(지우지 않았다 — 아트 에셋은 남긴다).

실측 비교(같은 씬·같은 자리·같은 방향, 면적이 같은 전천 96칸):

| | 별 | 빈 칸 | 원점 8방향 | 동쪽 80m 8방향 |
| --- | --- | --- | --- | --- |
| 지금까지 (아트 메시) | 1000 | **84/96** | 1방향 빔 | **4방향 빔** |
| 이 브랜치 (코드) | 4400 | **0/96** | 0 | **0** |

씬을 실제로 렌더해 방위 8곳의 별 픽셀을 세면 **어느 자리·어느 방향에서도 최소 548개**다
(똑바로 위를 봐도 626~701개). 지금까지는 0 이 나오는 방향이 있었다.

> **완전 균등은 아니다.** 칸당 24~104 로 4배 차이가 난다. 은하수 띠(900개)가 의도적으로
> 몰린 것이고 없애면 하늘이 밋밋해진다. "빈 곳이 없다" 와 "완전히 균등하다" 는 다른
> 목표이며 이 티켓은 전자다.

### (2) 반짝이게 한다

**지금까지 별은 한 번도 깜빡인 적이 없다.** 정점 색이 구워진 정적 메시이고,
`LateUpdate` 는 위치만 옮기며, `FlatUnlit.shader` 에 `_Time` 이 0회 나왔다.

**셰이더에서 한다.** CPU 로 매 프레임 정점 색을 다시 쓰면 별 4400개 = 정점 17600개를
매 프레임 올려야 한다 — 화면에 보이는 것에 비해 너무 비싸다.

별마다 다른 위상이 필요한데 **쓸 자리가 이미 있었다.** 정점 색의 알파는 불투명 패스라
버려지므로 지금까지 `1f` 가 들어가던 빈칸이었다. 거기에 위상을 싣는다 — 정점도 메모리도
늘지 않는다.

```hlsl
half phase = input.color.a * 6.2831853;
half wave = 0.5 + 0.5 * sin(_Time.y * _TwinkleSpeed + phase);
half twinkle = lerp(1 - _TwinkleAmount, 1, wave);
return half4(_Color.rgb * input.color.rgb * twinkle, 1);
```

`_TwinkleAmount` 의 **기본값은 0** 이다. 이 셰이더는 주석대로 "stars and distant markers"
공용이라, 기본이 0이어야 별이 아닌 것들이 한 픽셀도 바뀌지 않는다. 별 머티리얼만
프로파일 값(0.55 / 2.4)을 올린다.

#### 위상을 난수열에서 뽑지 않았다

여기서 `random.NextDouble()` 을 한 번 더 부르면 그 뒤의 별이 전부 밀려 **별자리가 통째로
바뀐다.** `!444` 에서 색을 다른 흐름으로 옮기며 별빛을 조용히 다시 굴린 적이 있다.
대신 번호에서 결정적으로 만든다.

```csharp
public static float TwinklePhaseAt(int index) =>
    index * 0.6180339887f - Mathf.Floor(index * 0.6180339887f);
```

**단정하지 않고 쟀다.** develop 과 이 브랜치에서 각각 배포 설정으로 별 4400개를 만들어
방향·밝기·크기·색을 하나의 수로 접었다.

```
develop  접은 값 72538.507222
브랜치   접은 값 72538.507222
```

한 톨도 안 바뀌었다.

## 검증

`Stage1SkyCoverageTests` 8개 + `StarTwinkleTests` 10개 = **18개**.

**`StarfieldEvennessTests`(`-530`)와 겹치지 않는다.** 저쪽은 *알고리즘이 옳은가* 를 재고,
이쪽은 *그 알고리즘이 이 씬에서 실제로 돌 수 있는가* 를 잰다. `-530` 이 통과하고도
화면이 그대로였던 이유가 정확히 그 틈이었다.

- 씬: 수제 조명이 켜져 있는가 · 코드 별하늘을 요청하는가 · 프로파일이 있는가 ·
  아트 메시가 꺼져 있는가
- 전천: 96칸에 빈 칸이 없는가 · 천정과 지평선 아래에 별이 있는가 · 방위 8구간이 고른가
- 아트 메시가 **덮을 수 없었다**는 것도 못박는다(없으면 위의 검증들이 "원래 문제가
  없었다" 로도 통과한다)
- 반짝임: 위상 범위 · 이웃끼리 안 붙는가 · 한 바퀴를 채우는가 · **별빛이 안 바뀌었는가** ·
  메시 알파에 실리는가 · 머티리얼이 프로파일 값을 받는가 · **공용 셰이더 기본값이 0인가** ·
  별만 만들 때 하늘과 천체를 안 건드리는가 · 전체 적용은 여전히 다 만드는가

### 화면으로 확인했다

실제 씬을 렌더해 PNG 로 남겼다. 반짝임은 **한 바퀴(2.6초)를 12장으로 찍어** 확인했다.

`_Time` 을 밖에서 바꿀 수 없어(`Shader.SetGlobalVector` 가 안 먹었다) **실제로 기다려서**
쟀고, **대조를 함께 돌렸다.**

| 1.3초 뒤 | 어두워진 픽셀 | 밝아진 픽셀 | 총 밝기차 |
| --- | --- | --- | --- |
| 반짝임 깊이 0.00 | **0** | **0** | **0.0** |
| 반짝임 깊이 0.55 | 461 | 383 | 168.5 |

깊이 0 에서 변화가 정확히 0 이므로, 달라진 픽셀은 씬의 다른 무엇이 아니라 별이다.

> 이 대조를 넣기 전에 한 번 틀렸다. 처음에는 `speed=0` 으로 두고 깊이만 바꿔 비교했는데
> **밝아진 픽셀이 850개** 나왔다 — 깊이를 올리면 별은 어두워지기만 해야 하므로 있을 수
> 없는 값이다. 설명하지 못한 숫자라 보고하지 않고 측정 방법을 바꿨다.
> (`DestroyImmediate(backdrop)` 만으로는 만들어진 별 메시가 안 지워진다는 것도 그때
> 알았다 — `OnDisable` 의 `Clear` 는 플레이 중에만 돈다.)

## 남은 것

1. **눈으로 볼 것.** 렌더는 EditMode 카메라이고 게임의 후처리(톤매핑·블룸·비네트)를
   거치지 않았다. 반짝임의 깊이 0.55 · 빠르기 2.4 는 **눈으로 맞춰야 하는 값**이다 —
   별이 1~3픽셀이라 너무 깊으면 반짝임이 아니라 지글거리는 잡티가 된다.
2. `Distant star field` 는 껐을 뿐 지우지 않았다. 아트가 더 쓸 데가 없다고 하면 그때
   메시 에셋까지 정리한다.
3. `Vacuum` 과 레거시 `Starfield` 가 이제 어느 씬에서도 안 도는지 따로 봐야 한다.
   안 돈다면 지울 후보다.
4. `WorldSyncReadinessTests` 도 `Main.unity` 를 연 채로 끝난다. 이 티켓의 범위를 넘어
   건드리지 않았지만 같은 함정이다.
