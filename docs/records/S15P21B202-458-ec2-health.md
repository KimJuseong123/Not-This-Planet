# 아침 점검이 서버를 본다 (S15P21B202-458)

2026-09-11

## 무엇이 문제였나

아침 점검(`mm-digest`, 평일 09:30)은 **Jira 와 GitLab 만** 봤다. 서버는 아무도 보지 않았다.

그래서 이런 것들이 조용히 나빠졌다:

- **컨테이너가 죽어 있는 것.** 2026-09-11 에 개발 백엔드가 `JWT_SECRET` 때문에 재시작 루프였는데, 사람이 `docker ps` 를 쳐 봤기에 알았다. 그러지 않았으면 그날 팀 테스트가 통째로 막혔을 것이다
- **디스크가 차는 것.** 릴리스마다 빌드 산출물이 쌓이고 회수 절차가 없다(`-457`)
- **인증서 만료.** certbot 자동 갱신이 멈춰도 만료 당일에야 안다
- **꺼져 있어야 할 것이 살아난 것.** `metagame.service` 는 `disabled` 지만 확인하는 장치가 없었다

## 어떻게 보나 — 호스트가 재고 잡이 읽는다

**CI 잡은 도커 컨테이너 안이라 호스트를 직접 못 본다.** 그래서 이렇게 나눴다:

```
호스트                                   CI
────────────────────────────────────    ──────────────────────────────────────
metagame-status.timer  (5분마다)
  └ /opt/metagame-deploy/ec2-status.sh
      └ JSON 한 장 →
        /home/ubuntu/metagame/deploy/EC2-STATUS
                                         ec2-status 잡  (tags: deploy)
                                           └ /spool/EC2-STATUS 를 읽어
                                             ec2-status.json 아티팩트로
                                         mm-digest 잡  (공용 러너)
                                           └ 아티팩트를 읽고 판정 → 아침 카드
```

`deploy.sh` 가 `STATUS` 를 쓰고 잡이 읽는 것과 **같은 방식**이고 이유도 같다 — **도커 소켓도 SSH 키도 CI 에 주지 않는다**(`-139` · `-252` · `-324`).

잡을 둘로 나눈 이유: `mm-digest` 는 공용 러너에서 돌아 `/spool` 이 보이지 않는다. 스풀이 마운트된 배포 러너에서 한 번 꺼내 아티팩트로 넘긴다. **`ec2-status` 는 `allow_failure: true` 다** — 서버를 못 본 것이 아침 카드 전체를 막으면, 정작 서버가 나쁠 때 아무 소식도 없다.

### 재는 쪽과 판정하는 쪽을 나눈 이유

호스트 스크립트는 **재기만 한다.** 임계값과 문구는 전부 `scripts/ci/ec2_status.py` 에 있다.

- 임계를 바꾸려고 **서버에 들어가지 않아도 된다** (호스트 스크립트를 고치면 설치를 다시 해야 한다)
- 판정 로직을 **오프라인 테스트로 잠글 수 있다** — 이 판정은 서버가 나빠진 아침에만 돌아서, 조용히 틀리면 나쁜 날에 아무 말도 안 한다

2026-09-11 실측에서 **한참 떨어진 곳**에 선을 뒀다. 실측값 바로 옆에 두면 평소에도 울리고, 그러면 사람이 카드를 안 본다 — 없는 것과 같아진다.

| --- | --- | --- | --- |
| 디스크 | 80% | **20%** (여유 250 GB) | 차면 빌드와 배포가 같이 죽는다 |

| 인증서 | 30일 이하 | **78일** | certbot 이 멈춰도 한 달 전에 안다 |
| 상태 파일 나이 | 20분 초과 | 5분 주기 | 네 번 빠지면 재는 쪽이 멈춘 것이다 |

## 두 가지 함정 — 기록해 둔다

### ① `/actuator/health` 는 **403** 을 준다. 그래도 정상이다

인증에 막혀서 그렇다. 403 은 **스프링이 응답했다**는 뜻이고, 앱이 죽으면 curl 이 `000`(연결 거부)을 돌려준다. 우리가 잡으려는 것이 그 `000` 이다.

403 을 실패로 읽으면 **매일 아침 두 줄이 뜬다.**

### ② 준비 확인용 `/auth/guest` 를 여기서 쓰면 안 된다

`deploy.sh` 는 그것을 쓰지만 **배포마다 한 번**이다. 5분마다 부르면 **게스트 사용자가 계속 쌓인다.** 테스트가 이 규칙을 잠근다.

## 조용한 것과 못 읽은 것을 구별한다

**정상이면 아무 줄도 붙지 않는다** — `mm-digest` 규칙 그대로다.

그런데 상태 파일을 **못 읽은 것**도 조용하면, 재는 쪽이 멈춰도 "서버가 멀쩡하다" 로 읽힌다. 그것이 이 기능이 없던 상태와 같다. 그래서 못 읽음·오래됨을 각각 한 줄로 만든다.

오래된 값으로 **나머지를 판정하지는 않는다** — 이미 고쳐진 것을 계속 말하게 된다.

## 알아 둘 것 — 스풀은 배포 잡이 쓸 수 있다

상태 파일이 놓이는 스풀은 배포 러너에 `rw` 로 마운트돼 있다. 즉 **배포 태그가 붙은 잡은 가짜 상태를 써 넣을 수 있다.** 그 러너는 Protected · `ref_protected` 라 보호 브랜치에서만 돌고(`-252`), 이 파일은 알림용이라 그것으로 서버가 바뀌지는 않는다. 다만 알아 두고 쓴다.

## 설치

```
sudo bash scripts/deploy/host/install-status.sh
```

`install.sh` 와 따로 둔 이유: 배포 장치 설치는 러너를 재시작한다. 이쪽은 재시작이 필요 없는 추가라, 섞어 두면 상태 하나 고치려고 배포 러너를 내리게 된다.
