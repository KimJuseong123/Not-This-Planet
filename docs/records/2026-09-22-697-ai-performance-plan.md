## 원인 후보와 해결 방법

### 1. 2초 간격 광역 내비게이션 갱신 — 최우선 CPU 후보, AI 정지 경로 확인

`Runtime/Network/AiNavigationWorld.cs:52–120`: 서버 AI 상태가 Active이면 2초마다 크기 `(512,128,512)` 범위의 PhysicsCollider 소스를 수집·필터링하고 NavMesh 갱신을 요청한다. 실제 AI 수, 진행 중인 작업, 지형 변경 여부를 갱신 조건으로 확인하지 않는다. Active 상태라면 AI가 없는 방도 불필요한 갱신 대상이 될 수 있다.

`UpdateNavMeshDataAsync`를 쓰지만 그 전에 호출하는 `CollectSources`와 부모 검사, 콜라이더 필터링은 호출 스레드의 일이다. 네이티브 갱신이 매번 모든 타일을 전부 다시 만든다고 단정하지 않는다. 비동기 빌드에도 CPU 작업과 자원 경쟁은 남는다.

`Ready`는 빌드 진행 중 false가 된다(:22). 이미 유효한 내비게이션 데이터가 있어도 Follow/Pin/Recovery가 이 상태에서 이동 입력을 비우거나 경로를 초기화한다. 즉 갱신 때 AI가 멈출 수 있는 제어 흐름이 있다. 이것만으로 사람 플레이어의 이동 누락을 설명할 수는 없다.

해결: AI 작업 수요와 geometry dirty 상태로 갱신을 제한하고 변경을 모아서 처리한다. 정적 지형은 사전 베이크, 동적 물체는 설계에 맞는 장애물/국소 갱신으로 분리한다. 가능한 경우 기존 유효 경로를 유지하고 새 버전이 준비되면 전환한다. 단순히 Ready 검사를 지우면 이동한 부품을 통과할 수 있으므로 즉시 충돌 검사와 경로 무효화 조건을 함께 설계해야 한다. voxel 크기는 좁은 통로의 통과 정확도와 함께 비교한다.

### 2. AI 음성 명령이 이동 입력과 같은 reliable 채널에 몰림 — 통신 지연 후보

`Runtime/Network/NetPlayer.AiVoice.cs:30–67`: 녹음 종료 시 WAV를 8192바이트씩 나누지만 같은 호출에서 모든 Command를 연속 전송한다. `AiVoicePacket` 기준 최대 8초/16kHz/16bit로 256,044바이트, 최대 32개 청크다. 기본 reliable Command이며 `CmdSendInput`도 같은 reliable 채널이다. 청크로 쪼갰다는 사실만으로 대역폭이나 프레임당 전송량이 제한되지는 않는다.

`Runtime/UI/AiVoiceControls.cs`는 종료 시 샘플 복사와 WAV 인코딩을 수행하고, 청크마다 배열을 새로 만든다. 따라서 V키를 놓는 시점에 메인 스레드/GC 비용과 송신 대기열 증가가 함께 발생할 수 있다. 서버가 Busy로 시작을 거절해도 클라이언트는 승인 응답을 기다리지 않고 청크를 이미 보낸다.

해결: 업로드 승인/Busy 응답 후 전송, 프레임·연결별 전송 예산, 음성 압축, 재사용 버퍼를 적용한다. 오디오와 조작 데이터의 스케줄링을 분리한다. 별도 연결도 공통 대역폭을 공유하므로 혼잡 제어가 필요하다. RPC 이름 변경은 격리가 아니며, 재조립·유실 복구 없이 unreliable로 바꾸면 음성 명령이 깨진다.

### 3. 호스트 CPU 추론 경쟁 — 명령 실행 중에 측정할 후보

`tools/AICompanionService/portable_worker.py:136–137`: Whisper CPU int8, CPU 4스레드, worker 1. `companion_plan.py:89–92`, `engine.py:16`: LLM은 CPU 4스레드, `num_gpu=0`, context 4096, 출력 상한 640토큰이다. 단일 실행 lock과 STT→LLM 순차 처리이므로 한 요청에서 두 엔진이 항상 8스레드를 동시에 사용한다고 설명하면 안 된다.

Unity는 비동기 웹 요청으로 기다린다. 요청 대기 자체가 매 프레임 Unity 스레드를 직접 막는 구조는 아니다. 다만 같은 PC의 추론 프로세스가 Unity 물리·렌더 준비·내비게이션과 CPU/메모리 대역폭을 경쟁한다. AI가 존재한다고 지속적으로 모델을 추론하거나 일반 근접 음성마다 LLM을 실행하지는 않는다.

해결: 호스트 CPU 사용률/프레임 시간과 추론 구간을 함께 기록하고 스레드 2/4, 프로세스 우선순위, context/출력 예산을 비교한다. 모델은 로비에서 실제 명령 경로로 예열한다. 출력 상한 축소는 JSON 잘림과 명령 정확도를 검증해야 한다. GPU 이관은 렌더링/VRAM 경쟁이 있어 자동 해결책으로 취급하지 않는다.

### 4. AI 경로·물리 질의의 순간 집중 — 호스트 CPU 후보

`NetPlayer.cs:1082`에서 AI Tick은 서버 FixedUpdate에 연결된다. 현재 물리 기준은 100Hz다. Follow의 안전 검사, Recovery, 조향이 물리 실행과 연동된다. 단, `AiNavigationRoute`는 경로 객체/코너 버퍼를 재사용하고 .75초 또는 목표 이동 조건으로 재탐색을 제한한다. 모든 경로 계산을 100Hz로 수행하는 것은 아니다.

`AiPinTask.Select/FindApproach`: 후보마다 최대 3개 반경×8방향 접근점을 평가하며 일부 지점에서 경로를 계산한다. 이는 선택/목표 변경 시 비용이며 매 틱 전체 탐색이라고 단정하지 않는다. `AiWorkTask.StandNear`에도 동기 경로 탐색이 있다. `AiFlightCorridor.Find`는 최대 20개 후보×5구간 검사 구조이며 재시도는 제한돼 있어도 한 번의 호출에 비용이 모일 수 있다.

해결: 전략 판단과 물리 제어를 분리한다. 전략 판단 5–10Hz를 초기 실험값으로 두고 캐릭터별 실행 시점을 분산한다. 후보 탐색은 프레임별 예산으로 나누고 내비게이션 버전/물체 이동 기준 캐시를 둔다. 긴급 정지, 충돌 안전, 점프·잡기 타이밍까지 저주기로 낮추면 기존 AI 행동이 망가질 수 있다.

### 5. 기존 공통 비용 — AI와 함께 누적

- `PartOutlineTargets.Collect`, `PartOutlineGroups`: 매 프레임 전체 부품 검색과 그룹 컬렉션 할당. 등록/해제 목록, 결합·분리 시 dirty 처리, 버퍼 재사용으로 변경한다. 파괴·풀링·씬 전환 시 캐시 무효화 누락을 검증해야 한다.
- 100Hz 물리, solver 14/4, 래그돌 ContinuousDynamic, 원격 팔다리의 동적 물리: 솔로/호스트/클라이언트 모두 캐릭터 수에 따른 비용을 측정한다. 충돌 레이어 정리, 수면, 중요 부위 선택적 CCD, 거리/역할별 물리 단순화를 우선한다. 60Hz/50Hz 변경은 관절·운반·던지기·점프·예측까지 영향을 주므로 마지막에 별도 실험한다. 현재 AI는 설정/활성 조건에 따라 충원되며 모든 모드가 항상 같은 인원인 것은 아니다.
- PC URP의 전체 해상도 SSAO, 4단 그림자, 추가 광원 그림자, 색상/깊이 텍스처, 안개와 두 outline 패스: GPU 시간을 측정해 반해상도 SSAO, 그림자 거리·계단 수·광원 예산, 불필요한 복사/패스 제거를 비교한다. SRP Batcher는 이미 켜져 있다. 상위 품질 단계들이 같은 PC 에셋을 공유하므로 이름만 바꿔도 비용이 줄지 않을 수 있다.
- 메시/콜라이더: Stage1 직접 YAML에 MeshRenderer 438, MeshCollider 524, prefab instance 875가 있다. 런타임 활성 수나 draw call 수가 아니며 prefab 확장을 포함하지 않는다. LOD, instancing, 정적 배칭, 단순 충돌체는 실제 가시성·재질·이동 특성에 맞춰 적용한다. 전역 mesh combine은 컬링을 악화시킬 수 있다.
- `SoundRuntime`의 반복 오브젝트 검색과 `ReportAim`의 문자열 생성은 캐시/진단 게이트로 줄인다. 초상화 BakeMesh는 이미 외형 캐시가 있어 우선순위가 낮다.

### 6. 사람의 입력 누락은 별도 정확성 문제도 존재

`NetPlayer.cs:1325–1332`의 `CmdSendInput`은 pending 하나를 덮어쓴다. 한 물리 스텝 전 짧은 누름/해제가 함께 도착하면 사건을 놓칠 수 있다. 계속 누른 이동이 영구적으로 안 되는 현상까지 입증하지는 못했다. 현재 20Hz 간격은 변경 입력 전체의 상한이 아니라 keepalive 성격이며 마우스 변화도 전송을 유발한다.

해결: 이동 같은 지속 상태는 최신 상태를 유지하고, 상호작용 같은 단발 사건은 순번을 가진 별도 큐로 중복 없이 소비한다. 입력 시각/서버 소비 틱/ack를 기록하고 예측 보정은 같은 시뮬레이션 시점끼리 비교한다. 오래된 이동을 모두 재생하는 큐는 지연을 쌓는다. reliable 전송 자체가 결함이라는 뜻은 아니다.

별도로 멀티에서 T 끼임 탈출 입력의 서버 실행 경로 누락도 남아 있다. 성능 최적화와 분리해 기능 회귀로 수정·검증해야 한다.

### 7. 일반 근접 음성 — 후순위

일반 음성은 AI 명령 업로드와 다르다. 40ms/640바이트 단위, VAD, unreliable, 거리 수신 제한이 이미 있다. 발화자당 payload 약 16KB/s다. 수신자 수에 따른 호스트 중계 비용, 패킷별 배열, 오디오 큐 lock은 측정할 가치가 있다. Opus/블록 단위 링 버퍼/장치 목록 캐시를 검토하되 현재 증거로 가장 큰 병목이라고 판단하지 않는다.
