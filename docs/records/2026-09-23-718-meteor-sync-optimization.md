# 718 운석 동기화 최적화

기준: `S15P21B202-718-physics-fps-72-41`, `af143761`. 2026-09-23.
선행 조사: [운석 성능 검토](2026-09-23-718-meteor-performance-review.md).
화면 조작 없이 소스 검토·자료 조사·Unity 배치 테스트를 수행했다.

## 증상과 원인 범위

호스트가 보내는 것은 완성된 렌더링 이미지가 아니라 운석 위치·회전·속도·상태다. 참가자는 이를 표시용 운석에 적용한다. 기존에는 참가자 물리가 다음 위치를 예측하다가 수신 때 Rigidbody 위치를 즉시 덮어썼다. 이러한 보정은 FPS가 충분해도 물체가 끊겨 보이는 원인이 될 수 있다.

소스 및 회귀 테스트에서 확인한 문제:

- 낙하 목록의 순서가 바뀌면 기존 고스트가 다른 운석을 맡았다. 모델뿐 아니라 이미 그린 꼬리가 다른 자리로 옮겨갈 수 있다.
- 착탄 전체 목록은 움직이는 돌도 추정 속도를 0으로 초기화했다.
- 이동 속도를 참가자 패킷 도착 시간으로 계산했다. 묶여 도착하는 패킷의 간격은 서버 시뮬레이션 간격과 다르다.
- 신뢰 채널 전체 목록이 비신뢰 채널 이동보다 늦으면 목록 전체를 버려 생성·삭제까지 다음 keepalive로 미뤘다.
- 매 착탄/소멸마다 모든 착탄 운석의 자세를 다시 보냈다.
- 원격 착탄 운석의 생성/파괴와 낙하 꼬리 방출이 계속됐으며, 비활성 MonoBehaviour만 믿어 충돌 판정을 차단하지 못했다.
- 생성 상한이 렌더 프레임이 아니라 개별 물리 Tick에 적용됐다.

실제 사용자 환경의 FPS 하락을 하나의 원인으로 확정한 것은 아니다. 공세 후 약 8배의 낙하량, 호스트의 물리/착탄 처리, 모델·그림자·경고 렌더링, 프레임 지연에 따른 여러 FixedUpdate 실행은 별도의 비용이다.

## 조사한 기법과 적용 선택

- [Mirror Snapshot Interpolation](https://mirror-networking.gitbook.io/docs/manual/components/network-transform/snapshot-interpolation): 여러 스냅샷을 버퍼에 두고 사이를 보간하는 방식. 불규칙한 네트워크를 완충하지만 버퍼만큼 표시 지연을 추가한다.
- [Gaffer — State Synchronization / Visual Smoothing](https://gafferongames.com/post/state_synchronization/): 물리 상태는 확정 값으로 보정하고 표시의 위치·회전 오차만 시간에 따라 줄이는 방식.
- [Gaffer — Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/): 송신 주기보다 높은 화면 주기로 움직임을 표시할 때 보간·패킷 손실을 다루는 배경.

운석은 방망이 타이밍 가이드와 착탄 돌의 물리적 가로막기가 있으므로, 이번에는 긴 표시 버퍼를 추가하지 않고 **상태 동기화 + 모델의 오차 완화**를 적용했다. 스냅샷 버퍼 보간 전체를 도입했다고 주장하지 않는다.

## 적용한 변경

### 낙하와 화면 보정

- 권위 운석 생성 시 생애별 ID를 부여하고 송신한다. 고스트는 ID로 유지한다. 앞 운석 삭제/목록 재정렬에도 남은 모델과 꼬리의 대응을 보존한다.
- `MeteorReplicaVisual`이 물리 루트와 시각 모델을 분리한다. Collider/Rigidbody가 있는 자식은 옮기지 않는다. 실제 프리팹의 모델 계층과 생성형 fallback 구체를 지원한다.
- 수신 시 물리 루트는 확정 좌표를 받고, 모델은 직전 표시 위치·회전을 유지한 뒤 프레임률에 독립적인 지수 감쇠로 오차를 줄인다. 작은 오차의 반감기는 약 35ms이며 큰 오차는 더 빠르게 보정한다. 2m 초과는 즉시 이동해 긴 끌림을 막는다.
- 오차가 해소되면 시각 자식의 매 프레임 Transform 쓰기를 멈춘다. 물리 루트의 기존 보간은 유지한다.

### 착탄·착탄 후 표시

- 착탄 표시용 운석은 낙하 풀과 분리된 최대 48개 풀에서 재사용한다. 낙하 풀은 기존 최대 16개다. 종료 정리 시 풀도 제거한다.
- 착탄 고스트에서는 낙하 꼬리 방출을 끄고 잔여 점을 정리한다. Collider, Prop 레이어, kinematic 상태는 유지한다.
- `Meteor.IsReplica`가 충돌·착탄·반사·Tick 판정을 차단한다. 컴포넌트가 다시 활성화돼도 표시 고스트가 권위 운석 목록에 등록되지 않는다.
- 호스트의 피해, 집기, 밀기, 방망이 판정, 실제 착탄 수명은 그대로다. 호스트의 운석 전체 풀링은 생애별 이벤트·운반 상태 초기화까지 별도 검증이 필요하므로 이번 수정에 포함하지 않는다.

### 전송과 수신

- 최초/2초 복구 시점에는 전체 목록, 그 사이에는 신뢰 채널의 생성·삭제 차분만 보낸다. 예를 들어 35개 중 하나가 바뀌어도 35개 자세 전체를 재전송하지 않는다. 차분 틱에는 기존 움직이는 돌의 이동 송신도 유지한다.
- 이동 중인 돌만 기존 비신뢰 이동 채널로 보내며, 패킷 용량 초과 시 시작 지점을 순환해 뒤쪽 돌의 갱신이 계속 굶지 않게 한다.
- 서버의 `Time.timeAsDouble` 샘플 시각으로 속도를 계산한다. 두 기기의 절대 시계 일치는 요구하지 않으며 서버 시각 차이만 사용한다.
- 전체 목록에도 Moving 상태를 담아, 움직이는 돌의 보간 속도를 무조건 지우지 않는다. 정지 상태에서는 속도를 지운다.
- 멤버십의 순번과 자세의 순번을 구분한다. 늦은 신뢰 목록도 생성·삭제를 반영하되 기존 고스트의 더 최신 자세를 덮지 않는다. 개별 운석의 이전 샘플보다 오래된 자세도 적용하지 않는다.
- 수신 공백 중 착탄 돌의 외삽은 약 100ms까지만 허용한다. 패킷 손실이나 정지 알림 지연으로 무한히 미끄러지는 것을 막는다.
- Mirror의 ID는 가변 길이 정수다. 최악 크기로 낙하 상태 59바이트, 착탄 상태 34바이트를 사용해 패킷 용량을 계산한다. 일반적인 작은 ID는 더 작다. ID·Moving·시간 추가로 개별 상태 크기는 늘지만 빈번한 전체 목록 전송은 줄었다. 실제 네트워크 사용량 감소율은 아직 측정하지 않았다.

### 생성 집중 방지

런타임에서는 동일한 `Time.frameCount`의 여러 물리 Tick이 생성 예산 2개를 공유한다. 순수 테스트는 프레임 번호를 주입할 수 있다. 랜덤 1~5초 규칙과 생존 상한을 유지한다.

## 검증

Unity 6000.5.4f1, `-batchmode -nographics`, EditMode 테스트(일부 EnterPlayMode 포함).

**최종 214개 중 214개 통과, 실패 0.** 결과: `artifacts/718/regression.xml`, 실행 로그: `artifacts/718/regression.log`.

포함 범위: AssaultFrameCost, ScarInterpolation, NetworkReceivedState, ScarSolidGhost, MeteorReplica, IndependentMeteor, MeteorScar, MeteorAftermath, MeteorSpawner, MeteorBat, MeteorBatSwing, MeteorWarning, KinematicVelocityOrder.

새 회귀 검증은 ID 재정렬/삭제, 물리 즉시 보정과 시각 연속성, 큰 이동, 착탄 재사용과 꼬리 종료, 원격 판정 차단, 같은 프레임에 도착하는 서버 샘플, 늦은 멤버십/오래된 이동, 프레임별 생성 상한, 차분 생성·삭제 및 전체 복구, 실제 Mirror 직렬화 최대 크기를 확인한다.

첫 실행의 라이선스 연결 실패는 서비스 접근이 가능한 배치 실행으로 해소했다. 첫 수정 테스트에서 발견된 시각 Transform 갱신 시점, 가변 길이 ID 크기, 테스트 PlayMode 전환 정리 문제를 수정한 뒤 최종 회귀를 통과했다. 초기 테스트 실패를 기존 문제로 숨기지 않는다.

테스트가 다시 저장한 렌더링 설정/머티리얼 11개는 줄바꿈 정규화 후 HEAD와 내용이 동일함을 확인하고, 바이트 단위 백업 후 원복했다. 씬·프리팹·패키지·프로젝트 설정의 의미 있는 변경은 없다.

## 남은 검증과 적용 조건

- 프로토콜 필드와 RPC 서명이 변경됐다. **호스트와 참가자를 모두 같은 새 빌드로 실행해야 한다.** 구버전과 혼합 연결은 지원하지 않는다.
- 실제 두 기기/다인 연결의 RTT, 패킷 손실, 호스트 인계, 늦은 참가, 화면 품질과 FPS는 미측정이다. 214개 테스트 통과가 다인 실전 성능 개선 수치를 뜻하지 않는다.
- 같은 카메라·품질·시드에서 탐색/공세/생성만 정지한 뒤를 비교하고 CPU/GPU 프레임 시간, Physics, GC, 송수신 바이트와 살아 있는 운석 수를 따로 기록해야 한다.
- 실제 모델의 그림자/경고 효과가 GPU 병목이면 LOD·그림자 거리·화면 점유율 최적화가 다음 단계다. 현재 결과만으로 GPU가 주원인이라고 단정하지 않는다.
- 호스트 권위 물리는 유지하므로 GPU나 호스트 물리가 병목인 환경에서는 화면 보정만으로 FPS가 오르지 않을 수 있다.
