# [Network] 장 전환 설계 — 로비를 거치지 않고 다음 맵으로 (S15P21B202-504)

[문서 안내](../README.md) → [작업 기록](README.md) → 네트워크

1장이 끝난 뒤 참가자·연결·호스트를 유지한 채 다음 장 씬으로 넘어가는 방법을 정한 설계 기록입니다. 엔딩 전환 코드에서 재사용할 부분과 새로 만들 부분을 가르고, 백엔드 상태 전이와 후속 구현 단위를 함께 정리합니다.

## 목적

2장이 추가되면 1장이 끝난 뒤 **전원을 다음 맵 씬으로 함께 옮겨야 한다.** 구현에 들어가기 전에 누가 전환을 명령하고, 그때 백엔드의 판 상태가 어떻게 바뀌며, 전환 중에 끊긴 사람을 어떻게 다루는지를 정한다.

이 문서는 **계획과 결정**만 담는다. 코드는 없다. `☐`는 다른 파트나 팀장의 합의가 필요한 것이다.

**현재 상태**: 데모 엔딩은 얼리액세스 범위를 자르느라 만든 임시 종료다. 기획 §22가 “다음 장 로딩을 끼워 넣지 않는다”고 적은 것은 그 범위 선언이며, 장 추가는 예정돼 있다. 그래서 장 전환 경로는 **아직 없다.**

<a id="section-1"></a>

## 1. 기획이 이미 정해 둔 제약

기획 §22.5 — `LaunchTest.cs`의 `Finish()` 주석에 그대로 인용돼 있다:

> 별도의 장 사이 로비와 다시 준비하는 절차는 없다 … 참가자, 연결과 호스트 상태를 유지한 채 다음 장을 로딩한다

여기서 따라오는 것:

- **연결을 끊지 않는다.** 로비를 경유하는 전환(`StopClient` → 로비 → 다시 방 만들기)은 쓸 수 없다.
- **다시 준비하지 않는다.** 준비 버튼·시작 버튼을 다시 누르게 하지 않는다.
- **호스트가 그대로 간다.** 전환을 이유로 호스트를 바꾸지 않는다.

`LaunchTest.Finish()`는 이 사실을 알고 **상태와 이벤트만 남긴다** — `Completed` 이벤트가 붙일 자리로 비어 있다. 스테이지를 초기화하지 않는 것도 같은 이유다.

<a id="section-2"></a>

## 2. 선례 — 엔딩 전환이 이미 푼 문제

`EndingSceneFlow`는 1장 클리어 시 전원을 엔딩 씬으로 옮긴다. **같은 문제의 절반을 이미 풀어 놨다.**

| 푼 것 | 어떻게 |
| --- | --- |
| 누가 씬을 바꾸나 | 서버만 `ServerChangeScene(ScenePath)`. 참가자는 Mirror가 따라오게 한다 |
| 언제 함께 시작하나 | 참가자별 준비 완료를 집합에 모아 `AllParticipantsReady()`가 참이 될 때 `StartTogether()` |
| 시각을 어떻게 맞추나 | `NetworkTime.time` 기준 `startAt`을 서버가 정해 전원에게 방송 |
| 상태를 어떻게 넘기나 | 스냅샷을 JSON 직렬화해 **청크로 나눠 전송**(`EndingSceneSnapshotChunk`, 상한 8MB) |
| 늦게 온 사람 | 서버가 스냅샷을 **보존**하고, 씬을 늦게 로드했거나 재접속한 참가자가 요청하면 다시 보낸다 |
| 실패 | 45초 타임아웃 · `Abort(reason)` 방송 · 3초 뒤 로비 복귀 |

**안 푼 것 — 여기가 장 전환에서 새로 해야 하는 부분이다.**

| 안 푼 것 | 왜 엔딩에는 없었나 |
| --- | --- |
| 플레이어 스폰 | 엔딩은 **종착지**라 조작할 캐릭터가 필요 없다. `SuppressPlayerCreation()`으로 `autoCreatePlayer`를 꺼 둔다. 2장은 다시 플레이가 시작되므로 이걸 **되살려야** 한다 |
| 월드 동기화 재설치 | 엔딩 씬에는 동기화할 월드가 없다. 2장은 `WorldSync`가 새 씬의 오브젝트를 다시 잡아야 한다 |
| 백엔드 판 상태 | 엔딩은 복귀 시 `SendGameEnd()`로 방을 **대기로 되돌린다**. 장 전환은 **판이 계속되므로 이 메시지를 보내면 안 된다** |
| 진행도 보존 | 엔딩은 끝이라 이어서 할 것이 없다 |

<a id="section-3"></a>

## 3. 결정할 것 넷

### 3-1. 1장 → 2장은 같은 판인가, 새 판인가

**제안: 같은 판으로 본다.** §1의 “참가자·연결·호스트 유지”가 사실상 이것을 요구한다. 방을 대기로 되돌렸다가 다시 시작하는 모양이면 준비 상태·참가자 명단이 초기화되고(`Room.end()`가 `participants`를 비우고 준비를 전부 내린다), 그 사이에 낯선 사람이 들어올 수 있다.

따라서 **`Room`은 `PLAYING`을 유지**하고, 바뀌는 것은 “이 판이 지금 어느 스테이지인가” 하나다.

### 3-2. 진행 중 `stageId`를 바꾸는 경로

여기서 [S15P21B202-487](https://ssafy.atlassian.net/browse/S15P21B202-487)에서 **일부러 닫아 둔 문**을 열어야 한다. 현재 `Room.setStageId()`는 `WAITING`에서만 통한다 — 판 도중에 맵이 바뀌면 그 뒤에 재입장한 사람만 다른 맵을 열어 **한 판에 두 개의 맵**이 생기기 때문이다.

**제안: 아무나 바꾸는 것이 아니라 전환 전용 경로 하나만 뚫는다.**

- `Room.advanceStage(다음맵)` — `PLAYING`에서만 동작하고, 호출되면 새 `GameState(다음맵)`로 갈아 끼운다.
- 요청은 **방장만** 보낼 수 있다(`STAGE_ADVANCE` 같은 새 메시지). `HOST_TAKEOVER`와 같은 판정을 쓴다.
- 갱신 시점은 **호스트가 `ServerChangeScene`을 부르기 직전**이다. 순서가 뒤집히면 3-4의 문제가 생긴다.

`setStageId`(대기 중 맵 선택)와 `advanceStage`(판 중 장 넘김)를 **이름부터 갈라 둔다.** 하나로 합치면 “진행 중 변경 금지”라는 규칙이 조건문 속에 묻혀 다음 사람이 못 본다.

☐ 다음 맵을 **누가 정하나** — 방장이 고르나, 스테이지 순서가 서버에 고정돼 있나. 2장뿐이면 고정이 단순하지만 3장이 생기면 순서표가 필요하다.

### 3-3. 체크포인트

`docs/backend-guidelines.md` §5-1이 이미 정해 뒀다:

> **체크포인트 = 스테이지 경계.** 스테이지를 클리어하면 다음 스테이지가 자동으로 체크포인트가 된다. 스테이지 중간 체크포인트는 없다.

그런데 `Room.lastCheckpoint` 필드는 **선언만 되어 있고 아무도 쓰지 않는다**(`stageId`가 그랬던 것과 같다). 장 전환이 이 필드를 처음 쓰는 자리다.

**제안**: `advanceStage()`가 새 `GameState`를 만들면서 그것을 `lastCheckpoint`에도 같이 넣는다. 전원 기절 시 되돌아갈 지점이 곧 “그 스테이지의 시작”이므로 둘이 같은 값이다.

☐ 되감기(전원 기절 → 스테이지 재시작)를 이번 범위에 넣을지. 넣지 않더라도 **필드는 이때 채워 두는 편이 낫다** — 나중에 채우려면 그 사이에 만들어진 판들은 되돌아갈 곳이 없다.

### 3-4. 전환 중 끊긴 사람과 호스트 이관

**끊긴 사람.** `AllParticipantsReady()`는 **지금 연결돼 있는** 인증된 참가자만 본다. 백엔드 30초 유예 중인 사람은 Mirror 연결 목록에 없으므로 **전환을 막지 않는다** — 이 동작은 그대로 두는 것이 맞다. 한 사람의 네트워크 사정으로 나머지가 멈추면 안 된다.

대신 **돌아왔을 때 2장으로 보내야 한다.** 재입장은 백엔드가 `GAME_STARTED`를 다시 만들어 보내는 경로를 쓰고, 거기에는 [487](https://ssafy.atlassian.net/browse/S15P21B202-487)에서 실어 둔 `stageId`가 들어간다. 그래서 **3-2의 갱신이 씬 전환보다 먼저**여야 한다. 순서가 뒤집히면 전환 도중에 돌아온 사람이 1장을 열고, 아무도 없는 맵에 혼자 서 있게 된다.

**호스트 이관.** 지금 `HostMigration`은 “게임 씬이 이미 떠 있으면 로비를 거치지 않는다”를 전제로 동작하고, 이관 중에는 `offlineScene`을 일시적으로 비워 `StopClient`가 로비를 여는 것을 막는다. 씬 전환과 이관이 **겹치는 구간**은 지금 아무도 다루지 않는다.

**제안**: 전환이 시작되면 이관을 **막지 말고 미룬다.** `EndingSceneFlow`가 `IsTransferring`으로 엔딩 중 F12를 막는 것과 같은 방식으로, 전환 중에는 이관 요청을 큐에 두고 새 씬이 뜬 뒤 처리한다.

☐ 전환 도중 **호스트가 아예 나가면** — 전환을 중단하고 남은 사람 중 새 호스트가 다시 시작하나, 아니면 이관 후 이어서 진행하나. 이관이 미뤄진 상태에서 호스트가 사라지는 것이 가장 복잡한 경우다.

<a id="section-4"></a>

## 4. 엔딩 코드를 재사용하나

**제안: 전송·합류 부분만 공용으로 빼고, 씬별 동작은 각자 둔다.**

`EndingSceneFlow`에서 장 전환과 공통인 것은 **“서버가 씬을 바꾸고, 전원이 준비될 때까지 기다렸다가, 보존된 상태를 늦게 온 사람에게도 준다”** 이 골격이다. 반대로 엔딩 고유인 것은 재생·복귀·`autoCreatePlayer` 억제다.

그대로 상속하거나 조건문을 더해 한 클래스로 만들면, **엔딩에만 맞는 기본값(플레이어를 만들지 않는다)이 2장에 새어 들어간다** — 2장에서 캐릭터가 없는 채로 로딩이 끝나는 종류의 버그는 원인을 찾기 어렵다.

☐ 공용 골격을 뽑는 리팩터링을 **2장 구현과 같은 MR에 넣을지, 먼저 뽑아 둘지.** 엔딩은 이미 출시된 경로라 건드리면 회귀 위험이 있다.

<a id="section-5"></a>

## 5. 후속 구현 단위

이 설계가 합의되면 아래로 쪼갠다. 위에서 아래로 의존한다.

1. **백엔드 — 판 중 스테이지 전이** (`advanceStage` · `STAGE_ADVANCE` 메시지 · 방장 판정 · `lastCheckpoint` 기록)
2. **클라이언트 — 전환 흐름** (`LaunchTest.Completed` 구독 → 백엔드 갱신 확인 → 호스트가 `ServerChangeScene`)
3. **새 씬에서 되살리기** (플레이어 스폰 복구 · `WorldSync` 재설치 · HUD)
4. **끊김·이관** (전환 중 이관 미루기 · 재입장자가 새 맵으로 붙는지 확인)
5. **2장 씬 스캐폴딩** — `StageCatalog`에 한 줄 추가하면 빌드 목록과 씬 검사는 따라온다([488](https://ssafy.atlassian.net/browse/S15P21B202-488))
6. **실측** — 4인에서 전환 소요 시간, 전환 중 끊김 복구

<a id="section-6"></a>

## 6. 확인이 필요한 것

- ☐ 3-2 다음 맵을 방장이 고르나, 서버가 순서로 정하나 (기획)
- ☐ 3-3 전원 기절 되감기를 이번 범위에 넣나 (기획·팀장)
- ☐ 3-4 전환 도중 호스트가 나가면 어떻게 하나
- ☐ 4 공용 골격 리팩터링을 먼저 하나
- ☐ 2장 기획이 나오면 **씬 이름**과 `stageId` 문자열을 확정한다 — `StageCatalog`와 백엔드 기본값이 같은 값을 써야 한다
