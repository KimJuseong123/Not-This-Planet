## 어떻게 드러났나

2026-09-08 아침 점검의 `🔗 머지됐는데 완료 안 된 이슈` 에 `-322` 가 올라왔다. 담당자가 시키는 대로 손으로
완료로 옮겼더니 **2초 뒤 `진행 중` 으로 되돌아왔다.**

```
10:08:47  금준영              해야 할 일 → 완료
10:08:49  Automation for Jira 완료 → 진행 중
          코멘트: "완료는 MR이 develop에 머지될 때 자동으로 처리됩니다. (자동 되돌림)"
```

R9(손으로 끈 "완료" 되돌림)에는 탈출구가 있었다 — `MR 이 있고 열린 MR 이 없으면 수동 완료를 허용`
(`development[pullrequests].all = 0 OR development[pullrequests].open > 0` 이면 되돌린다). `-322` 는
그 탈출구에 못 들어갔다. **Jira 가 이 이슈의 MR 을 아예 몰랐기 때문에** `all = 0` 이었다.

## 왜 몰랐나 — 우리 설정 문제가 아니다

같은 날 18분 차이로 같은 경로를 지나간 이웃과 하나하나 맞춰 봤다.

| | `-321` | **`-322`** | `-323` |
| --- | --- | --- | --- |
| 브랜치 이름 | `S15P21B202-321-ci-cd-map` | `S15P21B202-322-mr-title-link` | `S15P21B202-323-share-sync` |
| MR 대상 | develop | develop | develop |
| 이슈 생성 | 16:13 | 16:28 | 17:01 |
| 브랜치 커밋 | 16:21 | 16:38 | 17:11 |
| MR 생성 | 16:22:09.242 | 16:40:00.702 | 17:12:30.492 |
| **Jira 개발정보 갱신** | **16:22:09.242** | **없음** | **17:12:30.492** |
| `has-branch` 라벨 | 있음 | **없음** | 있음 |

`-321`·`-323` 은 **MR 생성 시각과 개발정보 갱신 시각이 밀리초까지 같다.** `-322` 만 그 기록이 없다.

배제한 것:

- **이슈가 늦게 생긴 것 아님** — 16:28 생성, 브랜치는 10분 뒤
- **브랜치 이름이 바뀐 것 아님** — MR `!244` 의 시스템 노트가 2건뿐이고(`!243 언급` · `커밋 언급`)
  이름 변경·force push 기록이 없다
- **스택 아님** — 셋 다 `→ develop`
- **연동이 죽은 것도 아님** — `-322` 는 커밋에서 나온 build 정보 2건을 정상 수신했다

그리고 결정적으로, **`-322` 의 전체 변경 이력이 오늘 두 줄뿐이었다** — 어제 만들어진 뒤 오늘까지
자동화 규칙이 한 번도 이 이슈를 건드리지 않았다(R1·R2·R4 전부 침묵. `Infra` 라벨은 R2 가 붙인 것이
아니라 이슈를 만들 때 넣은 값이다).

**GitLab→Jira 개발정보 동기화가 그 이벤트를 조용히 흘렸다.** 재현 조건이 없고, 담당자 경험상
한 번씩 있는 일이다. **머지 때 브랜치가 삭제되므로 다시 발생시킬 이벤트도 없다** — 재동기화로 복구할 수 없다.

## 진짜 문제는 되돌림이 아니라 손이 없었던 것

R4·R6·R5·R9 가 **모두 같은 하나의 입력**을 읽는다. 재시도도 없고 대체 입력도 없다.

| 규칙 | 이벤트가 빠지면 |
| --- | --- |
| R4 브랜치 생성 → 진행 중 | 미발동. 이슈가 `해야 할 일` 에 머물고 `has-branch` 도 없다 |
| R6 MR 머지 → 완료 | 미발동. 머지돼도 완료가 안 된다 |
| **R9 수동 완료 되돌림** | **사람의 복구를 되돌린다** |
| **R5 수동 진행 중 되돌림** | **`has-branch` 가 없으니 진행 중으로도 못 옮긴다** |

즉 **자동화가 못 옮긴 이슈를 사람도 못 옮긴다.** 문서는 "R6 하나에 기대지 않는다. 1차 안전망은
아침 점검" 이라고 적어 두었는데, 그 안전망이 부르는 담당자에게 실제로는 손이 없었다. 이 구멍은
`-322` 가 밟기 전까지 드러나지 않았다.

## 한 것 — `automation-missed` 라벨

라벨 하나로 빠져나갈 길을 만들었다. **JQL 문자열 두 개만 고쳤다** — 컴포넌트를 새로 만들지 않아
`__NEW__COMPONENT__` 기제를 쓸 필요가 없었다.

**R5**(5793968) `components[2].children[0].conditions[0]` — 이 JQL 은 if 블록의 **허용** 조건이라
선택지를 `OR` 로 더한다.

```
before: labels = has-branch OR development[commits].all > 0 OR development[pullrequests].all > 0
after : … OR labels = automation-missed
```

**R9**(5799839) `components[2]` — 이 JQL 은 **되돌림** 조건이라 예외를 `AND` 로 더한다.

```
before: development[pullrequests].all = 0 OR development[pullrequests].open > 0
after : (…) AND (labels IS EMPTY OR labels != automation-missed)
```

### `labels IS EMPTY OR` 를 빼면 가드에 구멍이 난다

Jira JQL 의 `labels != x` 는 **라벨이 하나도 없는 이슈를 맞히지 않는다.** `labels != automation-missed`
만 쓰면 라벨 없는 이슈에서 조건이 거짓이 되어 R9 가 되돌리기를 멈춘다 — 아무 태스크나 손으로
완료할 수 있게 된다. 하필 파트 라벨을 붙이는 R2 도 **같은 동기화 누락으로 안 걸릴 수 있어서**
(`-322` 가 그랬다) 라벨이 빈 이슈는 실제로 생긴다. 그래서 `IS EMPTY` 를 명시해 그때는 되돌리게 둔다.

### 왜 라벨인가

- **이슈에 남는다** — 왜 손으로 옮겼는지가 보인다
- **셀 수 있다** — `project = S15P21B202 AND labels = automation-missed ORDER BY created DESC`.
  자주 쓰이면 연동 자체를 봐야 한다는 신호다. **그래서 확인 후에도 라벨을 지우지 않는 것이 절차의 일부다**
- CI 가 Jira 상태를 쓰는 경로는 `-242` 에서 의도적으로 없앴다. 자동 복구가 아니라 사람 override 로 푸는 이유다

**대가**: 라벨이 붙어 있는 동안 **그 이슈의 R5·R9 가드는 꺼진다** — 누구든 그 이슈의 상태를 자유롭게
옮길 수 있다. 그래도 남기는 쪽을 택했다. ① 라벨을 붙이는 시점은 작업이 이미 머지돼 끝난 이슈라서
가드가 지킬 것이 없고, ② 누락 빈도를 세는 값이 그 위험보다 크다. 되살려야 하면 라벨을 떼면
그 이슈만 원래대로 돌아온다. (이 트레이드오프는 `!250` 의 AI 리뷰가 지적해 문서에 명시했다.)

라벨이 **프로젝트에서 완전히 사라지면 JQL 조건이 성립하지 않을 수 있다.** 임시 이슈 `-330` 을 지운 뒤
`project = S15P21B202 AND labels = automation-missed` 로 확인했다 — `-322` 가 들고 있어 1건 조회된다.

## 검증 (2026-09-08)

규칙 적용 — 부록 A 방식으로 두 JQL 을 `PUT`: R5·R9 모두 `PUT 200`, 다시 읽어 **새 JQL 1개 ·
옛 JQL 0개 · 상태 ENABLED** 확인. 값으로 조건을 찾아 바꿨으므로 규칙 순서가 바뀌어도 맞고,
딴 데서 바뀌었으면 0개가 되어 시끄럽게 실패한다.

가드가 살아 있는지(①)와 override 가 통하는지(②)를 **둘 다** 봐야 한다 — override 를 잘못 쓰면
가드가 통째로 열려 아무 태스크나 손으로 완료할 수 있게 된다.

| # | 대상 | 한 일 | 결과 |
| --- | --- | --- | --- |
| ② | `-322` (라벨 있음) | 10:25:03 `진행 중 → 완료` | **유지** — 45초 뒤에도 되돌림 없음 |
| ① | `-330` (라벨·브랜치·MR 없음) | 10:27:17 `→ 진행 중` | **되돌림** — 10:27:20 R5 가 `해야 할 일` 로 (3초) |
| ① | `-330` (라벨 없음) | 10:28:38 `→ 완료` | **되돌림** — 10:28:40 R9 가 `진행 중` 으로 (2초) |
| ② | `-330` (라벨 붙인 뒤) | 10:30:01 `→ 완료` | **유지** — 45초 뒤에도 되돌림 없음 |

①의 두 줄과 ②의 마지막 줄은 **같은 이슈**이고 그 사이에 바꾼 것이 라벨 하나뿐이므로, 차이를 만든 것이 라벨임이 갈린다.
임시 이슈 `-330` 은 확인 뒤 삭제했다(`-93`·`-207`·`-208` 과 같은 관행).

오프라인 CI 테스트는 전후 모두 **통과 28 · 실패 1**로 같다. 그 하나(`test_doc_drift.py`)는 내가
건드리지 않은 기존 실패이고 대기 중인 `-325` 커밋에 이미 고쳐져 있다.

## 부수적으로 고친 것 — `dump_rule.py` 가 규칙을 0개로 읽었다

목록 조회가 `total=10` 을 돌려주는데 스크립트는 0건으로 읽고 있었다. 응답의 항목이 **`values`** 에
오는데 `data`/`rules` 로만 찾고 있었다(최상위 키: `limit`·`links`·`offset`·`total`·`values`).
`--name` 으로 규칙을 못 찾던 증상의 원인이 이것이었다 — 전에는 `systemLabelId` 필터 탓으로 짐작했는데
그쪽이 아니었다.

## 남은 것

- **근본 원인(동기화 누락)은 우리가 고칠 수 없다.** 라벨 사용 횟수를 세다가 잦아지면 GitLab for Jira
  연동 자체를 팀장과 함께 봐야 한다 — 지금은 표본 1건이다
- R9 의 **다른** 빈틈은 그대로다: `development[pullrequests].open > 0` 이 **대상 브랜치가 그 이슈의
  브랜치인 남의 MR** 까지 세어, 스택 자식이 열려 있는 동안 부모를 완료로 못 옮긴다(`-199`).
  이번 건은 `all = 0` 쪽이라 별개다. 이제는 그것도 `automation-missed` 로 빠져나갈 수 있다
- 워크플로우 전환 자체를 제한하는 방안(문서 §3)은 여전히 미적용이다. 적용하면 R5·R9 는 안전망으로 남는다
