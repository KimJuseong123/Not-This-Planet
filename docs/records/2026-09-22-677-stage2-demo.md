## Player flow

`Stage2Bootstrap` defaults to demo mode. The server waits for authenticated connections to be scene-ready with player bodies. The existing Stage1 ending/arrival still enters `Stage2_Earth` through `EndingSceneFlow`.

1. Allow movement, jumping and looking for 3 seconds. Yard interactions, grabbing and tools are unavailable.
2. Spend 6 seconds surveying the launch yard with an orbiting camera.
3. Show three 6-second assembly demonstrations: open the container, lift/transfer/lower the rocket section, move crew toward the work ladder, animate wrench tightening and highlight bolts. Crew use the connected players' appearance data; offline play uses the local appearance.
4. Show the assembled rocket for 3 seconds, including a 1-second fade.
5. Hold `-- 데모 완 --` with a thank-you message and an ESC/menu hint. Do not resume Stage2 gameplay or automatically advance to another stage.

Total: approximately 30 seconds from the shared start to the final card. ESC/settings stay available throughout and the existing menu returns to the lobby.

## Integration and regression controls

- `Stage2State.DemoStart/DemoStarted/DemoPlayers` ride existing yard snapshots. Late arrivals seek the current presentation instead of restarting a local cutscene; the cast is frozen in server player-ID order at the start, so late viewers see the same crew.
- `GameSession.CinematicInputBlocked` includes the Stage2 demo and is already enforced by server-side `NetPlayer`. Closing a pause menu therefore cannot release the cinematic lock.
- The initial movement-only filter also runs on server input, retaining sequence/aim metadata.
- `Stage2Yard` rejects demo puzzle commands and stops authoritative yard simulation. The visual assembly never marks a part secured, invokes `Completed`, sets `Launched`, or records a gameplay clear.
- Presentation dolls have kinematic bodies, disabled colliders and disabled behaviours; they do not receive network identities or player input. Live player renderers are hidden locally and restored with the previous camera/HUD state when the view is removed.
- Network disconnect does not grant a former client solo yard authority or switch the cinematic to an unrelated process-local clock. Host migration, packet loss and backend lobby integration still require their own environment validation.
- The serialized `Stage2Bootstrap._demoMode` defaults to true without scene rewiring. `ConfigureDemo(false)` allows explicit authoring/test use of the retained full yard simulation; existing yard fixtures opt out before entering Play Mode. The network smoke harness likewise opts out except for its new demo scenario.

### Fixed: AI-to-human body handoff exception

The first three-peer run passed the timeline assertions but host logs exposed two real `NullReferenceException`s in `NetPlayer.AttachTransport`, immediately preceded by `Can't add TractorBeamController ... already added`. Evidence is preserved under `network-before-handoff-fix/`.

`TeamSeats` hands the same body from an AI to a human in the same frame. Previously `RemoveBody` scheduled the controller for deferred destruction, and `AttachTransport` attempted to add another component before that destruction finished. `DisallowMultipleComponent` rejected the add and the following `Configure` dereferenced null.

The controller now lives with its pooled body. Releasing an owner still calls `ReleaseForRespawn` to clear rider/input state, then disables the controller; the next owner reuses and re-enables it. Nonpooled body destruction stays unchanged. The final build and three-peer rerun reproduce the same handoffs without either error, and the 22-test targeted regression run passes. The smoke script now fails on such runtime logs even if its timeline assertions pass.

### Existing Stage1 test mismatches

Four failures are outside the changed Stage2 behaviour. Their test and production source files are unchanged from the base commit:

- `Stage1CutsceneTests.ActualWorldSurvivesBothCutscenesAndRestoresCamera` (line 221): waits for a volley after walking into `Stage1AssaultTrigger`. That component is now a serialization-only marker; `Stage1Sequence` starts assault on the first released clamp. The test's old trigger never starts the volley.
- Three `SerializedAssaultMultiplierControlsInterval` cases (line 148): expect an initial interval of 30 seconds, while the current `MeteorSpawner.IntervalAt` uses the newer wave-band policy and returns 10. The test still expects the old multiplier policy.

These are identified from unchanged base source and the regression failure traces, not from a second full pristine-baseline Editor run. They are left visible rather than disabling tests or changing unrelated Stage1 gameplay.
