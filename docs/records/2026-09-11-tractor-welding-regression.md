# 견인 엔진의 용접·조립 판정 복구

## 조사 범위와 원인

- Unity 6000.5.4f1, Mirror 서버 권한 구조. 작업 시작 시 Git 변경 사항 없음.
- `Part_1`은 고정못 4개가 모두 해제되면 `Locked → Free`로 전환되고 `PartTractorActivator`가 견인 기능을 붙인다.
- 수정 전에는 이때 `SpaceshipPart`와 모든 `PartSocket`을 끄고 새 몸체를 `Prop` 레이어로 만들었다. `WeldBead`의 `PartMask` 탐색에서 제외되므로 하차하기 전부터 용접할 수 없었다.
- 소켓 비활성화는 `ShipAssembly.FindEngine`의 엔진 탐색도 차단했다. 소켓만 복구해도 Free 상태의 엔진은 적층을 받을 수 없었고, 견인 빔용 루트가 아래를 향하므로 기존 루트 up 방향 검사에서 90도 기울어진 엔진으로 판정됐다.
- 하차 자체는 파츠 상태나 레이어를 바꾸지 않는다. 탑승·하차가 초기 전환 시 이미 잃은 판정을 복구하지 못했던 것이다.
- 호스트 입력과 비호스트 입력은 서버 `NetPlayer.FixedUpdate → TractorBeamController.SetInput`의 동일한 탑승·하차 처리를 거친다. 비호스트의 고정못 복원은 `WorldSync → PartClamp.ApplyNetworkState → Release`를 통해 같은 활성화 코드를 실행한다. 용접 RPC도 양쪽에서 같은 `WeldBead.TryGrowNear`를 사용하므로 레이어 오류의 영향은 공통이다.

## 수정 내용

- 견인 엔진은 파츠 컴포넌트·조립 소켓·Part 몸체 레이어를 유지한다. 기존 중복 몸체 충돌, 밀기, 손잡이만 비활성화한다.
- 소켓을 실제 외형과 같은 좌표계로 옮겨 몸체의 위치·회전을 따라가게 했다.
- 비어 있는 Free 상태 견인 엔진에 상위 파츠를 조립할 수 있게 했다. 일반 Free 파츠의 조립 규칙은 유지한다.
- 조립 및 발사 기울기는 실제 몸체의 위쪽 방향으로 계산한다.
- 용접 질량 갱신이나 권한 복원 시 일반 파츠 물리가 견인 물리를 덮어쓰지 않게 했다. 원격 복제본은 kinematic을 유지한다.
- Part 레이어가 복구된 엔진을 자기 견인 빔으로 잡는 것을 방지한다.
- 발사 순서, 용접 강도 및 붕괴 판정은 우회하지 않는다. 정상 조립·용접으로 성공 상태에 도달하는 경로를 복구한다.

## 실행 검증

동일한 코드·패키지·프로젝트 설정을 복사한 독립 Unity 프로젝트에서 EditMode 테스트를 실행했다. 수정 전 비교는 런타임 소스만 HEAD 버전으로 교체하고 동일한 테스트를 실행했다.

| 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 고정못 전부 해제 후 소켓 유지 | 실패 | 통과 |
| 서버 해제 경로의 용접·자기 견인 방지·질량 갱신 | 실패 | 통과 |
| 클라이언트 고정못 상태 복원 경로의 용접·kinematic 유지 | 실패 | 통과 |
| 미탑승 / 1회 탑승 / 다른 탑승자로 교대 후 용접·조립·발사 시작 | 3개 실패 | 3개 통과 |
| 견인 엔진을 포함한 4층 용접 탑의 물리 하중 시험 및 `LaunchState.Success` 도달 | 실패: 2층 조립 후보 없음 | 통과 |
| 용접·견인·하차·적층·우주선 탑승·발사 관련 전체 선택 테스트 | 127개 중 118 통과 / 9 실패 | 127개 중 125 통과 / 2 실패 |

남은 두 실패는 동일한 검증 환경의 수정 전 코드에서도 재현되었다:

- `PartTractorActivatorTests.ActivatedPart1_IsRegisteredAsTransportInteractionTarget`: 기존 포커스 테스트에서 대상이 null.
- `LaunchTestTests.FailedLaunch_LeavesSomeJointsIntact`: 붕괴 후 일부 접합이 남아야 하는 검사에서 남은 접합이 0.

새로 추가한 회귀 테스트 6개는 모두 통과했다. 수정 후 Unity 스크립트 컴파일 오류는 없었다. 전체 씬·시각 리소스를 포함하지 않는 코드 중심의 검증 환경이므로 위 두 기존 실패를 실제 게임 환경의 원인까지 확정한 것은 아니다.

로컬 실행 기록: `.local-validation/tractor-baseline-suite.xml`, `.local-validation/tractor-after.xml` 및 같은 이름의 로그. 검증용 프로젝트: `outputs/tractor-tests` (Git 제외).

## 실제 두 피어에서 남은 확인 절차

이번 검증은 실제 네트워크 패킷을 교환하는 두 플레이어 세션을 실행한 결과가 아니다. 서버 경로와 원격 복원 경로를 각각 검사한 결과다.

1. 호스트와 비호스트가 같은 Main 씬에 접속한다. 고정못을 하나씩 제거하며 3개까지는 Locked, 4개째에 Free 및 견인 활성화가 되는지 양쪽에서 확인한다.
2. 탑승 전 몸체에 비드를 만들고 양쪽에 보이는지 확인한다.
3. 호스트가 탑승·이동·하차한 뒤 두 플레이어가 각각 용접한다. 같은 절차를 비호스트 탑승과 호스트→비호스트 교대에도 반복한다.
4. 견인 엔진을 발사 구역에 놓고 2~4층을 적층·용접한다. 양쪽에서 엔진 및 층별 상태가 인식되는지 확인한다.
5. 모든 플레이어가 우주선에 탑승하고 카운트다운, 하중 시험, 상승, 게임 종료 연출까지 양쪽에서 확인한다.
6. 견인 활성화 후 재접속한 복제본에서도 소켓·비드·몸체 위치가 유지되는지 확인한다.
