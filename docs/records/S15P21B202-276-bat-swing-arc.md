# S15P21B202-276 방망이 타격을 눈으로 납득할 수 있게 궤적을 만든다

## 재확인 결과 — 판정은 고칠 것이 없었다

S15P21B202-274 로 운석이 대각선으로 오게 한 뒤 방망이 판정을 확인했다.
`MeteorBat.FindTarget` 은 운석의 현재 위치를 보지 않고 **예측 착탄 지점**을 본다.

```csharp
if (!meteor.TryPredictImpact(out var seconds, out var point)) continue;
if (seconds > PhysicsScale.BatSwingWindowSeconds) continue;

var offset = point - origin;   // 낙하 지점까지의 거리를 수평으로
offset.y = 0f;
if (offset.magnitude > PhysicsScale.BatAssistRadius) continue;
```

대각선이 되어도 예측 지점은 변하지 않으므로 판정이 영향을 받지 않는다. 조준 방향을
보지 않는 것도 §18.2 "반사 방향은 플레이어 **카메라**의 수평 방향" 이라 의도대로다.

측정으로 확인했고, 대각선에서 깨지지 않는다는 것을 `BatSwingArcTests` 앞부분 6개로
잠갔다. **대각선 운석은 스포너를 거치지 않고 직접 만든다** — 그러면 274 가 머지되기
전에도 이 검증이 성립하고, 판정이 낙하 경로와 무관하다는 것 자체를 보여준다.

## 대신 §18.1 의 마지막 줄이 지켜지지 않았다

> 실제 방망이 메시가 운석과 정확히 닿지 않아도 **넓은 에너지 궤적으로 판정을
> 납득시킨다.**

코드에는 그 문장이 주석으로 적혀 있었지만 실제로 나오던 것은 **파티클 세 개**였다.

```csharp
// 궤적. 기획 §18.1 "넓은 에너지 궤적으로 판정을 납득시킨다".
Puff.Thruster(origin, direction);      // 0.05~0.09m 파티클 3개
...
Puff.Thruster(point, direction);       // 운석 자리에 3개 더
```

타격 순간(착탄 1초 전) 운석의 위치를 계산하면 이렇다.

| | 수직 | 대각선 50도 |
|---|---|---|
| 수평 거리 | 0m | 8.4m |
| 높이 | 12.8m | 12.8m |
| 방망이에서 | 12.8m | **약 15m** |

두 파티클 무리 사이에 아무것도 없다. 플레이어는 **허공을 휘두르는데 15m 위의 운석이
날아가는** 것을 본다.

**이것은 274 의 회귀가 아니다.** 수직 낙하에서도 그 순간 운석은 12.8m 위였다 — 이
기믹은 **처음부터 물리적 접촉이 아니었고**(§18.1 이 그렇게 정했다), 274 가 그것을
눈에 보이게 만들었을 뿐이다.

## 고친 것

### ① 스윙 궤적 — 판정과 같은 함수에서 나온다

```csharp
var t = Mathf.Lerp(tail, head, i / (float)(count - 1));
into[i] = origin + MeteorBat.SwingAim(aim, t) * PhysicsScale.BatArcRadius;
```

`MeteorBat.SwingAim` 은 S15P21B202-261 이 우타자 스윙을 만들 때 쓴 함수다. 궤적이
**같은 함수**에서 나오므로 동작과 어긋날 수 없다.

**지나온 만큼만 그린다.** 앞으로 갈 곳까지 그리면 아직 휘두르지 않은 자리가 빛나고,
맞는 순간이 어디인지 읽히지 않는다.

### ② 방망이에서 운석까지 줄기를 잇는다

판정이 "닿지 않아도 된다" 이므로 **연출이 그 간극을 메워야 한다.** 맞은 자리까지 선을
0.18초 남긴다 — 짧아야 한다. 쳐낸 운석이 날아가는 것이 가장 강한 피드백이므로 그것을
가리면 안 된다.

헛스윙에는 줄기가 없다. 둘이 같아 보이면 대기 1초 동안 클릭이 안 먹히는 이유를 알 수
없다.

### ③ 떨어지는 운석에 꼬리를 붙인다

**대각선 낙하가 예고 없는 피격을 만들었다.** 274 의 경로 검사는 결정성을 위해 동적
물체를 막힘으로 세지 않으므로, 대각선 경로에 서 있으면 **원에서 8m 떨어진 곳에서**
남의 운석에 맞는다 — §17.2 의 "원이 어디 떨어질지 알려준다" 는 계약과 어긋난다.

`TrailRenderer` 0.45초면 대각선 13.1m/s 에서 약 6m 꼬리가 되어, 옆에서 오는 것이
읽힌다.

| 방법 | 판단 |
|---|---|
| 낙하 궤적에 꼬리를 붙인다 | **이것을 썼다.** 274 의 "진짜 운석 느낌" 과 같은 방향이고, ① 의 작업과 겹친다 |
| 떨어지는 운석을 착탄 전까지 무해하게 | §19 "충돌 순간에만 넉백과 기절" 을 어기고, §18.2 의 반사 운석 피해와도 어긋난다 |
| 경로 검사에 플레이어를 넣는다 | 274 의 결정성이 깨지고, 스폰 시점 검사라 이후 움직이면 무의미하다 |

꼬리를 붙여도 플레이로 보고 불공정하면 두 번째를 다시 검토한다.

## 그리는 쪽을 별도 컴포넌트로 만들지 않았다

**S15P21B202-275 의 교훈이다.** `MeteorWarningView` 를 아무도 만들지 않아 세 이슈가
죽어 있었다. 방망이는 이미 세계에 있고 이미 `ShowSwing` 을 부르므로, 그 안에서 그리면
**붙이는 것을 잊을 자리가 없다.**

규칙만 `BatSwingLook` 으로 뗐다 — 렌더러를 세우지 않고도 잠글 수 있고, [Art] 가 실제
VFX 로 바꾸면 `MeteorBat.EnsureTrails` 만 바뀐다.

머티리얼은 **공유한다.** 궤적 색이 매 프레임 변하지 않으므로 나눌 이유가 없다 —
`MeteorWarningView` 가 표시마다 따로 갖는 것과 반대인데, 그쪽은 색이 매 프레임
변하기 때문이다. 운석 꼬리도 같은 이유로 하나를 공유한다(§19 의 기준이 20분에
150~200개다).

꼬리는 **자식에 붙였다.** 운석 본체에 붙이면 `GetComponent<Renderer>()` 가 꼬리를
집어, 크기·재질을 다루는 기존 코드가 엉뚱한 것을 만진다.

## 검증

```
develop : 647개 중 630 통과 / 17 실패
276     : 662개 중 645 통과 / 17 실패

276 에서만 실패 : 없음
```

새 `BatSwingArcTests` 15개 포함, 방망이 4개 스위트 **60개 전부 통과.** 17개는 모두
develop 것이다(S15P21B202-232 건).

`Meteor.TrailsEnabled` 를 뒀다 — `Puff.Enabled` 와 같은 자리이고, 검증이 수백 개의
운석을 만들므로 연출을 끌 수단이 필요하다.

### 검증 하나를 잘못 재서 고쳤다

`TheArcIsWide` 를 처음에 **현의 길이**로 재서 통과할 수 없는 검증을 만들었다. 호의
현은 각도가 180도를 넘기 전까지 늘 반지름보다 짧을 수 있으므로, 넓은 궤적도 "좁다"
로 나온다. **각도로 재는 것이 맞다** — 맞는 순간의 궤적은 110도를 훑는다.

S15P21B202-261 에서 스윙 각도를 `Vector3.Dot` 으로 재서 pitch 와 yaw 를 섞었던 것과
같은 종류의 실수다.

## 남은 것

- **E** 플라즈마 용접 건 빔이 노즐 끝에서 나가게
- 꼬리를 붙여도 예고 없는 공중 피격이 불공정하면 "착탄 전까지 무해" 를 재검토한다

**[Art] 와 겹칠 수 있다.** 팀 계획에 "VFX 추가" 가 있는데 에너지 궤적은 전형적인 VFX
작업이다. `LineRenderer` 로 만든 이 표현은 [Art] 가 실제 VFX 를 주면 버려질 수 있다 —
`BatSwingLook` 의 규칙은 그대로 살고 `EnsureTrails` 만 바뀌게 나눠 두었다.
