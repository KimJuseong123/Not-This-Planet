# 발사 실패 시 공중 분리와 낙하 (S15P21B202-340)

[문서 안내](../README.md) → [작업 기록](README.md) → 조립·용접·발사

발사 실패 순간 추력이 바로 사라져 우주선이 주저앉던 동작을 수정했습니다. 분리 후 낙하 연출과 기존 ShipHatch·낙하 규칙의 관계, 검증을 기록합니다.

본문의 “현재”, 검증 수치, 미완료 항목은 **기록 당시 기준**입니다. 후속 변경은 관련 이슈와 [주제별 색인](README.md)을 함께 확인합니다.

## 왜 "터진다" 가 아니라 "주저앉는다" 로 보였나

```csharp
// LaunchTest.Tick 첫 줄
if (State != LaunchState.Ramping) return;
...
    Fail("접합부가 하중을 버티지 못했다");
    return;
```

`Fail()`은 `FailureReason`과 `State`만 바꾼다. 그러면 다음 스텝부터 `Tick`이 첫
줄에서 돌아나가므로 **추력이 그 프레임에 사라진다.** 엔진이 꺼진 우주선은 공중에서
그냥 멈춰 떨어진다.

끊어질 때 우주선은 **이미 공중에 있다.** 추력이 무게의 3.2배라 출력 31%(램프 5초의 약
1.6초)에서 무게를 이기고, 접합은 그보다 높은 출력에서 끊어진다. 그래서 추력만 잠깐
남기면 위쪽이 떨어져 나가는 것이 보인다.

## 변경 내용

`LaunchState`에 `Breaking`을 넣어 `Ramping`과 `Failed` 사이를 만들었다.

```
Ramping → (접합부 파손) → Breaking (1.4초, 추력 남음) → Failed
```

- 봉인하지 않는다 — 남은 접합에 하중이 몰려 **연쇄로 끊어지는 것이 연출이다**(§22.4)
- 시간 상한이 지나면 **반드시** `Failed`로 간다
- 엔진이 사라져도 `Failed`로 간다

### 발사 전 실패는 그대로 즉시 실패다

`Fail()`을 부르는 자리가 여섯 군데인데 성격이 다르다. **접합부 파손만** 새 경로를
탄다.

| 호출 지점 | Breaking | 이유 |
|---|---|---|
| `Begin` — 최하단 파츠·Rigidbody 없음 | 아니오 | 추력을 준 적이 없다 |
| `Begin` — 자기 무게로 서 있지 못한다(12도) | 아니오 | §22.3 이 "추력을 주기 전에" 확인한다고 정했다 |
| `Tick` — 최하단 파츠가 사라졌다 | 아니오 | 밀 대상이 없다 |
| **`Tick` — 접합부가 하중을 버티지 못했다** | **예** | 이것만이 공중에서 일어난다 |
| `Ascend` — 상승 중 최하단 파츠 소실 | 아니오 | 이미 성공 이후다 |

### 추력을 램프 값 그대로 쓰면 안 됐다

**처음에는 끊어진 순간의 `Output`으로 계속 밀었다. 틀렸다.**

램프 추력은 탑 전체(약 2,000kg) 기준이다. 최하단 접합이 끊어져 엔진(약 500kg)만
남으면 **자기 무게의 12.8배**를 받는다 — 1.4초면 +46m/s, +32m 로 **화면 밖으로
날아간다.**

남은 덩어리의 무게 대비 1.2배로 묶었다.

```csharp
var weight = _engine.mass * Mathf.Abs(UnityEngine.Physics.gravity.y);
var thrust = weight * PhysicsScale.LaunchBreakupThrustRatio;
```

**잠깐 버티다 함께 무너진다.** 연출의 주역은 엔진이 도망가는 것이 아니라 **위쪽이
떨어져 나가는 것**이고, §22.4 도 카메라가 최상단 모듈을 따라간다고 정했다.

노즐 위치(`LaunchNozzleDrop`)는 그대로라 **토크는 계속 걸린다** — 비뚤어진 덩어리가
돌며 무너지는 것이 남는다.

## `ShipHatch` 는 변경하지 않았다 — 한 번 고쳤다가 되돌렸다

`WatchLaunch`가 `Failed` 하나만 본다. 처음에는 `Breaking`도 실패 진행으로 보게
고쳤다. **되돌렸다.**

`Breaking`을 실패 진행으로 보면 모듈이 그 사이에 착지해 **사출이 먼저 일어나고**,
`ShipHatch`의 기존 주석이 말하는 "접합부가 터진 뒤 모듈이 떨어지는 동안은 타고 있어야
한다. 그 낙하가 실패의 연출이다" 가 짧아진다.

`Failed`부터 착지를 보는 지금 규칙이 그 연출을 온전히 남긴다. 근거만 주석으로 적었다.

**갇히지 않는다.** `Breaking`은 어떤 경로로도 `Failed`에 도달하므로 §22.4 의 사출이
반드시 온다 — 검증 세 개가 그 동작을 검증한다.

## 낙하 규칙이 전제였다 (S15P21B202-334)

§22.4 가 "플레이어는 날아가고 잠시 구르지만 **기절하지 않고 자동으로 일어난다**" 를
요구한다. 334 가 낙하를 피해에서 자세로 바꿨으므로 이제 성립한다. 그 전이었다면
공중에서 부서져 떨어지는 것이 곧 기절이었다.

## 검증

새 `LaunchBreakupTests` 10개.

```
develop : 786개 중 759 통과 / 27 실패
340     : 796개 중 769 통과 / 27 실패

340 에서만 실패 : 없음
```

### 2층으로는 재현되지 않았다

처음 하니스를 2층 스택으로 만들었더니 **용접을 아예 안 해도 통과했다.** 최하단 접합이
위 파츠 하나(약 500kg)만 지므로 하중이 `UnweldedBreakForce`(8,000N)에 못 미친다.
S15P21B202-331 의 측정이 4층에서 용접률 0% 가 파손된다는 것을 보였으므로 4층으로
바꿨다.

### 내 검증의 측정이 한 번 틀렸다

`ThrustKeepsPushingWhileBreaking`을 처음에 **"엔진 속도가 오른다"**로 썼다. 추력을
무게 대비 1.2배로 묶은 뒤에는 틀린 척도다 — 아래 접합이 붙어 있으면 엔진이 그만큼을
함께 지므로 오히려 느려진다.

**"자유낙하보다 덜 떨어지는가"**가 추력의 존재를 보는 정확한 척도다.

```csharp
var freeFall = before - Mathf.Abs(UnityEngine.Physics.gravity.y) * Span;
Assert.Greater(engine.linearVelocity.y, freeFall, ...);
```

S15P21B202-261(스윙 각도를 `Dot`으로 재서 pitch·yaw 혼동) · 276(호의 현으로 "넓음"
측정)과 같은 종류의 실수다. **검증이 검사가 실패하면 코드가 틀렸다고 먼저 단정하지 않는다.**

### 기존 검증 하나의 시간 예산을 늘렸다

`ShipRideTests.Failure_KeepsThePlayerAboardUntilTheModuleLands`가 400스텝(8초)만
돌렸다. 접합이 끊어진 뒤 `LaunchBreakupSeconds` 만큼 추력이 남아 착지까지 그만큼 더
걸리므로 700스텝으로 늘렸다. **검증의 뜻은 그대로다** — 착지하면 수습으로 넘어간다.

## 남은 작업

- **인게임 확인이 필수다.** 연출이라 눈으로만 판단된다. 층당 0.4m 어긋난 탑이나
  용접이 부족한 탑을 발사해 **공중에서 부서지며 떨어지는지** 봐야 한다
- **`LaunchBreakupSeconds`(1.4초)와 `LaunchBreakupThrustRatio`(1.2)는 플레이로 조정할
  값이다.** 짧으면 여전히 주저앉아 보이고, 추력비가 크면 엔진이 날아간다
- **카메라가 최상단 모듈을 추적하는 것**(§22.4)은 별건이다. 지금 어떻게 되어 있는지
  확인하지 않았다
- 태블릿이 앞단 차단 이유를 알려주는 것 — S15P21B202-331 이 근거를 남겼고 별건이다
