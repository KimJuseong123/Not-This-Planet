# S15P21B202-679 · 안내 표시를 한 문법으로

> "텍스트나 알림표시 이런 식으로 통일하는걸로 하자. 키가 들어가는 곳은 마우스 모양
> 대신 `[E]` 이런 식으로."

## 화면에 안내 문법이 셋이었다

| 어디 | 어떻게 생겼나 |
|---|---|
| 왼쪽 아래 키 안내 | 패널 + **네모 키캡**, 키는 `TAB` |
| 크로스헤드 아래 상호작용 안내 | 패널(모서리 표식 + 렌즈), 키는 `[E]` |
| 크로스헤드 아래 상황 안내 | 같은 패널 — **읽기만 하면 되는 줄인데 눌러야 할 것처럼 보였다** |
| 태블릿 | 네모 점 줄 **과** 글자 점 줄, **둘이 서로 다른 쪽을 가리켰다** |

## 무엇을 기준으로 갈랐나

**테두리의 있고 없음이 "누르라"와 "읽으라"를 가른다.**

* 키를 누르라는 것 → 둥근 청록 테두리 안에 `[E]  잡기` (`UiTheme.DrawPrompt`)
* 읽기만 하면 되는 것 → **바탕 없이 글자만.** 대신 둘레에 검은 테를 두른다

한쪽 그림자(`L`)로는 모래 지면 위에서 글자가 사라진다. 여덟 방향으로 두른다
(`LOutline`).

`DrawPrompt` 는 `DrawPanel` 과 달리 **모서리 표식도 렌즈도 없다.** 그것은 창의
장식이라, 한 줄짜리 안내에 붙이면 열어 볼 것처럼 보인다.

키는 전부 `[E]` 꼴이고, 글자는 `TabletHelpContent.Name` 을 거친다 — **태블릿과 같은
이름이 나온다.** 손으로 적으면 키를 바꾼 사람에게 거짓말이 된다(S15P21B202-657 이
고친 것이 정확히 그것이다). 왼쪽 아래만 대문자(`TAB`)였던 것도 여기서 없어진다.
`Alpha1` 처럼 KeyCode 의 이름이 키캡의 글자와 다른 것도 한 곳에서 처리한다.

## 태블릿 — 같은 것을 두 번, 그것도 다르게 말하고 있었다

**쪽 표시가 둘이었다.** 네모 점 4개(`pageDots`)와 글자 점 8개(`guideKeys`)다.

그리고 **글자 점 줄이 거짓말을 하고 있었다.**

```csharp
// 예전 Stage1TabletScreen.Guide.cs
guideKeys.text = TabletHelpContent.PageDots(true, guide.Page) + ...
//                                          ^^^^ 늘 참
```

안내를 빠져나와 조작 안내를 넘겨도 **불이 안내 칸에 머물렀다.** 관측된 증상이
그것이다 — "오른쪽으로 가는데 오른쪽 불이 안 들어온다". 옆의 네모 점은 제대로
움직였으니, 화면에 서로 다른 말을 하는 표시가 둘 있었던 셈이다.

네모 점 줄을 지우고, 어느 칸에 불이 들어오는지를 `TabletHelpContent.PageStrip`
**한 곳에서** 정한다. 화면은 상태만 넘긴다.

**657 이 넣은 `footer` 라벨은 화면에 나온 적이 한 번도 없다.** 만들 때
`SetActive(false)` 하고 다시 켜지 않았다 — 내가 657 에서 넣은 쪽 표시가 거기
갇혀 있었다. 지웠다.

전체 화면 태블릿(`Stage1ExplorationHud`)도 네모 점 줄을 쓰고 있었다. 같은 한 줄로
바꿨다.

## 말

**"줍기" → "잡기".** 줍기는 집어서 주머니에 넣는 말로 읽힌다. 실제로는 손으로 쥐고,
놓으면 떨어진다.

## 지나가다 막은 것 — 네모가 뜰 수 있었다

665·669 가 넣은 안내 글자가 **폰트 요청 목록에 없었다.** 657 이 같은 함정에 한 번
걸렸고 기록에도 적어 뒀는데, 그 뒤에 넣은 두 이슈가 그대로 빠뜨렸다. 안내를
만드는 쪽이 제 글자를 내놓게 하고(`OnboardingNotices.AppendGlyphs` ·
`GameHud.AppendPromptGlyphs`), 검사로 잠갔다.

## 검증

화면 없이 재도록 결정을 순수 함수로 꺼냈다 — `GameHud.PromptFor` 와
`TabletHelpContent.PageStrip`. **틀렸던 것이 "어떤 값을 넘기느냐" 였기 때문에**,
넘기는 쪽이 아니라 정하는 쪽을 재야 잡힌다.

| 무엇을 지키나 |
|---|
| 모든 안내의 키가 `[E]` 꼴이다 |
| 키 이름이 태블릿과 같다 |
| **키를 바꾸면 안내도 바뀐다** |
| 숫자 키가 `Alpha1` 이 아니라 `1` 로 적힌다 |
| 줍기 줄이 **"잡기"** 라고 적혀 있다 |
| 끼임이 다른 모든 안내보다 앞선다 |
| 도구를 들고 있으면 줍기 안내가 안 뜬다 |
| **안내를 나오면 불이 안내 칸을 벗어난다** |
| **오른쪽으로 넘길 때마다 불이 오른쪽으로 간다** |
| 불이 하나고, 점 개수가 쪽 수와 같다 |
| 쪽 번호가 범위를 벗어나도 끝 칸에 머문다 |
| 안내의 모든 글자가 폰트 목록에 있다 |

`HudNoticeStyleTests` 13건 신규. 관련 스위트 합쳐 116건 중 실패 4건은 **전부
`Stage1CutsceneTests` 이고 develop 에서도 같은 4건이 실패한다** — 따로 기준선을
돌려 이름까지 맞춰 확인했다.

## 고친 검사 하나

`KeyGuideHolderTests` 가 `"TAB"` · `"MOUSE4"` 를 잠그고 있었다. **이 이슈가 일부러
바꾼 바로 그것**이라(태블릿과 같은 이름을 쓴다), 기대값을 고쳐 적고 왜 바뀌었는지
클래스 주석에 남겼다.

## 남은 것

* **실제 화면에서의 읽힘** — 밝은 모래 위에서 바탕 없는 안내가 충분히 읽히는지는
  사람이 봐야 한다. 안 되면 글자색을 흰색으로 올리거나 테를 굵히는 선에서 끝난다
* 운석 타격 표시(`GameHud.MeteorRhythm`)는 그대로 뒀다 — 읽는 안내가 아니라 타이밍
  게이지라 창처럼 보이는 것이 맞다
