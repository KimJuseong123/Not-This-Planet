# 플레이 데이터 파이프라인 계획

[문서 안내](README.md) → **플레이 데이터 파이프라인**

> **아직 만들지 않은 것의 계획입니다.** 지금 있는 것은 §1 에 적었고, 나머지는 제안입니다. 구현하면서 결정이 바뀌면 이 문서를 고칩니다.

플레이 데이터를 자동으로 모아 중앙 서버에서 분석할 수 있는 토대를 만듭니다.

## 1. 지금 무엇이 있고, 무엇이 없나

| 있는 것 | 어디 |
| --- | --- |
| 실행마다 평문 로그 파일 (8 MB 상한 · 30개 보관) | `RunLog.cs` → 빌드 폴더 `logs/` |
| **다음 실행 시작 때** 지난 판 로그를 업로드 | `RunLogUpload.cs` → `POST /logs` |
| 게스트 토큰 인증 · 크기·빈도·디스크 상한 | `RunLogController.java` · `RunLogStore.java` |
| 날짜 폴더 저장 + 보관 기간 회수 | `/var/log/metagame-runlogs/<날짜>/` |
| 기기별로 안정된 사용자 번호 | `AuthService.guestLogin()` — `deviceId` 로 찾고 없으면 만든다 |

**없는 것이 더 중요합니다.**

- **구조화된 이벤트가 없습니다.** 지금 모이는 것은 사람이 읽는 평문 로그입니다. *"파트를 몇 개째에서 포기하나"* 를 물으려면 로그를 파싱해야 하고, 파싱 규칙은 로그 문구가 바뀔 때마다 깨집니다.
- **한 판이 저장되지 않습니다.** `Room`·`RoomPlayer`·`GameState` 는 **메모리에만** 있습니다. JPA 저장소는 `UserRepository` 하나뿐이고, 엔티티는 `User` 하나뿐입니다. 서버는 어제 몇 판이 돌았는지 모릅니다.
- **수집 경로가 한 번도 성공한 적이 없습니다.** 2026-09-15 실측 — 배포 서버의 `/var/log/metagame-runlogs` 에 **파일 0개**입니다. 원인 둘(`-501` 헤더 비ASCII · `-507` 런처가 로그를 지움)을 각각 고쳤고, `-507` 은 배포됐지만 `-501` 은 아직입니다. E2E 점검표 `G14` 가 이것을 기다립니다.

**먼저 `G14` 를 닫아야 합니다.** 한 건도 도착한 적 없는 길 위에 두 번째 길을 놓으면, 새 길이 안 되는 이유가 새 코드 탓인지 옛 문제 탓인지 가릴 수 없습니다.

## 2. 사용자가 거의 없다는 것

지금 상태에서 *"사용자 행동 분석"* 은 나오지 않습니다. 표본이 없습니다. 그래도 지금 만드는 이유는 셋입니다.

1. **데이터는 소급되지 않습니다.** 나중에 사람이 늘어도 그때부터만 쌓입니다. 계측이 늦으면 초기 구간은 영원히 비어 있습니다.
2. **표본이 1이어도 답이 나오는 질문이 있습니다.** *"이 판은 왜 실패로 끝났나"* · *"용접이 어느 자리에서 실패하나"* 는 한 판으로도 답합니다. 통계가 아니라 **재현 가능한 서술**이 필요한 질문입니다.
3. **AI 플레이어가 표본을 만듭니다.** [AI 동료 계획](ai-companion.md) §9 의 자동 플레이어가 같은 이벤트를 냅니다. 다만 **그것은 사람의 데이터가 아닙니다** — 시스템(밸런스·물리·충돌·크래시)에 대해 말할 뿐, 사람이 무엇을 헷갈려 하는지는 말하지 않습니다. 둘을 같은 표에 섞으면 안 됩니다(`source` 로 가릅니다).

그래서 **질문을 먼저 정하고 그 질문에 답하는 이벤트만** 넣습니다. "나중에 쓸지도 모르니 다 보내자" 는 저장소와 개인정보만 늘리고 답은 안 늘립니다.

## 3. 답하려는 질문

| 질문 | 필요한 것 |
| --- | --- |
| 한 판이 얼마나 걸리나 · 어디서 끝나나 | 세션 시작·끝, 끝난 이유(성공·포기·크래시) |
| 파트 4개 중 몇 개째에서 멈추나 | 파트 획득·운반·도킹 시각 |
| 용접이 실패하는 자리 | 용접 시작·완료·실패 + 접합부 번호 |
| 왜 기절하나 | 기절·기상 + 원인(운석·낙하) |
| 몇 명이 함께 하나 · 누가 호스트인가 | 세션의 인원수·역할 |
| 크래시가 어디서 나나 | 마지막 이벤트 + 기존 평문 로그 |

이 여섯이 1차 범위입니다. 히트맵·경로 추적은 **넣지 않습니다** — 좌표를 주기적으로 보내면 용량이 두 자릿수 늘어나는데, 지금 인원으로는 그림이 안 그려집니다.

## 4. 무엇을 보내나 — 이벤트

평문 로그는 **그대로 둡니다.** 사람이 사고를 읽는 용도이고 잘 하고 있습니다. 그 옆에 **기계가 읽는 이벤트**를 따로 냅니다. 둘은 목적이 다르므로 합치지 않습니다.

```
{"seq":42,"t":915.3,"type":"weld_complete","joint":7,"ms":4120}
```

- `seq` — 그 세션 안에서 1씩 는다. **빠진 번호가 곧 유실 신호**입니다
- `t` — 세션 시작 이후 초. 벽시계는 세션 머리에 한 번만 둡니다(기기 시계는 믿을 수 없습니다)
- `type` — 아래 목록 중 하나. **문자열을 자유롭게 늘리지 않습니다**
- 나머지 — 그 종류가 정한 칸만

**1차 이벤트 목록**

| 종류 | 언제 | 칸 |
| --- | --- | --- |
| `session_start` | 판 시작 | `build` · `role`(host/client) · `players` · `scene` |
| `session_end` | 판 끝 | `result`(cleared/abandoned/disconnected) · `elapsed` |
| `part_pickup` · `part_drop` · `part_dock` | 파트를 집고·놓고·붙일 때 | `part` |
| `weld_start` · `weld_complete` · `weld_fail` | 용접 | `joint` · `ms` · (실패면 `reason`) |
| `stun` · `revive` | 기절·기상 | `cause` |
| `launch_attempt` | 발사 시도 | `ok` · `missing` |

**자유 문자열은 넣지 않습니다.** 닉네임·채팅·음성 원문은 이벤트에 담지 않습니다(§7).

## 5. 어떻게 보내나 — 플레이 중에는 안 보냅니다

**"플레이 중에 네트워킹을 쓰지 않는다"** 는 이미 팀이 정한 것이고(`RunLogUpload.cs` 의 근거: 4 vCPU EC2 가 릴레이·매칭·CI 를 겸한다), 이 파이프라인도 그 결정을 그대로 따릅니다.

- 이벤트는 판이 도는 동안 **파일에 줄 단위로 쌓입니다**(`logs/` 옆 `events/`, NDJSON)
- **다음 실행이 시작할 때** 지난 세션 파일을 보냅니다 — 로그 업로드와 **같은 시점·같은 인증**
- 보낸 파일은 이름을 바꿔 표시합니다(`.sent`) — 로그 쪽에서 쓰는 방식 그대로

크래시로 죽은 판도 회수됩니다. 종료 훅이 안 불려도 파일은 남아 있고 다음 실행이 집어 갑니다 — 그 판이 정작 가장 알고 싶은 판입니다.

**대가**: 한 번만 해 보고 다시 안 켜는 사람의 데이터는 오지 않습니다. 로그 쪽이 이미 감수한 것과 같은 대가입니다.

**보내는 쪽은 호스트만인가?** 아닙니다. 참가자 화면에서만 나는 일이 있으므로 **각자 자기 것을 보냅니다.** 같은 판이 여러 벌 모이는데, 그것이 오히려 필요합니다 — 세션을 묶는 열쇠(`match`)를 호스트가 정해 모두에게 내려보내면 나중에 한 판으로 합칠 수 있습니다.

## 6. 어디에 쌓나

**MySQL 에 넣습니다.** 이미 떠 있고(`metagame-mysql`, prod·dev 각 1), 용량이 문제가 되지 않습니다.

한 판 20분에 이벤트 500건, 한 건 120바이트로 잡으면 **세션당 60 KB** 입니다. 하루 100세션이어도 6 MB 입니다. 배포 서버는 디스크 **246 G 가 비어 있습니다**(2026-09-15 실측, 309 G 중 64 G 사용). 지금 규모에서 저장은 제약이 아닙니다.

| 테이블 | 무엇 |
| --- | --- |
| `play_session` | 세션 1행 — `id`(UUID) · `match` · `user_id` · `build` · `role` · `source`(human/bot) · `started_at` · `ended_at` · `result` · `players` |
| `play_event` | 이벤트 1행 — `session_id` · `seq` · `t` · `type` · `payload`(JSON) |

`payload` 만 JSON 으로 둡니다. 종류마다 칸이 달라 열로 펴면 대부분이 `NULL` 이 되고, MySQL 8 은 JSON 을 그대로 질의할 수 있습니다.

**`source` 를 처음부터 둡니다.** 나중에 봇 데이터가 섞이면 가를 수 없습니다.

**EC2 는 임시라는 것을 잊지 않습니다.** 반납되면 데이터도 같이 사라집니다. 그래서 **내보내기(덤프)를 1단계에 넣습니다** — 분석을 서버에서만 할 수 있게 만들면 서버와 함께 끝납니다.

## 7. 개인정보와 보관

- 사람을 가리는 값은 **`deviceId` 에서 나온 사용자 번호 하나**입니다. 닉네임·IP·채팅·음성 원문은 이벤트에 **담지 않습니다**
- `deviceId` 는 **기기**를 가립니다. 한 PC 를 여러 사람이 쓰면 같은 번호가 됩니다 — 교육장 PC 에서는 흔한 일이므로, *"사용자 N명"* 이라고 쓰면 틀립니다. **"기기 N대"** 로 씁니다
- 보관 기간을 정하고 지난 것은 회수합니다 — 평문 로그가 이미 그렇게 하고 있으므로 같은 규칙을 씁니다
- 수집한다는 사실을 게임 안에서 알립니다

## 8. 받는 쪽 — 이미 배운 것을 그대로 씁니다

`/logs` 가 공개 서버에서 배운 것을 새 엔드포인트가 다시 배울 이유가 없습니다.

- 게스트 토큰을 요구합니다 — 없으면 누구나 우리 DB 에 행을 부어넣습니다
- 본문 크기 상한 · 사용자별·전역 빈도 상한 · 디스크 여유 확인
- 거절 경고는 **사유별로 묶어서** 씁니다 — 거절마다 쓰면 막으려던 것이 애플리케이션 로그로 자리만 옮깁니다(`-467`)
- 모르는 `type` 은 **버리지 않고 그대로 저장합니다** — 옛 클라이언트가 보낸 것일 수 있고, 조용히 버리면 그 판이 통째로 사라집니다

## 9. 무엇으로 보나

**BI 도구를 올리지 않습니다.** 4 vCPU 에 릴레이·매칭·CI 가 이미 있습니다.

1. **SQL** — 위 여섯 질문에 답하는 질의를 저장소에 둡니다(`scripts/analytics/*.sql`). 질문이 코드로 남아야 다음 사람이 같은 것을 다시 셉니다
2. **정적 페이지** — 날마다 한 번 질의를 돌려 JSON 을 만들고 사이트에 올립니다. 배포 사이트가 이미 `publish-site` 로 `/var/www` 에 올라가므로 새 배포 경로가 필요 없습니다
3. 그 이상은 필요해질 때

## 10. 단계

| 단계 | 무엇 | 끝났다고 말할 수 있는 조건 |
| --- | --- | --- |
| **M0** | `G14` 를 닫는다 — 평문 로그가 실제로 서버에 도착 | `/var/log/metagame-runlogs` 에 파일이 생긴다 |
| **M1** | 이벤트를 파일로 남긴다(업로드 없음) | 한 판 돌리면 `events/` 에 NDJSON 이 생기고 `seq` 가 안 빠진다 |
| **M2** | 업로드 + 저장 | 두 테이블에 행이 쌓이고, 상한·인증이 `/logs` 와 같은 수준으로 막는다 |
| **M3** | 질의와 페이지 | 여섯 질문에 SQL 로 답하고, 하루 한 번 갱신되는 페이지가 있다 |
| **M4** | 덤프 | 서버 밖으로 한 번에 내보낼 수 있다(EC2 반납 대비) |

M1 까지는 서버를 건드리지 않으므로 **세션을 끊지 않습니다.** M2 는 백엔드 배포이므로 버튼으로 나갑니다.

## 11. 정해야 할 것

- **보관 기간** — 평문 로그와 같게 할지, 이벤트는 더 길게 둘지
- **`match` 를 무엇으로 할지** — 호스트가 만든 UUID 를 내려보내는 것이 가장 단순하지만, 그러려면 동기화 경로에 한 칸이 붙습니다
- **봇 세션을 같은 테이블에 둘지** — `source` 로 가르는 것으로 충분한지, 아예 나눌지
- **알림 문구** — 수집 사실을 어디에서 어떻게 알릴지
