# 플레이 데이터 파이프라인 계획

[문서 안내](README.md) → **플레이 데이터 파이프라인**

> **아직 만들지 않은 것의 계획입니다.** §1 은 코드에서 확인한 사실이고, 나머지는 결정과 제안입니다.

플레이 데이터를 모아 **기획에 쓰는 것**이 목적입니다 — 사람들이 실제로 어디서 포기했는지를 수치로 봅니다.

## 1. 지금 무엇이 있고, 무엇이 없나

| 있는 것 | 어디 |
| --- | --- |
| 실행마다 평문 로그 파일 (8 MB 상한 · 30개 보관) | `RunLog.cs` → 빌드 폴더 `logs/` |
| **다음 실행 로그인 직후** 지난 파일을 업로드 | `RunLogUpload.SweepOnce` ← `NetworkSession.cs:269` |
| 게스트 토큰 인증 · 크기·빈도·디스크 상한 | `RunLogController.java` · `RunLogStore.java` |
| 기기별로 안정된 사용자 번호 | `AuthService.guestLogin()` — `deviceId` 로 찾고 없으면 만든다 |

**평문 로그는 디버깅용입니다.** `Application.logMessageReceivedThreaded` 를 걸어 게임이 찍는 Unity 로그를 **전부** 받아 적습니다 — 고른 값이 아닙니다. 그래서 분석에 쓸 내용이 없습니다. 실측한 파일 셋이 157 B · 157 B · 845 B 였고 작은 쪽은 세 줄이 전부입니다.

```
[I] [RUN] 이 실행의 로그: …
[I] ThreadLog initialized.
[I] [WorldSync] 감시자 설치 완료
```

로그인·방 입장·플레이·종료가 하나도 안 남습니다.

**없는 것이 더 중요합니다.**

- **구조화된 이벤트가 없습니다.** 위 로그를 파싱해 답을 뽑는 길은, 로그 문구가 바뀔 때마다 깨집니다
- **한 판이 저장되지 않습니다.** `RoomManager` 가 방을 `ConcurrentHashMap` 에 들고 있을 뿐이고(`@Entity` 는 `User` 하나, JPA 저장소는 `UserRepository` 하나), 방이 닫히거나 서버를 다시 띄우면 **그 판이 있었다는 사실 자체가 사라집니다.** 서버는 *"어제 몇 판이 돌았나"* 를 답할 수 없습니다
- **파일이 "한 판" 단위가 아닙니다.** 이름이 `yyyyMMdd-HHmmss.log` 이고 **프로세스가 뜰 때** 하나 만듭니다 — 켜서 세 판 하고 끄면 파일 1개에 세 판이 섞이고, 껐다 켜며 한 판씩 하면 파일 3개입니다
- **같은 판을 찾을 열쇠가 없습니다.** 파일 안에 판을 가리키는 값이 아무것도 없어, 각자 기기 시각으로 맞춰야 합니다 — 기기 시계는 서로 다릅니다
- **수집 경로가 한 번도 성공한 적이 없습니다.** 2026-09-15 실측 — 배포 서버의 `/var/log/metagame-runlogs` 에 **파일 0개**입니다. 원인은 `-501`(빌드 스탬프의 한글이 HTTP 헤더를 깨뜨린다)이고 지금 고치는 중입니다

**`-501` 이 먼저입니다.** 한 건도 도착한 적 없는 길 위에 두 번째 길을 놓으면, 안 되는 이유가 새 코드 탓인지 옛 문제 탓인지 가릴 수 없습니다.

## 2. 사용자가 거의 없다는 것

지금 표본으로 *"사용자 행동 통계"* 는 안 나옵니다. 그래도 지금 만드는 이유는 셋입니다.

1. **데이터는 소급되지 않습니다.** 계측이 늦으면 초기 구간은 영원히 비어 있습니다
2. **표본이 1이어도 답이 나오는 질문이 있습니다.** *"이 판은 왜 실패로 끝났나"* 는 한 판으로도 답합니다 — 통계가 아니라 **재현 가능한 서술**이 필요한 질문입니다
3. **AI 플레이어가 표본을 만듭니다** ([AI 동료 계획](ai-companion.md) 의 단계 M6). 다만 **봇은 사람이 아닙니다** — 시스템(밸런스·물리·크래시)에 대해 말할 뿐, 사람이 무엇을 헷갈려 하는지는 말하지 않습니다. `source` 로 가릅니다

그래서 **질문을 먼저 정하고 그 질문에 답하는 이벤트만** 넣습니다.

## 3. 답하려는 질문 — 기획에 쓰는 것이 1순위

| 질문 | 어떤 수치로 | 필요한 것 |
| --- | --- | --- |
| **어디서 포기하나** | 파트 4개 중 몇 개째에서 멈추나 · 몇 분째인가 · 마지막으로 한 일 | 파트 획득·도킹 시각, 세션 끝 사유 |
| **어디서 막히나** | 접합부별 용접 시도 횟수와 실패율 | 용접 시작·완료·실패 + 접합부 번호 |
| **왜 죽나** | 기절 원인 분포 · 기절과 포기 사이 간격 | 기절·기상 + 원인 |
| 한 판이 얼마나 걸리나 | 성공/포기별 길이 분포, 인원수별 | 세션 시작·끝, 인원수 |
| 몇 명이 함께 하나 | 인원수 분포, 역할 | 세션 머리 |
| **다시 오나** | 기기별 D1 · D7 재방문 | `deviceId` 기반 사용자 번호 |
| 크래시가 어디서 나나 | 마지막 이벤트 분포 | 이벤트 + 기존 평문 로그 |

히트맵·경로 추적은 **넣지 않습니다** — 좌표를 주기적으로 보내면 용량이 두 자릿수 늘어나는데, 지금 인원으로는 그림이 안 그려집니다.

## 4. 무엇을 보내나 — 이벤트

평문 로그는 **그대로 둡니다.** 목적이 다르므로 합치지 않습니다.

### 대부분은 이미 호스트가 알고 있습니다

물리와 진행도가 서버에서만 돌기 때문에, 알고 싶은 것의 상당수가 **이미 값으로 존재합니다.**
코드 여기저기에 호출을 심는 대신 **그 값이 바뀌는 순간을 보는 관찰자 하나**를 두면 됩니다.

특히 `ShipAssembly` 의 값 둘이 §3 의 첫 두 질문을 거의 다 답합니다.

#### `Floors` — 우주선을 어디까지 쌓았나

**스테이지가 아니라 조립 중인 우주선의 층입니다.** 스테이지1 안에서 로켓을 4층으로
쌓는데, 그 4칸의 상태입니다. 칸 수는 항상 `PartSpec.All.Length`(=4)이고 인덱스가 곧
층입니다 — `Evaluate()` 가 엔진에서 위로 타고 올라가며 높이 순으로 모읍니다.

```
4층  Part_4  상단 조립 모듈      ← 맨 위
3층  Part_3  승무원 거주 모듈
2층  Part_2  부양·안정화 모듈
1층  Part_1  주 추진 엔진 모듈   ← 조립대 위
```

| 값 | 뜻 |
| --- | --- |
| `Empty` | 아무것도 없다 |
| `Stacked` | 올바른 파츠가 올라갔고 **아직 용접 전** |
| `Welded` | 그 층의 접합이 끝났다 (최하단은 놓이는 순간 이 상태) |
| `WrongPart` | 다른 파츠가 올라가 있다 — 조립 순서를 어겼다 |
| `Tilted` | 올바른 파츠지만 탑승 한계보다 기울었다 |

그래서 `floors: [2,1,0,0]` 은 **1층 용접 끝 · 2층 올려만 둠 · 3·4층 비어 있음** 입니다.

- **어디서 포기했나** — 판이 끝난 순간의 `Floors` 가 곧 답입니다
- **어디서 막혔나** — `WrongPart`·`Tilted` 가 몇 층에서 얼마나 오래 유지됐나

#### `Blocker` — 지금 무엇이 발목을 잡았나

`Evaluate()` 의 조기 탈출 순서 그대로 다섯 가지입니다.

| 순서 | 사유 | 딸린 값 | 코드(제안) |
| --- | --- | --- | --- |
| 1 | 주 추진 엔진 모듈이 조립대에 없다 | — | `no_engine` |
| 2 | 파츠가 n/4 층만 쌓였다 | 쌓인 수 | `incomplete` |
| 3 | k층이 〈이름〉 이 아니다 | 층 | `wrong_order` |
| 4 | 우주선이 발사 구역 밖에 있다 | — | `off_pad` |
| 5 | 〈파츠〉 이 n도 기울어 있다 | 층 · 각도 | `tilted` |

**둘은 쓰임이 다릅니다.** `Blocker` 는 **첫 문제에서 멈추고**, `Floors` 는 끝까지 돌아
**모든 층의 상태**를 보여줍니다 — 3층이 틀렸는데 2층도 기울어 있으면 태블릿이 둘 다
보여줘야 하기 때문입니다(`-345`). 분석에서도 그대로입니다: `Floors` 는 전체 그림,
`Blocker` 는 그 순간의 발목.

**`Blocker` 는 한글 문자열이므로 그대로 담지 않습니다.** 문구가 바뀌면 집계가 갈라집니다 —
위 코드로 바꿔 싣고 딸린 값은 따로 칸에 넣습니다.
### 관찰로 되는 것 (게임플레이 코드를 안 건드립니다)

| 이벤트 | 무엇을 본다 | 어디 |
| --- | --- | --- |
| `assembly` | `Floors` 배열이 바뀔 때 | `ShipAssembly.Floors` · `Evaluate()` |
| `blocked` | `IsBoardable` 이 false 이고 `Blocker` 가 바뀔 때 | `ShipAssembly.Blocker` |
| `checkpoint` | `CheckpointIndex` 가 바뀔 때 | `GameSession.ReachCheckpoint` |
| `fall` | `Falls` 가 늘 때 | `GameSession.RecoverFallenPlayer` |
| `cleared` | `Cleared` 가 켜질 때 | `GameSession.Clear()` |
| `weld` | `WeldBead.All` 의 상태가 바뀔 때 | `WeldBead.All` · `IsWeldedToPad` |
| `dock` | `DockedPart` 가 바뀔 때 | `AssemblyDock.DockedPart` |

### 심어야 하는 것 (관찰로는 안 됩니다)

| 이벤트 | 왜 |
| --- | --- |
| `session_start` · `session_end` | 각자 자기 판의 시작·끝을 안다. 특히 **튕김**은 호스트가 "떠났다" 까지만 알고 왜인지는 모른다 |

**`session_end` 에는 그 순간의 `floors` 를 함께 싣습니다.** 그 한 줄이 곧 *"어디서
포기했나"* 의 답입니다. 변화 이벤트를 하나라도 놓쳤어도 마지막 상태는 남습니다.

> **주기적으로 상태를 찍지는 않습니다.** 변화가 있을 때만 내면 필요한 것이 이미 다
> 잡히고, `seq` 로 유실도 알 수 있습니다. 주기 스냅샷은 같은 정보를 반복할 뿐입니다 —
> 판이 끝나는 순간의 한 줄만 따로 둡니다.
| `weld_fail` 의 사유 | 실패는 상태가 아니라 **사건**이라 다음 관찰 때는 이미 사라져 있다 |
| `launch_attempt` 의 실패 사유 | 위와 같다 |

### 누가 보내나

| 보내는 쪽 | 무엇 |
| --- | --- |
| **호스트** | 세계 상태 — `assembly` · `blocked` · `weld` · `dock` · `checkpoint` · `cleared` |
| **각자** | 자기 것 — `session_start` · `session_end` · `fall` · 튕김 |

둘 다 같은 `match` 를 달아 나중에 한 판으로 합칩니다(§5).

### 누가 했나 — NPC 가 섞인다

**AI 동료가 빈자리를 채우므로 거의 모든 판에 NPC 가 있습니다**([AI 동료 계획](ai-companion.md) 의 정해진 것:
NPC 수 = 4 − 사람 수). 그런데 관찰로 잡는 이벤트는 **세계가 어떻게 바뀌었는지**만 보고
**누가 바꿨는지**는 안 봅니다.

그대로 두면 분석이 틀립니다.

- NPC 가 용접하면 `weld` 가 잡히는데, 그건 **사람이 해낸 것이 아닙니다**
- *"어디서 막히나"* 를 세는데 NPC 가 대신 뚫어 준 것이 섞이면 난이도 판정이 틀립니다
- 사람 4명 판과 사람 1명 + NPC 3명 판은 **절대 같은 표에 넣으면 안 됩니다**

`source`(human/bot)는 **세션 단위**라 이걸 못 가릅니다 — 전부 봇인 판과 *"사람 판인데
NPC 가 도왔다"* 는 다른 것입니다. 그래서 둘을 더합니다.

| 어디 | 무엇 |
| --- | --- |
| 세션 | `humans` · `npcs` 를 따로 센다 (`players` 하나로는 4인 판의 구성이 안 보인다) |
| 이벤트 | NPC 가 할 수 있는 일(`fetch`·`weld`·`dock`)에는 `by`(`human` \| `npc`)를 붙인다 |

**`by` 는 관찰로는 못 채웁니다.** 상태 변화에는 행위자가 안 적혀 있습니다 — NPC 의 행동은
호스트의 상태 기계가 몰므로, **의도를 실행하는 그 자리에서** 호스트가 직접 남깁니다.
관찰이 아니라 심는 쪽입니다(§4 의 둘째 표).

### 이벤트 모양

```
{"seq":42,"t":915.3,"type":"assembly","floors":[2,1,0,0]}
{"seq":43,"t":920.1,"type":"blocked","code":"tilted","floor":1}
{"seq":44,"t":931.7,"type":"weld","joint":7,"state":"done","ms":4120,"by":"npc"}
```

- `seq` — 세션 안에서 1씩 는다. **빠진 번호가 곧 유실 신호**이고, 중복을 걸러내는 열쇠이기도 하다(§5)
- `t` — 세션 시작 이후 초. 기기 시계는 믿지 않는다
- `type` — 정해진 목록 중 하나. **자유롭게 늘리지 않는다**
- `by` — NPC 가 할 수 있는 일에만. 없으면 사람이다

세션 머리에는 **지문**이 붙습니다.

```
{"session":"…","match":"…","schema":"edc88fb5d764","humans":2,"npcs":2, …}
```

`schema` 는 이벤트가 기대는 게임 코드의 정의(`FloorState` 의 순서 · 층 수 · 막는 사유)를
묶은 값입니다(`-552`). **이것이 없으면 옛 데이터와 새 데이터가 조용히 섞입니다** —
`FloorState` 에 값이 하나 끼어들면 `floors:[2,…]` 의 `2` 가 다른 것을 뜻하게 되는데,
숫자는 그대로 들어오고 질의도 그대로 돌아갑니다.

**자유 문자열은 넣지 않습니다.** 닉네임·채팅·음성은 담지 않습니다.

> 자세한 자리와 주의는 `-498`, 지문은 `-552` 에 있습니다.
## 5. 어떻게 보내나

**플레이 중에는 안 보냅니다.** `RunLogUpload` 가 이미 정한 *"플레이 중에 네트워킹을 쓰지 않는다"* 를 그대로 따릅니다 — 4 vCPU EC2 가 릴레이·매칭·CI 를 겸합니다.

- 판이 도는 동안 **파일에 줄 단위로 쌓고**(`logs/` 옆 `events/`, NDJSON)
- **다음 실행이 시작할 때** 지난 세션 파일을 보냅니다 — 로그 업로드와 같은 시점·같은 인증
- 보낸 파일은 이름을 바꿔 표시합니다(`.sent`)

크래시로 죽은 판도 회수됩니다 — 종료 훅이 안 불려도 파일은 남습니다. 대가는 하나, **한 번만 해 보고 다시 안 켜는 사람의 데이터는 오지 않습니다.**

### `match` — 같은 판을 묶는 열쇠

호스트가 판을 시작할 때 무작위 ID 를 만들어 **모두에게 내려보내고**, 그 판의 모든 이벤트에 붙입니다.

```
호스트 A   session=a1   match=7f3c9e…
참가자 B   session=b2   match=7f3c9e…
참가자 C   session=c3   match=7f3c9e…
```

`session` 은 *"이 사람의 이 판"*, `match` 는 *"모두의 같은 판"* 입니다. 이것이 없으면 **한 판을 통째로 볼 수 없고**, 참가자 화면에서만 난 문제를 호스트 기록과 맞춰 볼 수도 없습니다. 각자 자기 것을 보내므로 같은 판이 여러 벌 모이는데, 그것이 필요한 것입니다.

### 같은 것을 두 번 받아도 한 번이어야 한다

지금 평문 로그 경로에는 중복을 알아볼 열쇠가 없습니다. `.sent` 표시가 **이름 바꾸기와 표시 파일 둘 다 실패하면** 같은 파일이 실행마다 다시 가고, 서버는 받을 때마다 **새 이름**을 만들어 쌓습니다.

그래서 이벤트는 **`(session, seq)` 를 유일 열쇠로** 둡니다. 두 번 받으면 두 번째는 버립니다 — 보내는 쪽이 조심하는 것에 기대지 않습니다.

## 6. 어디에 쌓나 — DB 가 아니라 파일입니다

**우리 규모에서 DB 성능은 쟁점이 아닙니다.** 세션당 60 KB 로 잡으면 하루 100세션에 6 MB 입니다. 쟁점은 두 가지입니다.

- **4 vCPU 가 이미 붐빕니다.** 2026-09-15 실측 부하 2.63 이고, 그 시각 Unity CI 빌드가 **154 % CPU** 를 쓰고 있었습니다. 프로세스를 하나 더 얹는 것 자체가 비용입니다
- **EC2 는 반납 예정입니다.** 서버에서만 꺼낼 수 있는 구조는 서버와 함께 끝납니다

| 무엇 | 어디 | 왜 |
| --- | --- | --- |
| **이벤트 원본** | **NDJSON 파일** — `/var/log/metagame-events/<날짜>/` | 평문 로그가 이미 쓰는 방식. 서버 프로세스 0개. **반납 때 복사하면 끝** |
| **분석** | **DuckDB** (각자 PC) | NDJSON 을 그대로 읽어 SQL. 서버 부하 0 |
| `play_session` 색인 | MySQL | `User` 와 조인해야 하고, 행이 판당 하나라 작다 |

**NoSQL 을 들이지 않는 이유.** 문서 DB 의 장점은 스키마 유연성과 고속 수집인데, 우리는 초당 몇 건이라 그 장점이 안 살고 운영 비용만 남습니다. 스키마 유연성은 NDJSON 이 이미 줍니다. 이벤트 본문을 DB 에 넣지 않으므로 **문서 DB 가 필요할 자리가 없습니다.**

**`play_session` 칸**: `id` · `match` · `user_id` · `build` · `role` · `schema` ·
`source`(human/bot) · `humans` · `npcs` · `started_at` · `ended_at` · `result`

**`source` 를 처음부터 둡니다.** 나중에 봇 데이터가 섞이면 가를 수 없습니다.

## 7. 개인정보와 보관

- 사람을 가리는 값은 **`deviceId` 에서 나온 사용자 번호 하나**입니다. 닉네임·IP·채팅·**음성**은 이벤트에 담지 않습니다
- 그 번호로 **재방문(D1 · D7)을 셉니다.** 이미 기기별로 안정된 값입니다
- **`deviceId` 는 기기를 가립니다.** 한 PC 를 여럿이 쓰면 같은 번호가 됩니다 — 교육장 PC 에서는 흔하므로 *"사용자 N명"* 이라 쓰면 틀립니다. **"기기 N대"** 로 씁니다
- **음성은 어느 채널도 수집하지 않습니다.** NPC 명령 음성은 기기 밖으로 나가지 않고, 사람끼리 음성은 중계만 하고 남기지 않습니다([AI 동료 계획](ai-companion.md) 의 음성 채널 절)
- 수집 고지는 **배포 사이트**에 있습니다
- 보관 기간(임시): **평문 로그 30일 · 이벤트 180일.** 이벤트가 훨씬 작고 오래 볼수록 값이 큽니다

## 8. 받는 쪽 — 이미 배운 것을 그대로 씁니다

`/logs` 가 공개 서버에서 배운 것을 새 엔드포인트가 다시 배울 이유가 없습니다.

- 게스트 토큰을 요구한다 — 없으면 누구나 우리 디스크를 채운다
- 본문 크기 상한 · 사용자별·전역 빈도 상한 · 디스크 여유 확인
- 거절 경고는 **사유별로 묶어서** 쓴다 — 거절마다 쓰면 막으려던 것이 애플리케이션 로그로 자리만 옮긴다(`-467`)
- 모르는 `type` 은 **버리지 않고 그대로 저장한다** — 옛 클라이언트가 보낸 것일 수 있고, 조용히 버리면 그 판이 통째로 사라진다
- `(session, seq)` 가 겹치면 **조용히 버린다**(§5)

## 9. 무엇으로 보나

**BI 도구를 올리지 않습니다.** 4 vCPU 에 릴레이·매칭·CI 가 이미 있습니다.

1. **DuckDB 질의를 저장소에 둡니다**(`scripts/analytics/*.sql`) — 질문이 코드로 남아야
   다음 사람이 같은 것을 다시 셉니다. **질의는 `schema` 로 나눠 봅니다** — 지문이 다르면
   `floors` 의 숫자가 다른 것을 뜻하므로 한 표에 섞으면 안 됩니다
2. **정적 페이지** — 날마다 한 번 돌려 JSON 을 만들고 사이트에 올립니다. `publish-site` 가 이미 `/var/www` 로 올리므로 새 배포 경로가 필요 없습니다
3. 그 이상은 필요해질 때

## 10. 단계

| 단계 | 무엇 | 끝났다고 말할 수 있는 조건 |
| --- | --- | --- |
| **M0** | `-501` — 평문 로그가 실제로 서버에 도착 | `/var/log/metagame-runlogs` 에 파일이 생긴다 (E2E `G14`) |
| **M1** | 이벤트 목록 확정 — 코드의 어느 자리인지까지 | `-498` 에 이벤트마다 심을 함수가 적힌다 |
| **M2** | 이벤트를 파일로 남긴다(업로드 없음) | 한 판 돌리면 `events/` 에 NDJSON 이 생기고 `seq` 가 안 빠진다 |
| **M3** | 업로드 + 저장 | 서버에 NDJSON 이 쌓이고 `play_session` 에 행이 생긴다. 같은 것을 두 번 보내도 한 번이다 |
| **M4** | 질의와 페이지 | §3 질문에 DuckDB 로 답하고, 하루 한 번 갱신되는 페이지가 있다 |

M2 까지는 서버를 안 건드리므로 **세션을 끊지 않습니다.** M3 은 백엔드 배포라 버튼으로 나갑니다.

**M1 전에 `-374`(여러 명이면 프레임이 떨어진다)를 끝내는 편이 낫습니다** — 이벤트 수집이 그 위에 얹히면 원인을 가르기 어려워집니다. 그리고 이벤트는 **빌드 채널별로 끄고 켤 수 있어야** 합니다(개발·QA 빌드가 배포 서버로 보내면 데이터가 섞입니다).

## 11. 아직 안 정한 것

- 이벤트 목록의 **코드 자리** — `-498` 의 일
- 채널별 켜고 끄기를 무엇으로 가를지 (`-460` 의 release/dev/qa 를 그대로 쓸지)
