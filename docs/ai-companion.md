# AI 동료 계획

[문서 안내](README.md) → **AI 동료**

> **아직 만들지 않은 것의 계획입니다.** §2 는 코드에서 확인한 사실이고, 나머지는 결정과 제안입니다.

4인 협동 게임인데 사람이 모이지 않습니다. 빈자리를 **말로 지시하는 NPC 동료**가 채웁니다.

## 1. 정해진 것

| 항목 | 결정 |
| --- | --- |
| NPC 인원 | **4 − 사람 수.** 어떤 경우에도 판은 4인이 된다 |
| 지시 방법 | **음성만.** 채팅 명령은 넣지 않는다 |
| 지시 권한 | **모든 플레이어** |
| 음성 채널 | **둘로 나눈다** — 사람끼리 통화 · NPC 명령. 인게임 버튼도 각각 |
| 음성 원문 | **기기 안에서만 처리하고 남기지 않는다** |
| 우선순위 | **지연 > 품질.** 느리고 똑똑한 것보다 빠르고 단순한 것 |
| 모델을 못 돌리는 PC | **지금은 고려하지 않는다**(모두 가능하다고 본다). 남은 문제로 둔다 |
| 명령이 없을 때 | 가만히 서 있지 않는다 — 정해진 규칙 안에서 움직인다(§7) |

## 2. 지금 구조가 강제하는 것

| 사실 | 어디 | 따라 나오는 것 |
| --- | --- | --- |
| **물리는 서버에서만 돈다.** 클라이언트의 같은 오브젝트는 키네마틱으로 두고 받은 자세를 따라간다 | `WorldSync.cs` (`-145`) | NPC 의 **몸은 호스트에서** 굴러야 한다 |
| 플레이어는 입력을 `[Command]` 로 보내고 **서버의 `PlayerRig` 가 그 입력으로 힘을 가한다** | `NetPlayer.cs` | *"클라이언트가 의도를 보내고 호스트가 실행한다"* 는 **이미 있는 모양**이다 |
| 씬 오브젝트는 `NetworkIdentity` 를 못 단다(sceneId 문제) | `WorldSync.cs` | NPC 는 **서버가 띄우는 프리팹**이어야 한다 |
| 전송은 **KCP over UDP** · 릴레이는 우리 EC2 위의 파이썬 프로세스 | `MatchTransport.cs` · `scripts/relay/metagame_relay.py` | 음성이 탈 자리가 이미 있다(§8) |

## 3. 층을 셋으로 나눕니다

| 층 | 하는 일 | 어디서 도나 |
| --- | --- | --- |
| **말 → 글** | 음성 인식(STT) | 말한 사람의 PC |
| **글 → 의도** | `"왼쪽 파트 가져와"` → `fetch(part=3)` | 말한 사람의 PC |
| **의도 → 행동** | 길 찾고 집고 용접한다 | **호스트** |

**셋째 층이 핵심이고 거기에 모델은 없습니다.** NPC 가 실제로 움직이는 것은 호스트의 상태 기계이고, 기존 `PlayerRig`·`ToolBase`·`PartClamp` 를 그대로 씁니다 — **두 번째 물리 경로를 만들지 않습니다.**

**개발 순서로는 채팅이 먼저입니다.** 셋째 층을 만들 때 `fetch 3` 을 쳐서 확인하는 것이 가장 싸기 때문입니다. 다만 그것은 **개발용 발판이지 내보내는 기능이 아닙니다.**

## 4. 모델이 할 일은 대화가 아니라 **분류**입니다

*"왼쪽에 있는 거 가져와"* 를 `fetch(part=3)` 으로 바꾸는 것은 **정해진 목록 중 하나를 고르고 칸을 채우는 일**입니다.

| | 대화용 | 의도 분류용 |
| --- | --- | --- |
| 크기(4bit) | 4~8 GB | **0.4~1 GB** |
| 출력 | 자유 문장 | 정해진 칸만 (문법 제약 디코딩) |
| 틀렸을 때 | 이상한 말을 한다 | **목록 밖이면 그냥 거절된다** |

**출력을 문법으로 묶습니다.** 모델이 무엇을 뱉든 의도 목록 밖이면 호스트가 받지 않습니다. 이것은 편의가 아니라 **필수**입니다 — `[Command]` 는 클라이언트가 보내는 것이고 클라이언트는 고쳐질 수 있습니다.

**지연이 품질보다 먼저입니다.** 더 작은 모델·더 짧은 출력·부분 결과 사용 중 무엇이든 반응이 빨라지는 쪽을 고릅니다.

## 5. 의도 목록 (초안)

| 의도 | 칸 | 뜻 |
| --- | --- | --- |
| `fetch` | `part` | 그 파트를 집어 우주선 쪽으로 가져온다 |
| `goto` | `target` | 그리로 간다 |
| `follow` | `player` | 따라다닌다 |
| `weld` | `joint` | 그 접합부를 용접한다 |
| `hold` / `release` | — | 지금 든 것을 유지·놓는다 |
| `revive` | `player` | 기절한 사람을 일으킨다 |
| `stop` | — | 지금 하던 것을 그만둔다 |

**`stop` 은 반드시 있어야 하고 즉시 들어야 합니다.** 사람이 통제를 되찾는 길이 없으면 NPC 는 도우미가 아니라 사고입니다.

**칸의 값은 사람이 부르는 이름이 아니라 번호입니다.** *"왼쪽 거"* 를 번호로 바꾸는 것은 말한 사람의 클라이언트가 합니다 — 그 화면에서 무엇이 왼쪽인지는 그 클라이언트만 압니다.

## 6. 여러 사람이 동시에 시키면

지시 권한은 모두에게 있으므로 겹칩니다.

| 규칙 | 이유 |
| --- | --- |
| 한 NPC 는 **한 번에 하나**를 한다 | 두 지시를 섞으면 둘 다 안 된다 |
| 나중 지시가 앞 지시를 **대신한다** | 줄을 세우면 사람이 한참 뒤에 반응을 본다 |
| `stop` 은 누구든 즉시 | 위 |
| 호스트가 최종 판정한다 | 권위가 하나여야 한다 |

**누가 무엇을 시켰는지 화면에 보여 줍니다** — `준영 → NPC 2: 3번 파트 가져와`. 음성을 남에게 중계하지 않고도 팀원이 중복 지시를 피할 수 있고, 비용이 거의 없습니다.

## 7. 명령이 없을 때 — 움직이되 **결과를 만들지 않습니다**

가만히 서 있으면 죽어 보입니다. 그렇다고 스스로 판단해 일하면 *"이거 누가 했지"* 가 생기고, 데이터에서도 사람 행동과 섞입니다.

| 해도 되는 것 | 하면 안 되는 것 |
| --- | --- |
| 가장 가까운 사람을 일정 거리로 따라다닌다 | 시키지 않은 파트를 줍는다 |
| 길을 막으면 비킨다 | 용접한다 |
| 말하는 사람 쪽을 본다 | 도킹한다 |
| 들고 있던 것을 우주선으로 옮긴다(받은 명령의 연장) | 발사한다 |

**경계는 하나입니다 — 세계 상태를 바꾸는 일은 명령을 받았을 때만 합니다.** 그러면 살아 있어 보이면서도 추적 가능성이 유지됩니다.

## 8. 음성 채널 둘 — 성질이 완전히 다릅니다

인게임 버튼을 따로 두므로 **말이 명령인지 잡담인지 기계가 가릴 필요가 없습니다.** 이것이 이 설계에서 가장 큰 단순화입니다.

| | 사람끼리 통화 | NPC 명령 |
| --- | --- | --- |
| 오디오가 가는 곳 | 다른 사람들(릴레이 경유) | **아무 데도 안 간다** |
| 네트워크에 나가는 것 | Opus 패킷 | 의도 한 줄 (`fetch(3)`) |
| 대역폭 | 방당 약 288 kbps | **사실상 0** |
| STT | 안 돌린다 | 기기 안에서 돈다 |
| 남는 기록 | 없다(중계만) | 없다 |

**그래서 서버 제약은 사람끼리 채널에만 걸립니다.**

### 사람끼리 채널의 현실적 제약

Opus 음성 24 kbps · 20 ms 프레임(초당 50패킷) 기준입니다.

| | 값 |
| --- | --- |
| 방 하나(사람 4명) 올라감 | 약 96 kbps · 200 pps |
| 릴레이가 내보냄 | 약 288 kbps · 600 pps |
| 한 방 1시간 | 약 170 MB |
| 지금 서버 실사용 | 15일에 28 GB (하루 약 1.9 GB) |

**대역폭은 여유롭습니다.** §1 대로 NPC 가 빈자리를 채우므로 실제 사람은 보통 1~3명이고, 부하는 더 작습니다.

**진짜 제약은 셋입니다.**

1. **CPU 경합.** 2026-09-15 실측 부하 2.63/4 이고 그 시각 Unity CI 빌드가 **154 % CPU** 를 쓰고 있었습니다. 음성은 지연에 민감해서 **빌드가 도는 동안 지터가 튑니다.** 대역폭과 달리 계산으로 못 없애고 재야 압니다
2. **릴레이가 파이썬 단일 프로세스**입니다(`metagame_relay.py`, 405줄). 초당 800패킷은 감당하지만 GIL·GC 순간이 실시간 오디오에는 그대로 튐으로 보입니다
3. **KCP 채널로 보내면 안 됩니다.** KCP 는 잃어버린 패킷을 기어이 다시 보내는데 **늦게 도착한 소리는 쓸모가 없습니다.** Unreliable 채널을 써야 합니다

**누르고 말하기(PTT)를 기본으로 합니다.** 상시 송신 대비 부하가 크게 줄고, 명령 채널에서는 구간이 명확해져 STT 가 훨씬 쉬워집니다. 버튼을 따로 두기로 한 결정과도 맞습니다.

**재야 할 것**: CI 빌드가 도는 동안과 안 도는 동안의 왕복 지연·지터. `-374`(여러 명이면 프레임 저하)와 같은 자리라 함께 재는 편이 낫습니다.

## 9. 모델을 어디서 돌리고 어떻게 전달하나

| 어디 | 판단 |
| --- | --- |
| **각 플레이어 PC** | **채택.** 서버 부하 0 · 원문이 기기 밖으로 안 나간다 · 오프라인에서도 된다 |
| 호스트 1대만 | 호스트는 **플레이어의 PC** 다. 물리·릴레이에 추론까지 얹으면 그 사람 프레임이 떨어진다 |
| 배포 서버(EC2) | 4 vCPU · GPU 없음 · 이미 붐빈다. *"플레이 중 네트워킹 안 쓴다"* 와도 어긋난다 |
| 외부 API | 비용 · 키 관리 · 오프라인 불가. 팀 계정·토큰 규칙과 맞지 않는다 |

**전달은 런처의 선택 내려받기**입니다. 런처는 이미 `files/<sha256>.gz` 를 매니페스트대로 받으므로 큰 파일을 하나 더 다는 것은 새 구조가 아니고, 서버 디스크도 246 G 비어 있습니다. 빌드에 넣으면 업데이트마다 모델까지 다시 받게 되므로 택하지 않습니다.

**모르는 것은 대역폭입니다.** 1 GB 짜리를 여러 명이 동시에 받을 때 우리 EC2 한 대가 어떻게 되는지는 재 본 적이 없습니다.

## 10. 단계

| 단계 | 무엇 | 끝났다고 말할 수 있는 조건 |
| --- | --- | --- |
| **M0** | 의도 계약 — 목록·칸·검증 | 문서와 코드의 목록이 같고, 목록 밖 값이 거절되는 것을 시험이 지킨다 |
| **M1** | 호스트의 NPC 몸과 상태 기계 | 개발용 채팅으로 `fetch 3` 을 치면 NPC 가 파트를 가져온다. **모델 0 MB** |
| **M2** | 명령 없을 때의 규칙(§7) | 따라다니고 비키되 **세계 상태를 바꾸지 않는다** |
| **M3** | 로컬 모델로 글 → 의도 | *"왼쪽 거 가져와"* 가 `fetch(3)` 이 된다. 내려받기 대역폭 실측 |
| **M4** | 음성 — 명령 채널 | 버튼을 누르고 말하면 M3 과 같은 결과. 원문이 기기 밖으로 안 나간다 |
| **M5** | 음성 — 사람끼리 채널 | 4인 통화가 되고, CI 빌드 중 지터를 재 둔다 |
| **M6** | 자동 플레이어 | 같은 의도 계층을 대본이 몰아 판을 완주하고 이벤트를 낸다 |

**M6 이 데이터 파이프라인과 만나는 자리입니다.** 의도 계층이 호스트에 있으므로, 그 위를 사람이 아니라 대본이 몰면 그대로 자동 플레이가 됩니다. 사람이 없어도 판이 돌고 [플레이 데이터 파이프라인](data-pipeline.md) 의 이벤트가 쌓입니다 — 다만 `source=bot` 으로 갈라 둡니다.

## 11. 안 하기로 하는 것

- **잡담·역할극** — 범위를 넓히면 모델이 커지고, 그러면 §9 가 무너집니다
- **NPC 가 스스로 판단해 세계를 바꾸는 것** — §7 의 경계
- **모델을 게임 로직 판정에 쓰는 것** — 용접이 됐는지 같은 판정은 지금처럼 규칙이 합니다
- **음성 원문을 저장하거나 올리는 것** — 어느 채널도 아닙니다

## 12. 아직 안 정한 것

- 모델을 못 돌리는 PC 의 동작 — 지금은 모두 가능하다고 보고 남겨 둔다
- 지연 목표 수치 — M3 에서 실측한 뒤 정한다
- NPC 가 방 정원(`Room`·`RoomPlayer`)에 어떻게 들어가는지 — 지금 그 구조는 메모리에만 있다
- 동시 내려받기 대역폭 — 실측 대상
