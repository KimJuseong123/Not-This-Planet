## 1. Jira 사전 설정

1. **레이블:** 미리 만들 필요 없음 — R2가 제목의 `[파트]`를 읽어 자동으로 붙이고, `needs-fix`도 규칙이 생성한다. 값은 파트 태그와 글자까지 동일(대소문자 구분).
   규칙이 쓰는 레이블은 셋이다 — `<파트>`(R2) · `has-branch`(R4가 붙인다, R5가 읽는다) ·
   **`automation-missed`**(사람이 붙인다, R5·R9가 읽는다 — §2 R9 아래 "자동화가 이벤트를 놓쳤을 때" 참고).
   `automation-missed`를 **아무 이슈도 들고 있지 않아도 괜찮다** — 2026-09-08 실측: `labels`는 자유
   입력 필드라 없는 값으로 물어도 **오류가 아니라 0건**이다(옵션 목록이 정해진 `component`·`fixVersion`
   과 다르다). 그때 R5의 허용 항은 항상 거짓이 되고 R9의 예외 항은 항상 참이 되어 **두 규칙 다
   override가 없던 때로 돌아간다** — 가드가 풀리는 쪽이 아니라 지켜지는 쪽이다.
2. **필수 필드:** Task 유형에서 **담당자 · 상위 항목 · 기한**을 필수로.
   - 팀 관리형: 프로젝트 설정 → 이슈 유형 → Task → 각 필드의 "필수" 체크 (프로젝트 관리자)
   - 회사 관리형: 필드 구성에서 Required (Jira 관리자에게 요청)
3. **설명 템플릿 본문**을 [`docs/templates/jira-issue-description.md`](./templates/jira-issue-description.md)에서 복사해 둔다 (R1에 붙임).

  | 무엇으로 쓰나 | 넣어야 하는 서식 | 위키 마크업을 넣으면 |
  | --- | --- | --- |
  | Automation(R1) 이슈 편집 | **위키 마크업** — `h2.` · 별표 불릿 · 중괄호 금지 | 정상 |
  | MCP·REST(사람·에이전트가 갱신) | **Markdown** — `##` · `-` · 백틱 | 변환기가 Markdown이 아니라고 보고 **글자 그대로 저장** |

  이 서식 규칙은 **설명뿐 아니라 자동화의 코멘트 액션에도 그대로 적용된다.** 위키 마크업에서 굵게는 별표 **1개**
  (`*텍스트*`)다. 마크다운식 `**텍스트**`를 넣으면 파서가 엉켜 **기울임으로 렌더링된다**(2026-08-31 실측:
  R5 되돌림 코멘트가 화면에 기울임으로 표시됨. API로 읽으면 별표 4개로 내려온다).
  주의 — **Mattermost 웹 요청 액션의 본문은 Markdown 이므로 `**텍스트**`가 맞다.** 위키 마크업은 Jira 안에
  글을 쓰는 액션(이슈 편집·코멘트)에만 해당한다.

  MCP 서버는 Markdown → 위키 마크업 → ADF 순으로 변환한다. 그래서 MCP로 `h2.`를 넣으면 제목이 아니라 `h2.` 라는 글자가 남는다(이슈 23건에서 그렇게 보였던 원인). 반대로 템플릿을 Markdown으로 "고치면" 위 ①로 깨진다. **부수 실측**: MCP로 쓸 때 코드 표기 안에 별표 하나만 넣으면 굵게 표기 경계가 어긋나고 뒤따르는 목록이 중첩으로 잘못 해석된다 — 별표는 글로 쓴다.
- **내용 없는 불릿은 불릿이 되지 않는다**(2026-08-28 실측). 템플릿 완료 조건 자리에 별표만 있는 줄 두 개를 두었더니 별표가 글자로 보였다(`-101`·`-107`·`-111`·`-113`). 자리표시자 텍스트를 함께 넣어 고쳤다(템플릿 v1.2) — **R1 규칙 본문도 같은 내용으로 갱신해야 한다**(브라우저 세션 필요, 부록 A).

- 트리거 **수신 웹훅** `jira.incoming.webhook` · `searchOrProvide: "provided"`(업무 항목 기준 = **웹후크 HTTP POST 본문에서 제공되는 이슈**). 웹훅 URL·암호는 규칙 화면에만 있고 **GitLab CI 변수 `JIRA_RELEASE_WEBHOOK`**(masked·protected)에 넣는다 — 값은 이슈·문서·채팅에 적지 않는다

  ```json
   "data": {"version": "v0.1.0", "releaseUrl": "https://…/-/releases/v0.1.0", "date": "2026-09-07"}}
  ```
  `issues`가 규칙이 다룰 이슈이고, `data`는 규칙 안에서 `{{webhookData.…}}`로 읽는다.
- 액션 **순서가 중요하다** — 버전이 없으면 `fixVersions` 부여가 실패한다:

  | # | 액션 | 값 |
  | --- | --- | --- |
  | 1 | `jira.version.create` | `versionName = {{webhookData.version}}` · project id `22557`(software) · `overrideReleaseDate: SET_ON_EMPTY` |
  | 2 | `jira.issue.edit` | `operations: []` · `advancedFields = {"update": {"fixVersions": [{"add": {"name": "{{webhookData.version}}"}}]}}` · `sendNotifications: false` |
  | 3 | `jira.version.release` | `versionName = {{webhookData.version}}` · `releaseDate = {{webhookData.date}}` · 같은 project |

- **왜 편집을 `operations`가 아니라 `advancedFields`로 하나**: UI가 만든 `operations`는 `type: "SET"` + `value: [{"type":"REFERENCE","value":"LAST_RELEASED_VERSION"}]` 이었다 — **기존 `fixVersion`을 지우고 엉뚱한 버전을 넣는다.** 스마트값을 `operations`의 값 항목에 어떤 `type`으로 싣는지는 문서화돼 있지 않아, 부록 A에 실측으로 남은 `advancedFields`(Jira REST 편집 JSON 문자열, `add`로 기존 값 유지) 를 쓴다. UI 에서는 "고급" 칸에 JSON으로 보인다 — 정상이다
- 적용: 부록 A 방식으로 `PUT`(dry-run으로 먼저 확인). 2026-09-07 `PUT 200` 후 재조회로 7항목 전부 확인(액션 순서·타입 · 세 스마트값 · advancedFields · `operations` 빈 것 · 트리거 기준)
- 실패는 CI 쪽에서 **비차단**이다 — Release는 이미 났으므로 웹훅이 실패해도 MM 카드에 한 줄만 남는다. 같은 버전을 다시 보내면 1) 이 "이미 있음" 으로 실패할 수 있는데 그것도 무해하다
- **웹훅 주소의 모양**: CI 변수 `JIRA_RELEASE_WEBHOOK` 은 `https://` 로 시작하고 앞뒤에 공백이 없어야 한다. CI 가 **버전 단계(0분)에서 모양을 미리 본다** — 틀리면 그때 경고하고 릴리스는 계속한다. 2026-09-11 v1.0.0 에서 이 값이 스킴 없이 들어가 있어 `urllib` 이 `ValueError: unknown url type` 으로 터졌고, **빌드·패키지·Release·MM 이 전부 끝난 뒤**였던 탓에 58분 걸린 잡이 빨간불로 남았다.

  - **v1.0.0(2026-09-11)은 미충족이다** — 위 오류로 웹훅이 가지 않아 Jira 쪽 fixVersion 이 비어 있다. 다음 릴리스에서 확인한다.
