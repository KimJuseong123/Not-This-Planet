## 0. 릴레이 테스트에 필요한 네트워크 조건

정확히는 **서로 다른 공인 IP** 여야 합니다. 백엔드가 이렇게 판단합니다
(`GameWebSocketHandler.sameNetwork`):

| 조건 | 판정 |
| --- | --- |
| 사람이 2명 미만 | 같은 망 → **직접 접속** |
| 두 사람의 **공인 IP가 같음** | 같은 망 → **직접 접속** |
| 공인 IP가 다르고, 사설 대역도 다름 | **릴레이** |

### ⚠ 가장 흔한 함정

**교육장에서 자리만 떨어져 앉는 것으로는 안 됩니다.** 같은 건물 WiFi는 LAN이 달라도
**밖에서 보이는 공인 IP가 하나**입니다. 그러면 `직접 접속`으로 빠지고 **릴레이는 한 줄도
실행되지 않습니다.** 같은 망에서의 접속 성공만으로는 릴레이 동작을 확인할 수 없습니다.

### 가장 확실한 조합

> **한 명은 교육장 WiFi, 다른 한 명은 휴대폰 핫스팟(LTE/5G).**

집·카페 회선도 사용할 수 있습니다. 선택한 두 회선의 공인 IP가 다른지 아래 명령으로 확인합니다.

```
curl https://ifconfig.me
```

## 2. 절차

### 2-1. 먼저 같은 망에서 한 번 (기준선)

**릴레이를 시험하기 전에 기본 멀티플레이가 되는지부터 확인합니다.**이 단계를 건너뛰면,
나중에 실패했을 때 릴레이 탓인지 게임 탓인지 구분할 수 없습니다.

1. 두 사람 다 **같은 WiFi**에서 클라이언트 실행
2. A가 방 만들기 → 방 코드 확인
3. B가 그 코드로 입장
4. A가 시작
5. **서로 움직이는 게 보이는지** 확인

여기서 안 되면 릴레이 이전 문제입니다. 기본 접속 문제를 먼저 해결하고 재검증합니다.

### 2-2. 서로 다른 망에서 릴레이 확인

1. 한 명이 **휴대폰 핫스팟으로 전환**
2. 위 1~5 를 그대로 반복
3. 몇 분 돌아다니며 확인:
   - 상대가 **끊기지 않고** 계속 보이는가
   - 움직임이 **튀지 않는가**
   - 물건을 잡거나 상호작용이 서로에게 보이는가

## 3. 무엇을 봐야 성공인가

**화면만 보고 판단하지 마세요.** 릴레이를 안 타도 화면은 똑같이 동작할 수 있습니다.
게임을 시작한 직후 EC2에서 아래를 확인합니다.

```bash
ssh -i ~/.ssh/J15B202T.pem ubuntu@j15b202.p.ssafy.io
```

### ① 백엔드가 릴레이를 골랐는가 — 가장 중요

```bash
sudo docker logs --since 5m metagame-backend 2>&1 | grep -E "game start|same network"
```

**성공이면 이렇게 나옵니다:**

```
game start: room=XXXX players=2 distinctIps=2 localIps=0 decision=relay
same network 판별: 공인IP종류=2 · 같은랜대역=false
```

| 나온 값 | 뜻 |
| --- | --- |
| `decision=relay` | ✅ 릴레이를 탔습니다. 이게 목표입니다 |
| `decision=direct(same network)` | ❌ **같은 공인 IP 입니다.** 망을 진짜로 나눠야 합니다 |
| `decision=direct(relay failed)` | ❌ 릴레이를 쓰려 했는데 실패. ②③ 을 보세요 |
| `localIps=`가 0 이 아님 | ❌ nginx가 `X-Forwarded-For`를 안 넘기고 있습니다 |

### ② 릴레이에 세션이 생겼는가

```bash
curl -s http://127.0.0.1:17779/sessions | python3 -m json.tool
```

세션이 하나 있고 사람이 2명이면 정상입니다.

### ③ 패킷이 실제로 오가는가

```bash
curl -s http://127.0.0.1:17779/health
```

`stats`의 `in`·`out`이 **계속 늘어나면** 실제로 중계되고 있는 것입니다.
게임을 움직이면서 두 번 찍어 비교하세요.

```bash
journalctl -u metagame-relay -f
```

방장 등록과 참가자 `connId` 배정이 실시간으로 찍힙니다.

## 4. 안 되면 — 이 순서로 보세요

릴레이 선택·세션 생성·호스트 등록·참가자 배정을 로그로 구분해 확인합니다. -298의 진단 이후 추가된 관측 경로입니다.

| 증상 | 먼저 볼 것 |
| --- | --- |
| `decision=direct(same network)` | 두 사람의 `curl ifconfig.me`가 정말 다른가 |
| `decision=direct(relay failed)` | 백엔드 로그의 `local relay` 경고 줄. 릴레이 프로세스가 살아 있는가(`systemctl is-active metagame-relay`) |
| 세션은 생겼는데 안 붙음 | `journalctl -u metagame-relay -f` — 방장 등록이 찍히는가 |
| 한쪽만 안 보임 | 같은 로그에서 그 사람의 `connId` 배정이 찍히는가 |
| 아예 접속이 안 됨 | UDP 17778 이 막힌 망일 수 있습니다. 다른 망으로 바꿔서 재시도 |

문제를 보고할 때는 사용한 빌드, 접속 시각, 두 PC의 네트워크 조건과 관련 로그를 함께 남깁니다.

## 6. 호스트/참가자 갈림 QA — 로그로 판정한다 (`-654`)

접속이 되는지가 아니라 **호스트와 참가자가 같은 세계를 보고 있는지**를 봅니다.
사람이 표에 ✅ 를 적는 대신 **두 로그를 기계로 대조**합니다 — 두 화면을 동시에 볼 수
없다는 것이 이 검증의 원래 문제였습니다(`-352`).

### 6-1. 빌드 — MR 의 버튼 하나

1. 브랜치를 올리고 MR 을 엽니다
2. 파이프라인의 **`build-devbuild`** 버튼을 누릅니다 (수동 실행)
3. `qa-<MR번호>-<커밋>` 이름의 zip 이 나옵니다

이 빌드는 **개발 백엔드(`/dev`)를 봅니다**(`SPACE_DEV: "1"`) — QA 플레이가 실유저
데이터에 섞이지 않습니다.

> ⚠ **처음 누르면 40~80분 걸릴 수 있습니다**(`-664`). GitLab Runner 는 보호 브랜치와
> 비보호 ref 에 **다른 빌드 볼륨**을 주는데, Unity 셰이더 캐시가 그 안에 있습니다.
> MR 빌드는 비보호 쪽이라 **한동안 안 누르면 캐시가 식습니다** — 그때 셰이더 변형
> 1000여 개를 새로 컴파일합니다. 실측: 식은 날 40~80분, 그 뒤 3.5~5.2분.
> 급하면 **새벽 스케줄을 수동 실행**해서 develop(보호·따뜻함) 기준으로 받으세요 —
> 4분이면 나옵니다. 다만 개발 서버 배포가 같이 돕니다.

> **진단은 저절로 켜집니다**(`-658`). 예전에는 양쪽 다 `-netdiag` 를 붙여야 했는데,
> 한 사람만 잊어도 짝지을 줄이 없어 **그 판이 통째로 버려집니다** — 다 놀고 난 뒤에
> 알게 됩니다. 그래서 `qa-` 로 시작하는 빌드는 스스로 켭니다. 릴리스와 새벽 개발
> 빌드는 그대로 꺼져 있습니다.

### 6-2. 플레이

- **두 사람**이 각자 PC 에서 그 zip 을 풀어 실행합니다 (한 명이 방을 만들어 호스트)
- 한 판을 끝까지 돕니다. 운석이 떨어지고 착지할 때까지 충분히 진행합니다
- **셋이면 더 좋습니다** — 제3자 시점(남이 하는 것을 보는 화면)은 2인에서 안 생깁니다

### 6-3. 로그 모으기

두 사람 모두 아래 파일을 가져옵니다.

```
%USERPROFILE%\AppData\LocalLow\Not This Planet\Not This Planet\Player.log
```

### 6-4. 대조

```
python scripts/ci/netdiag.py <호스트Player.log> <참가자Player.log>
```

**문제인 것**

**마지막 줄만 보면 됩니다.** 도구가 `✅ 판정:` 또는 `❌ 판정: …` 을 찍고 종료 코드로도
말합니다 — `0` 통과 · `1` 갈렸거나 판정 불가 · `2` 로그 파일을 못 찾음.

| 나오는 것 | 뜻 |
|---|---|
| `❌ 판정: 체크섬이 갈렸다` | **세계의 자세가 실제로 달랐다.** 가장 무거운 신호다 |
| `❌ 판정: 나르는 목록의 개수가 다르다` | 그 순간 자세가 **하나도** 적용되지 않는다. 두 창이 같은 빌드인지 먼저 본다 |
| `❌ 판정: 나르는 목록의 순서·이름이 다르다` | 남의 자리에 값이 들어간다 |
| `❌ 견줄 판을 고르지 못했다` | 두 로그가 **같은 판을 담고 있지 않다.** 틀린 답을 내지 않으려고 멈춘 것이다 |
| `⚠ live` · `pending` · `scars` | 개수가 엇갈렸다 — **참고일 뿐이다.** 갈렸는지는 체크섬이 판정한다 |

**판을 고르는 규칙** (`-685`). 한 로그에는 한 실행의 여러 판이 들어 있습니다 — 솔로로
둘러보다 방을 만들고, 나가서 남의 방에 들어갑니다. 도구는 `t` 가 되감기면 새 판으로
가르고, 호스트 판 × 참가자 판 중 **겹치는 묶음이 가장 많은 짝**을 고릅니다.

| | |
|---|---|
| 같은 판인지 가르는 자 | 같은 판이면 두 로그의 `t` 차이가 **일정합니다**(각자 켠 시각만큼 밀려 있습니다). **5초** 넘게 흔들리면 그 짝은 쓰지 않습니다 — 묶음 번호는 판마다 0 에서 다시 세므로 서로 다른 판이 우연히 겹칩니다 |
| 최소 표본 | 겹치는 묶음 **20개**. 그 아래면 수치를 아예 내지 않습니다 — 몇 개 겹친 것으로 높은 일치율을 내던 것이 2026-09-22 에 실제로 틀린 답을 만들었습니다(`97% 일치` → 같은 판으로 다시 재니 `121개 전부 일치`) |
| 개수 ±1 | **지연입니다**(`-654` Q0). 참가자는 ~100ms 늦게 받으므로 그 순간 날아가는 운석 하나가 엇갈립니다. 공세 묶음이 한 번에 여섯 개씩 나오는 순간에는 둘셋까지 벌어집니다 |

**문제가 아닌 것**

- **참가자가 늦게 받는 것** — 호스트는 지연이 0이고 참가자는 ~166ms 입니다. 리슨 서버
  구조의 대가이고 **사양으로 정했습니다**(2026-09-21 기획 확인, `-654` Q0).
  `RTT`·`buftime`·`buf` 는 그 값을 보는 칸이지 합격/불합격 칸이 아닙니다
- 참가자 쪽 `live` 가 호스트와 같은데 화면의 돌이 조금 뒤처져 보이는 것 — 같은 이유

### 6-5. 로그가 답하지 못하는 것 — 이건 눈으로 봅니다

대조는 **물체가 양쪽에 있는가·같은 자세인가**를 증명합니다. 아래는 그 바깥이라 사람이
봐야 합니다. 과거에 실제로 이 모양으로 깨졌던 것들입니다.

| 볼 것 | 과거 이슈 |
|---|---|
| 착지한 돌에 **몸이 막히는가** (통과하지 않는가) | `-658` |
| 피해를 입었을 때 **빨간 테두리**가 보이는가 | `-513` |
| 죽었을 때 **3인칭 전환**이 되는가 | `-511` |
| 동료를 **일으킬 수 있는가**, 게이지가 보이는가 (**일으켜지는 쪽 화면도**) | `-448` · `-378` |
| UFO 빔이 **탄 사람 말고도** 보이는가 | `-505` |
| 저중력장에 뜬 부품이 **떨리지 않는가** | `-538` |
| 탈것에 타면 **조종석 시점**이 되는가 (래그돌을 따라가지 않는가) | `-434` |

**한 동작마다 여섯 칸을 채웁니다** — 호스트가 할 때와 참가자가 할 때 각각, 호스트 화면 ·
행위자 화면 · 제3자 화면. 대상이 따로 있는 동작(살리기·던지기·피해)은 **대상 화면**이
한 칸 더 붙습니다. `-448` 이 그 칸에서만 깨져 있었습니다.

어느 동작이 어느 방식으로 맞춰지는지는 [동기화 정책](network-sync-policy.md) §3 에,
호스트와 참가자가 각각 무엇을 보는지는
[호스트/참가자 현황](records/S15P21B202-654-host-client-inventory.md)에 있습니다.
