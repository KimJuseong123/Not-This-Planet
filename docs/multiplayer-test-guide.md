## 0. 릴레이 테스트에 필요한 네트워크 조건

정확히는 **서로 다른 공인 IP** 여야 합니다. 백엔드가 이렇게 판단합니다
(`GameWebSocketHandler.sameNetwork`):

| 조건 | 판정 |
| --- | --- |
| 사람이 2명 미만 | 같은 망 → **직접 접속** |
| 두 사람의 **공인 IP가 같음** | 같은 망 → **직접 접속** |
| 공인 IP가 다르고, 사설 대역도 다름 | **릴레이** |

### ⚠ 가장 흔한 함정

**교육장에서 자리만 떨어져 앉는 것으로는 안 됩니다.** 같은 건물 WiFi는 LAN이 달라도
**밖에서 보이는 공인 IP가 하나**입니다. 그러면 `직접 접속`으로 빠지고 **릴레이는 한 줄도
실행되지 않습니다.** 같은 망에서의 접속 성공만으로는 릴레이 동작을 확인할 수 없습니다.

### 가장 확실한 조합

> **한 명은 교육장 WiFi, 다른 한 명은 휴대폰 핫스팟(LTE/5G).**

집·카페 회선도 사용할 수 있습니다. 선택한 두 회선의 공인 IP가 다른지 아래 명령으로 확인합니다.

## 1. 준비

| | 무엇 |
| --- | --- |
| 사람 | **2명** (각자 PC) |
| 망 | 서로 다른 공인 IP (위 참고) |
| 클라이언트 | Unity 에디터로 `Lobby.unity` 실행 또는 빌드한 실행 파일 |
| 서버 주소 | **설정할 것 없음** — `j15b202.p.ssafy.io`가 기본값입니다 |

각자 공인 IP 확인 (달라야 합니다):

```
curl https://ifconfig.me
```

<a id="section-3"></a>

## 2. 절차

### 2-1. 먼저 같은 망에서 한 번 (기준선)

**릴레이를 시험하기 전에 기본 멀티플레이가 되는지부터 확인합니다.**이 단계를 건너뛰면,
나중에 실패했을 때 릴레이 탓인지 게임 탓인지 구분할 수 없습니다.

1. 두 사람 다 **같은 WiFi**에서 클라이언트 실행
2. A가 방 만들기 → 방 코드 확인
3. B가 그 코드로 입장
4. A가 시작
5. **서로 움직이는 게 보이는지** 확인

여기서 안 되면 릴레이 이전 문제입니다. 기본 접속 문제를 먼저 해결하고 재검증합니다.

### 2-2. 서로 다른 망에서 릴레이 확인

1. 한 명이 **휴대폰 핫스팟으로 전환**
2. 위 1~5 를 그대로 반복
3. 몇 분 돌아다니며 확인:
   - 상대가 **끊기지 않고** 계속 보이는가
   - 움직임이 **튀지 않는가**
   - 물건을 잡거나 상호작용이 서로에게 보이는가

## 3. 무엇을 봐야 성공인가

**화면만 보고 판단하지 마세요.** 릴레이를 안 타도 화면은 똑같이 동작할 수 있습니다.
게임을 시작한 직후 EC2에서 아래를 확인합니다.

```bash
ssh -i ~/.ssh/J15B202T.pem ubuntu@j15b202.p.ssafy.io
```

### ① 백엔드가 릴레이를 골랐는가 — 가장 중요

```bash
sudo docker logs --since 5m metagame-backend 2>&1 | grep -E "game start|same network"
```

**성공이면 이렇게 나옵니다:**

```
game start: room=XXXX players=2 distinctIps=2 localIps=0 decision=relay
same network 판별: 공인IP종류=2 · 같은랜대역=false
```

| 나온 값 | 뜻 |
| --- | --- |
| `decision=relay` | ✅ 릴레이를 탔습니다. 이게 목표입니다 |
| `decision=direct(same network)` | ❌ **같은 공인 IP 입니다.** 망을 진짜로 나눠야 합니다 |
| `decision=direct(relay failed)` | ❌ 릴레이를 쓰려 했는데 실패. ②③ 을 보세요 |
| `localIps=`가 0 이 아님 | ❌ nginx가 `X-Forwarded-For`를 안 넘기고 있습니다 |

### ② 릴레이에 세션이 생겼는가

```bash
curl -s http://127.0.0.1:17779/sessions | python3 -m json.tool
```

세션이 하나 있고 사람이 2명이면 정상입니다.

### ③ 패킷이 실제로 오가는가

```bash
curl -s http://127.0.0.1:17779/health
```

`stats`의 `in`·`out`이 **계속 늘어나면** 실제로 중계되고 있는 것입니다.
게임을 움직이면서 두 번 찍어 비교하세요.

```bash
journalctl -u metagame-relay -f
```

방장 등록과 참가자 `connId` 배정이 실시간으로 찍힙니다.

<a id="section-5"></a>

## 4. 안 되면 — 이 순서로 보세요

릴레이 선택·세션 생성·호스트 등록·참가자 배정을 로그로 구분해 확인합니다. -298의 진단 이후 추가된 관측 경로입니다.

| 증상 | 먼저 볼 것 |
| --- | --- |
| `decision=direct(same network)` | 두 사람의 `curl ifconfig.me`가 정말 다른가 |
| `decision=direct(relay failed)` | 백엔드 로그의 `local relay` 경고 줄. 릴레이 프로세스가 살아 있는가(`systemctl is-active metagame-relay`) |
| 세션은 생겼는데 안 붙음 | `journalctl -u metagame-relay -f` — 방장 등록이 찍히는가 |
| 한쪽만 안 보임 | 같은 로그에서 그 사람의 `connId` 배정이 찍히는가 |
| 아예 접속이 안 됨 | UDP 17778 이 막힌 망일 수 있습니다. 다른 망으로 바꿔서 재시도 |

문제를 보고할 때는 사용한 빌드, 접속 시각, 두 PC의 네트워크 조건과 관련 로그를 함께 남깁니다.

## 5. 잘 되면 기록할 것 (`-151`)

접속 성공 후 아래 항목을 측정하고, -151의 완료 조건과 대조합니다.

- 조작 지연 체감 (내 입력이 화면에 반영되는 느낌)
- 상대 움직임이 튀는지 · Send Rate를 조정할 필요가 있는지
- 몇 분간 유지되는지 (끊김 여부)
- **한 명이 WiFi를 20초 껐다 켜면** 재접속되는지 (`-150`의 30초 유예 확인)

기록은 [멀티플레이 측정 기록](records/S15P21B202-151-multiplay-measurement.md) 에 남깁니다.
