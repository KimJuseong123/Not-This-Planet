# E2E 점검표 — 워크플로우 최종 검증 (v1.8 · 2026-09-14)

협업 워크플로우와 자동화의 동작을 재현하고 결과를 기록하는 점검표입니다. 시작 전 준비를 마친 뒤 A~D를 이슈 하나의 흐름으로 진행하고, E·F에서 알림과 복구 동작을 확인합니다.

**기대 결과는 판정 기준, 결과 칸은 날짜별 관측 기록**입니다. 기존 성공 표시를 이번 실행의 성공으로 간주하지 말고 새 실행 날짜와 결과를 추가합니다. 게임 플레이 검증은 [멀티플레이 안내](multiplayer-test-guide.md)와 [기능별 기록](records/README.md)에서 확인합니다.

[문서 안내](README.md) · 선행: [작업 흐름](workflow.md)

> 워크플로우에서 **어긋날 수 있는 상황(S01~S33)** 을 실제로 한 번씩 밟아 보는 표. 시나리오 정의는 이 문서 맨 끝 **첨부**에 있다(이 표와 같은 문서에 두어 점검표만 보고도 무엇을 재현하는지 알 수 있게 했다). 흐름 자체의 설명은 [workflow.md](./workflow.md).
> **각 항목: 준비 → 행동 → 기대 결과(대개 30초 내) → 어디서 확인**. 결과 칸에 ✅/❌ 와 비고를 적는다.
> 🔑 = 팀장(Maintainer) 권한이 필요한 항목. 나머지는 팀원 계정으로 할 수 있다.
> 테스트용 이슈는 `[Infra] E2E-…` 제목으로 만들고 끝나면 삭제한다(프로젝트 관리자). 테스트 MR 은 마지막에 팀장이 머지 또는 닫는다.

**시작 전 준비**

- 로컬 클론이 `develop` 최신 상태여야 한다 — `git switch develop && git pull --ff-only --prune`
  - 훅(`.githooks/pre-push`)과 MR 템플릿은 **작업 트리의 파일**이라 develop에 머지된 최신본이 로컬에 있어야 결과가 맞고, 테스트 브랜치도 최신 develop에서 갈라져야 한다
  - `pull`이 fetch를 포함하므로 앞에 따로 `git fetch`를 할 필요는 없다. `--prune`은 머지 후 자동 삭제된 원격 브랜치의 유령 참조를 정리하고, `--ff-only`는 보호 브랜치인 develop에 실수로 머지 커밋이 생기는 것을 막는다
- `git config core.hooksPath .githooks` · `git lfs install --skip-repo` 완료
  - `--skip-repo` 없이 `git lfs install`을 하면 `Hook already exists: pre-push` 경고가 난다(정상). `core.hooksPath` 때문에 git-lfs가 우리 훅을 덮어쓰려다 멈춘 것이며, **`git lfs update --force`는 절대 실행하지 말 것**(브랜치명 검사와 LFS 연계가 든 `.githooks/pre-push`가 지워진다). 필요한 LFS 필터는 `--skip-repo`로 설정되고, 업로드는 우리 훅이 `git lfs pre-push`를 호출해 처리한다
- 화면 4개 열어 두기: Jira 백로그·보드 / GitLab MR 목록 / GitLab 파이프라인 / Mattermost 알림 채널
- **CI 규칙은 MR 소스 브랜치의 스크립트로 돌아간다** — 새 검사가 develop에 머지돼도, 이미 열려 있는 MR은 그 브랜치가 develop을 받아야 새 규칙이 적용된다(2026-08-28 MR !42 사례). 아래 "머지 후 적용" 표시가 붙은 항목은 그래서다
- 선행 조건: **E3·F5** 아침 점검 스케줄 **등록 완료**(id 28 · `30 9 * * 1-5` Asia/Seoul · develop — **평일** 09:30) · 개발 서버 새벽 배포 **id 32**(`0 4 * * *`) · **master 는 릴리스 MR 두 번(09-11 · 09-14)으로 정렬됐다** — 훅·CI·MR 템플릿이 master 에도 있으므로 `B12`·`B12c` 의 선행 조건은 **이미 충족**이다
- 권장 순서: A → B → C → D를 **테스트 이슈 한 줄기로** 이어서 진행하고, E·F는 그 과정에서 나온 알림·상태로 확인
- 테스트 이슈에 활성 스프린트를 고르면 Jira가 "이 업무 항목을 만들면 활성 스프린트의 범위에 영향을 줍니다" 라고 안내한다 — **정상**(진행 중 스프린트에 항목을 넣으면 스프린트 리포트에 범위 변경으로 기록된다는 뜻). 스토리 포인트를 비워 두면 번다운에는 영향이 없고, 마무리에서 테스트 이슈를 삭제하면 목록에서도 사라진다

## G. 배포 · 릴리스 (S34~S38)

> **머지된 뒤 사람 손에 닿기까지.** A~D 가 "develop 에 들어가기까지" 라면 여기는 그 다음이다. 이 절이 없던 동안 "런처가 최신이냐" 같은 물음에 매번 파이프라인을 뒤져야 했다(`-518`).
