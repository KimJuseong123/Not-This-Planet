**시작 전 준비**

- 로컬 클론이 `develop` 최신 상태여야 한다 — `git switch develop && git pull --ff-only --prune`
  - 훅(`.githooks/pre-push`)과 MR 템플릿은 **작업 트리의 파일**이라 develop 에 머지된 최신본이 로컬에 있어야 결과가 맞고, 테스트 브랜치도 최신 develop 에서 갈라져야 한다
  - `pull` 이 fetch 를 포함하므로 앞에 따로 `git fetch` 를 할 필요는 없다. `--prune` 은 머지 후 자동 삭제된 원격 브랜치의 유령 참조를 정리하고, `--ff-only` 는 보호 브랜치인 develop 에 실수로 머지 커밋이 생기는 것을 막는다
- `git config core.hooksPath .githooks` · `git lfs install --skip-repo` 완료
  - `--skip-repo` 없이 `git lfs install` 을 하면 `Hook already exists: pre-push` 경고가 난다(정상). `core.hooksPath` 때문에 git-lfs 가 우리 훅을 덮어쓰려다 멈춘 것이며, **`git lfs update --force` 는 절대 실행하지 말 것**(브랜치명 검사와 LFS 연계가 든 `.githooks/pre-push` 가 지워진다). 필요한 LFS 필터는 `--skip-repo` 로 설정되고, 업로드는 우리 훅이 `git lfs pre-push` 를 호출해 처리한다
- 화면 4개 열어 두기: Jira 백로그·보드 / GitLab MR 목록 / GitLab 파이프라인 / Mattermost 알림 채널
- **CI 규칙은 MR 소스 브랜치의 스크립트로 돌아간다** — 새 검사가 develop 에 머지돼도, 이미 열려 있는 MR 은 그 브랜치가 develop 을 받아야 새 규칙이 적용된다(2026-08-28 MR !42 사례). 아래 "머지 후 적용" 표시가 붙은 항목은 그래서다
- 선행 조건: **E3·F5** 아침 점검 스케줄은 **등록 완료**(2026-08-28, `30 9 * * *` Asia/Seoul, develop — 매일 09:30. 평일만 원하면 크론을 `30 9 * * 1-5` 로) · 다이제스트의 `🔗 머지됐는데 완료 안 된 이슈` 블록은 develop 에 반영됨 ✅ · **B12 는 master 정렬(팀장의 develop→master 릴리즈 MR) 후**, **B12c 는 MR !73 머지 후**, **B15 는 MR !84 머지 후**, **E3b 는 MR !75 머지 후**에 재현된다
- 권장 순서: A → B → C → D 를 **테스트 이슈 한 줄기로** 이어서 진행하고, E·F 는 그 과정에서 나온 알림·상태로 확인
- 테스트 이슈에 활성 스프린트를 고르면 Jira 가 "이 업무 항목을 만들면 활성 스프린트의 범위에 영향을 줍니다" 라고 안내한다 — **정상**(진행 중 스프린트에 항목을 넣으면 스프린트 리포트에 범위 변경으로 기록된다는 뜻). 스토리 포인트를 비워 두면 번다운에는 영향이 없고, 마무리에서 테스트 이슈를 삭제하면 목록에서도 사라진다
