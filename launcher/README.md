# 런처 — 바뀐 파일만 받아 최신 배포 버전을 맞춘다 (S15P21B202-406)

[문서 안내](../docs/README.md) → 배포

사용자가 버전마다 zip 을 받아 압축을 풀고 옛 폴더를 지우는 일을 없앱니다.

## 사용자가 하는 일

`NotThisPlanetLauncher.exe` 를 **빈 폴더**에 두고 실행합니다. 런처가 옆에 `game/` 을
만들어 게임을 받고, 다음부터는 켤 때마다 바뀐 파일만 받아 맞춥니다.

```
받은폴더/
  NotThisPlanetLauncher.exe   ← 이것을 실행한다
  game/                       ← 런처가 만든다. 여기를 직접 건드리지 않는다
```

**게임이 켜져 있으면 업데이트가 안 됩니다** — 실행 중인 파일은 바꿀 수 없습니다.
런처가 그 사유를 말하고 멈춥니다.

## 얼마나 덜 받나 (2026-09-11 실측)

| | 받는 양 |
| --- | --- |
| 첫 설치 | **156.4 MB** — 지금 zip 을 받는 것과 같다 |
| 코드만 바뀐 릴리스 | **6.5 MB** — 전체의 4.2% |

v1.0.0(211 파일 · 355.5 MB)에 코드 4개 + `resources.assets` 를 바꾸고 파일 하나를
더하고 하나를 지운 판을 만들어 쟀습니다. 런처가 **받기 6개 · 지우기 1개 · 그대로
205개**로 판정했습니다. 서버 디스크는 버전 2개를 담고 **164 MB** 입니다(따로 쌓으면 312 MB).

한계는 정직하게: **아트가 바뀌는 릴리스는 `sharedassets1.assets.resS` 187 MB 를 다시
받습니다.** `resources.assets` 13.3 MB 는 씬을 조금만 건드려도 통째로 바뀌어 거의
매번 실립니다. 바이너리 델타(bsdiff 류)는 하지 않습니다 — 남는 절감이 10 MB 대인데
버전쌍마다 패치를 만들고 옛 버전을 보관하고 실패 시 폴백 경로를 다 만들어야 합니다.

## 서버 쪽 구조

`nginx` 가 `/builds/` 로 내보내는 폴더입니다(`-405`).

```
/var/www/metagame-builds/
  latest.json              ← **바뀌는 파일은 이것 하나뿐이다**
  manifest/v1.0.0.json     경로 → sha256 목록 + 실행 파일 이름
  files/<sha256>.gz        파일을 해시 이름으로, gzip 해서 저장
```

**롤백은 `latest.json` 을 옛 버전으로 되돌리는 것입니다.** 매니페스트와 파일은 한 번
쓰면 고치지 않습니다(해시가 이름이라 고칠 수도 없습니다). 지금은 나쁜 릴리스가 나가면
되돌릴 절차가 없는데, 이것이 실제로는 가장 큰 이득일 수 있습니다.

**gzip 으로 두는 이유.** 저장소는 파일을 그대로 두므로 압축이 없습니다 — v1.0.0 이
압축 없이 355.5 MB, zip 은 156 MB 였습니다. 그대로 두면 **첫 설치가 지금보다 2배 이상
무거워집니다.** 런처가 받아서 풀고, **해시는 푼 뒤의 바이트로** 확인합니다. nginx
`gzip_static` 을 쓰지 않은 이유는 압축본과 원본을 둘 다 둬야 해서 디스크가 두 배가
되기 때문입니다.

## 새 버전을 올리는 절차

```sh
# ① 빌드 폴더 → 매니페스트 + 저장소 (올려만 두고 전환은 하지 않는다)
python scripts/launcher/make_manifest.py <빌드폴더> v1.0.1 \
    --out /var/www/metagame-builds --no-latest

# ② 확인한 뒤 최신 표시를 옮긴다
python scripts/launcher/make_manifest.py <빌드폴더> v1.0.1 \
    --out /var/www/metagame-builds
```

`--no-latest` 로 먼저 올리는 이유: 파일이 다 올라가기 전에 `latest.json` 이 새 버전을
가리키면, 그 사이에 켠 사람이 **없는 파일을 받으려 합니다.** 런처는 그때
`latest.json` 과 매니페스트의 버전이 어긋나는 것을 보고 멈추지만, 애초에 만들지
않는 편이 낫습니다.

`--dry-run` 으로 무엇이 올라갈지 먼저 볼 수 있습니다.

## 런처를 만드는 법

```sh
cd launcher
dotnet publish -c Release          # bin/Release/net10.0/win-x64/publish/
```

`.NET` 없이 도는 단일 exe 로 나옵니다(self-contained). **받는 사람에게 ".NET 을 먼저
설치하세요" 를 요구하면 런처가 없애려던 수동 절차가 그대로 남습니다.**

`PublishTrimmed` 는 켜지 않습니다 — 리플렉션 경로가 조용히 깨질 수 있고, 런처가
조용히 깨지는 것은 사용자가 원인을 알 수 없는 종류의 고장입니다.

**런처는 CI 에 넣지 않습니다.** 릴리스마다 바뀌는 물건이 아니고, 실행 중인 자기
자신을 덮어쓸 수 없습니다. 한 번 만들어 올려 두고 런처 자체 갱신은 안내만 합니다.

## 검사

```sh
python scripts/ci/tests/test_launcher_manifest.py   # 매니페스트 도구 (ci-tests 가 자동으로 돈다)
NotThisPlanetLauncher.exe --selfcheck               # 런처의 경로·해시·매니페스트 판정
NotThisPlanetLauncher.exe --check                   # 무엇을 받고 지울지만 보고 끝낸다
```

`--selfcheck` 가 **배포되는 그 exe 안에서** 돕니다. 테스트 프로젝트를 따로 두면
배포 산출물과 검사 대상이 갈립니다.

막는 것: 매니페스트의 `path` 는 서버에서 온 문자열이고 런처는 **그것으로 파일을
씁니다.** `..`·절대 경로·드라이브 지정·UNC·백슬래시·끝의 점·대소문자만 다른 중복을
전부 거부합니다. 만드는 쪽(`make_manifest.py`)도 같은 검사를 하지만 **두 쪽 다**
해야 합니다 — 서버가 바뀔 수 있고 중간에서 끼어들 수도 있습니다.

## 런처가 하지 않는 일 — 구버전 막기

그건 **서버 게이트**(`-404`)의 몫입니다. 런처는 우회됩니다 — 압축 푼 폴더의 exe 를
직접 더블클릭하는 것이 가장 흔하고, 그게 정확히 막아야 하는 경우입니다.

그래서 런처는 **서버에 못 닿으면 막지 않고 그냥 실행시킵니다.** EC2 는 단일 장애점이고
(2026-09-10 팀 확인), 서버가 한 번 딸꾹질할 때 전원이 게임을 못 켜는 것이 더 나쁩니다.
매니페스트를 신뢰할 수 없을 때도 **파일을 하나도 건드리지 않고** 있는 것으로 실행합니다 —
반쯤 적용된 폴더가 가장 고치기 어렵습니다.

## 알려진 것

- **코드 서명이 없어 SmartScreen 경고가 납니다.** 지금 zip 을 받아 실행할 때도 같은
  경고를 받고 있으니 새 문제는 아니지만, 런처는 *다른 exe 를 받아서 실행하는*
  프로그램이라 백신이 더 민감합니다
- 자동 배포는 아직 없습니다 — 위 절차를 사람이 돌립니다(`-452` 에 이어집니다)
