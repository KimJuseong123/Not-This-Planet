# 런처 — 바뀐 파일만 받아 최신 배포 버전을 맞춘다 (S15P21B202-406)

[문서 안내](../docs/README.md) → 배포

사용자가 버전마다 zip 을 받아 압축을 풀고 옛 폴더를 지우는 일을 없앱니다.

## 사용자가 하는 일

`NotThisPlanetLauncher.exe` 를 **빈 폴더**에 두고 실행합니다. 런처가 옆에 `game/` 을
만들어 게임을 받고, 다음부터는 켤 때마다 바뀐 파일만 받아 맞춥니다.

```
받은폴더/
  NotThisPlanetLauncher.exe   ← 이것을 실행한다
  game/                       ← 런처가 만든다. 여기를 직접 건드리지 않는다
```

**게임이 켜져 있으면 업데이트가 안 됩니다** — 실행 중인 파일은 바꿀 수 없습니다.
런처가 그 사유를 말하고 멈춥니다.

## 얼마나 덜 받나 (2026-09-11 실측)

| | 받는 양 |
| --- | --- |
| 첫 설치 | **156.4 MB** — 지금 zip 을 받는 것과 같다 |
| 코드만 바뀐 릴리스 | **6.5 MB** — 전체의 4.2% |

v1.0.0(211 파일 · 355.5 MB)에 코드 4개 + `resources.assets` 를 바꾸고 파일 하나를
더하고 하나를 지운 판을 만들어 쟀습니다. 런처가 **받기 6개 · 지우기 1개 · 그대로
205개**로 판정했습니다. 서버 디스크는 버전 2개를 담고 **164 MB** 입니다(따로 쌓으면 312 MB).

한계는 정직하게: **아트가 바뀌는 릴리스는 `sharedassets1.assets.resS` 187 MB 를 다시
받습니다.** `resources.assets` 13.3 MB 는 씬을 조금만 건드려도 통째로 바뀌어 거의
매번 실립니다. 바이너리 델타(bsdiff 류)는 하지 않습니다 — 남는 절감이 10 MB 대인데
버전쌍마다 패치를 만들고 옛 버전을 보관하고 실패 시 폴백 경로를 다 만들어야 합니다.

## 개발 모드 — `--dev`

팀이 쓰는 모드입니다. **목록에서 골라 되돌립니다**(2026-09-10 팀 결정, `-405` §④).

```sh
NotThisPlanetLauncher.exe --dev                  # 목록을 보여 주고 고르게 한다
NotThisPlanetLauncher.exe --dev --version v1.0.1 # 바로 그 버전
```

**exe 를 두 개로 나누지 않은 이유**: 백신이 서명 없는 exe 를 막습니다(`-456` — AhnLab
V3 가 실제로 런처와 게임 실행을 막았고 **테스터 전원이 같은 백신**입니다). exe 가
둘이면 화이트리스트 등재도 두 번, 사용자의 "한 번만 실행" 도 두 번입니다. 그 비용이
"섞일 여지" 보다 크다고 판단했습니다(2026-09-11 팀 결정).

**대신 섞이지 않게 세 가지를 둡니다.**

| 장치 | 왜 |
| --- | --- |
| 화면에 크게 알린다 | 모르고 켜면 안 됩니다 |
| **게임 폴더가 다르다** (`game-dev/`) | 배포용 설치를 덮어쓰지 않습니다 — 실수로 켜 봐도 원래 것이 남습니다 |
| 게임에 `-backend=<dev>` 를 넘긴다 | 실행 인자가 가장 센 우선순위라(`-284`) 빌드 스탬프가 prod 여도 **개발 서버**를 가리킵니다. 실유저 데이터를 건드리지 않습니다 |

**없는 버전을 달라 하면 멈춥니다** — 조용히 최신으로 바꿔 주면 "옛 버전으로 재현해
본다" 는 목적이 사라집니다.

배포 모드에는 `--version` 이 없습니다. 고를 여지를 주면 그것이 곧 **구버전 잔류 경로**가
됩니다.

## 서버 쪽 구조

`nginx` 가 `/builds/` 로 내보내는 폴더입니다(`-405`).

```
/var/www/metagame-builds/
  latest.json              ← 배포 런처가 보는 최신 버전
  versions.json            ← 개발 런처가 골라 되돌릴 버전 목록 (최근 10개)
  launcher.json            ← 런처의 최신 버전 (+ 최소 허용 버전)
  manifest/v1.0.0.json     경로 → sha256 목록 + 실행 파일 이름
  files/<sha256>.gz        파일을 해시 이름으로, gzip 해서 저장
```

`versions.json` 이 따로 있는 이유: **`/builds/` 의 디렉터리 목록을 닫았습니다**(`-454`).
목록 파일이 없으면 개발 런처가 되돌릴 버전을 알 수 없습니다.

### 채널 (`-460`)

QA 는 두 번 일어납니다 — **머지 뒤**(합쳐진 상태가 되나)와 **머지 전**(이 MR 이 그 버그를
고쳤나). 릴리스 버전만으로는 둘 다 못 합니다. 그래서 셋으로 나눕니다.

| 채널 | 버전 이름 | 어디서 | 누가 본다 |
| --- | --- | --- | --- |
| `release` | `v1.0.0` | master 머지 | **배포 런처와 개발 런처 둘 다** |
| `dev` | `dev-20260914-1a2b3c4` | develop 새벽 빌드 | 개발 런처만 |
| `qa` | `qa-401-1a2b3c4` | MR 의 버튼 | 개발 런처만 |

**채널은 버전 이름에서 나옵니다.** 따로 적어 두지 않는 이유: 이름과 채널을 두 곳에 두면
어긋나고, 어긋나면 **배포 런처가 dev 빌드를 집습니다.**

```
latest.json  · versions.json       ← 배포 런처가 보는 것. release 만 담긴다
dev-latest.json · dev-versions.json ← 개발 런처가 더 보는 것. dev·qa 가 담긴다
```

개발 런처는 **둘 다 읽어 합칩니다.** 개발 목록이 앞이라 `Enter`(= 최신)가 "방금
develop" 을 고릅니다. 릴리스도 같은 화면에 있어서 "이 버그가 v1.0.0 에도 있었나" 가
됩니다. **개발 목록이 없는 서버에서도 그대로 동작합니다** — 404 면 릴리스만 보입니다.

**저장소(`files/`)는 셋이 공유합니다.** 채널이 달라도 대부분의 파일이 같아서(2026-09-10
실측: 서로 다른 두 빌드가 321/339 파일 바이트 동일) 나눈다고 디스크가 배로 늘지 않습니다.

**보관(`--keep`)은 채널마다 따로 셉니다.** 섞어 세면 매일 쌓이는 dev 빌드가 릴리스 10개를
밀어냅니다. 반대로 **회수 판정은 채널을 가리지 않습니다** — 한 채널이라도 빼고 세면 그
채널이 쓰는 파일이 "아무도 안 쓴다" 로 보여 지워지고, 해시가 이름이라 되살릴 수 없습니다.

**바뀌는 파일은 위 두 개뿐입니다.** 런처 exe 도 `files/` 안에 같은 형식으로
들어갑니다 — 받는 방식이 이미 있는데 런처 전용 경로를 따로 만들면 받는 코드가
두 벌이 되고 그중 하나는 덜 검사받습니다.

**롤백은 `latest.json` 을 옛 버전으로 되돌리는 것입니다.** 매니페스트와 파일은 한 번
쓰면 고치지 않습니다(해시가 이름이라 고칠 수도 없습니다). 지금은 나쁜 릴리스가 나가면
되돌릴 절차가 없는데, 이것이 실제로는 가장 큰 이득일 수 있습니다.

**gzip 으로 두는 이유.** 저장소는 파일을 그대로 두므로 압축이 없습니다 — v1.0.0 이
압축 없이 355.5 MB, zip 은 156 MB 였습니다. 그대로 두면 **첫 설치가 지금보다 2배 이상
무거워집니다.** 런처가 받아서 풀고, **해시는 푼 뒤의 바이트로** 확인합니다. nginx
`gzip_static` 을 쓰지 않은 이유는 압축본과 원본을 둘 다 둬야 해서 디스크가 두 배가
되기 때문입니다.

## 두 버전이 모두 최신이어야 합니다

강제해야 하는 것이 **둘**입니다.

| 무엇 | 누가 강제하나 |
| --- | --- |
| **게임 버전** | 서버 게이트(`-404`) — 로그인·토큰 검증을 지나야 방에 들어오므로 우회할 수 없습니다 |
| **런처 버전** | 런처 자신 — `launcher.json` 과 견주어 **스스로 갱신**합니다 |

**왜 런처도 강제해야 하나.** 사이트에서 받아 간 런처는 사용자 PC 에 남습니다. 런처의
규약(매니페스트 형식·주소·검증 방식)이 바뀌면 옛 런처는 **조용히 틀린 일을 하거나
아무것도 못 합니다.** 게임 버전만 강제해도 런처가 낡으면 그 강제가 동작하지 않습니다.

### 런처가 자기 자신을 바꾸는 방법

**실행 중인 파일은 잠겨 있어 자기를 덮어쓸 수 없습니다.** 그래서 손을 세 번 바꿉니다.

1. 지금 런처: 새 exe 를 `.new.exe` 로 받아 **해시를 확인한 뒤** `--finish-update <내 경로> <내 PID>` 로 띄우고 **끝납니다**
2. 새 exe: 그 PID 가 사라질 때까지 기다렸다가 자기를 옛 자리에 복사하고, 옛 자리의 exe 를 띄우고 **끝납니다**
3. 제자리로 돌아온 런처: 남은 `.new.exe` 를 지우고 평소대로 돕니다

해시 확인을 **띄우기 전에** 합니다 — 여기서 틀리면 사용자가 받은 적 없는 exe 를 돌리게 됩니다.

### 언제 막나

| 상황 | 결과 |
| --- | --- |
| 서버에 못 닿음 | **막지 않습니다** — 있는 것으로 실행 |
| 낡았고 갱신 성공 | 새 런처가 이어받음 |
| 낡았고 갱신 실패, `minLauncher` 없음 | **막지 않습니다** — 경고하고 계속 |
| 낡았고 갱신 실패, `minLauncher` 보다 낮음 | **막습니다** — 받을 주소를 화면에 줍니다 |

`minLauncher` 를 올리는 것은 **"옛 런처로는 더 못 돈다"는 선언**입니다. 규약을 깨는
변경일 때만 올립니다. 그냥 고친 것이면 주지 않습니다 — 갱신은 하되 실패해도 게임은
돌게 합니다.

### 런처를 서버에 올리는 절차

```sh
cd launcher && dotnet publish -c Release -p:Version=1.0.1
python scripts/launcher/publish_launcher.py \
    launcher/bin/Release/net10.0/win-x64/publish/NotThisPlanetLauncher.exe v1.0.1 \
    --out /var/www/metagame-builds
# 규약을 깨는 변경이면 (그 전 런처를 못 쓰게 한다):
#   ... v1.0.1 --out /var/www/metagame-builds --min v1.0.1
```

`--dry-run` 으로 먼저 볼 수 있습니다. 올리는 버전보다 `--min` 이 높으면 **방금 올린
런처도 거부되므로** 도구가 거절합니다.

**런처 버전은 게임 릴리스 버전과 무관합니다.** 게임은 매주 나가도 런처는 몇 달째
그대로일 수 있습니다. 두 수를 맞추려 하면 뜻 없는 릴리스가 생깁니다.

## 새 버전을 올리는 절차

```sh
# ① 빌드 폴더 → 매니페스트 + 저장소 (올려만 두고 전환은 하지 않는다)
python scripts/launcher/make_manifest.py <빌드폴더> v1.0.1 \
    --out /var/www/metagame-builds --no-latest

# ② 확인한 뒤 최신 표시를 옮긴다
python scripts/launcher/make_manifest.py <빌드폴더> v1.0.1 \
    --out /var/www/metagame-builds
```

`--no-latest` 로 먼저 올리는 이유: 파일이 다 올라가기 전에 `latest.json` 이 새 버전을
가리키면, 그 사이에 켠 사람이 **없는 파일을 받으려 합니다.** 런처는 그때
`latest.json` 과 매니페스트의 버전이 어긋나는 것을 보고 멈추지만, 애초에 만들지
않는 편이 낫습니다.

`--dry-run` 으로 무엇이 올라갈지 먼저 볼 수 있습니다.

### 보관은 최근 10개 (`--keep`)

`-405` §④ 의 2026-09-10 팀 결정입니다. 그보다 옛 버전은 매니페스트를 지우고, **어느
남은 매니페스트도 가리키지 않는 파일**을 회수합니다.

**회수는 되돌릴 수 없습니다.** 남은 버전이 쓰는 파일을 지우면 그 버전이 설치 불가가
되고, 해시가 이름이라 되살릴 방법도 없습니다. 그래서 지울 후보를 정할 때 **남은
매니페스트 전부와 `launcher.json` 을 읽어** 참조 집합을 먼저 만듭니다 — 지우면서
동시에 판단하지 않습니다.

검사가 그것을 지킵니다: 버전 4개를 넣고 `--keep 2` 로 회수한 뒤 ① 남은 두 버전이 쓰는
파일이 전부 살아 있는지 ② **모든 버전이 공유하던 파일**이 살아 있는지 ③ 런처 파일이
살아 있는지 ④ 그러면서도 실제로 회수가 일어났는지를 봅니다.

## 런처를 만드는 법

```sh
cd launcher
dotnet publish -c Release -p:Version=1.0.1   # bin/Release/net10.0/win-x64/publish/
```

**버전을 빼면 빌드가 섭니다.** 기본값은 `0.0.0-dev` 이고, 그대로 릴리스 publish 하면
에러로 멈춥니다. 빠뜨린 채 올리면 서버가 말하는 버전과 exe 가 말하는 버전이 어긋나
받는 사람이 **끝나지 않는 자기 갱신**에 빠지기 때문입니다. 개발 중 `dotnet build` 는
그대로 됩니다.

`.NET` 없이 도는 **단일 exe 14.4 MB**(압축 6.3 MB)로 나옵니다. **받는 사람에게
".NET 을 먼저 설치하세요" 를 요구하면 런처가 없애려던 수동 절차가 그대로 남습니다.**

트리밍을 켜서 **70.2 MB → 14.4 MB** 로 줄였습니다. 단, 그것은 **JSON 을 소스
생성기로 읽게 바꾼 뒤에만 안전합니다**(`JsonContext.cs`) — 기본 `JsonSerializer`
경로는 리플렉션을 쓰므로 트리머가 프로퍼티를 지워도 **빌드는 통과하고 실행만 조용히
깨집니다.** 런처가 조용히 깨지는 것은 사용자가 원인을 알 수 없는 고장입니다. 그래서
바꾼 뒤 실제 서버의 JSON 을 읽는 것까지 확인했습니다.

**런처는 CI 에 넣지 않습니다.** 릴리스마다 바뀌는 물건이 아닙니다 — 게임 버전과
따로 움직이므로 릴리스 파이프라인에 묶으면 뜻 없는 런처 릴리스가 생깁니다.
`publish_launcher.py` 를 사람이 돌립니다.

## 검사

```sh
python scripts/ci/tests/test_launcher_manifest.py   # 매니페스트 도구 (ci-tests 가 자동으로 돈다)
NotThisPlanetLauncher.exe --selfcheck               # 런처의 경로·해시·매니페스트 판정
NotThisPlanetLauncher.exe --check                   # 무엇을 받고 지울지만 보고 끝낸다
NotThisPlanetLauncher.exe --dev --version v1.0.1    # 개발 모드로 그 버전
```

`--selfcheck` 가 **배포되는 그 exe 안에서** 돕니다. 테스트 프로젝트를 따로 두면
배포 산출물과 검사 대상이 갈립니다. 경로 21종 · 해시 7종 · 매니페스트 10종 ·
**버전 비교 16종**(`v1.9.0 < v1.10.0` 처럼 문자열 비교면 틀리는 자리 포함)과
**개발 모드 판정 13종**을 봅니다 — `--devil` 을 `--dev` 로 보지 않는지, `--version` 뒤가
비었을 때 터지지 않는지, 두 게임 폴더가 다른지, 개발 백엔드가 `/dev` 인지.

자체 갱신은 로컬 서버로 끝까지 시험했습니다 — v1.0.0 런처가 v1.0.1 로 바뀌고
해시가 올린 것과 일치하며 `.new.exe` 가 정리됩니다. `minLauncher` 를 올리고 갱신을
실패하게 만들면 **종료코드 1 로 막고 게임 폴더를 건드리지 않습니다.**

막는 것: 매니페스트의 `path` 는 서버에서 온 문자열이고 런처는 **그것으로 파일을
씁니다.** `..`·절대 경로·드라이브 지정·UNC·백슬래시·끝의 점·대소문자만 다른 중복을
전부 거부합니다. 만드는 쪽(`make_manifest.py`)도 같은 검사를 하지만 **두 쪽 다**
해야 합니다 — 서버가 바뀔 수 있고 중간에서 끼어들 수도 있습니다.

## 런처가 하지 않는 일 — 구버전 막기

그건 **서버 게이트**(`-404`)의 몫입니다. 런처는 우회됩니다 — 압축 푼 폴더의 exe 를
직접 더블클릭하는 것이 가장 흔하고, 그게 정확히 막아야 하는 경우입니다.

그래서 런처는 **서버에 못 닿으면 막지 않고 그냥 실행시킵니다.** EC2 는 단일 장애점이고
(2026-09-10 팀 확인), 서버가 한 번 딸꾹질할 때 전원이 게임을 못 켜는 것이 더 나쁩니다.
매니페스트를 신뢰할 수 없을 때도 **파일을 하나도 건드리지 않고** 있는 것으로 실행합니다 —
반쯤 적용된 폴더가 가장 고치기 어렵습니다.

2026-09-11 AhnLab V3 가 런처 exe 와 게임 exe 를 막았습니다. **테스터 전원이 같은

### 2026-09-13 재측정 — 재현되지 않았습니다

V3 실시간 감시가 켜진 상태(`root\SecurityCenter2` → `0x41000`, 정의 최신)에서 **갓
빌드한**(= 평판이 없는) exe 를 세 곳에서 돌렸습니다.

| 실행 폴더 | 결과 |
| --- | --- |
| `…\Temp\…\publish\` (`--selfcheck`) | 막히지 않음 |
| `…\Temp\…\avtest\` (`--check`) | 막히지 않음 |
| `…\Downloads\launcher-av-test\` (`--check`) | 막히지 않음 |

**`%TEMP%` 에서도 안 막혔다는 점이 중요합니다.** "시험 폴더가 `%TEMP%` 라서 걸린
것" 이라는 짐작이 있었는데, 그 짐작만으로는 설명되지 않습니다. 평판 기반 판정은
**날마다 달라질 수 있고**, 재현이 안 되는 것 자체가 평판 기반과 들어맞습니다.

**그래서 "고쳤다" 가 아니라 "발생할 수 있다" 로 둡니다.** 우리 PC 에서 안 뜨는 것과
사이트에서 받아 가는 사람에게 안 뜨는 것은 다른 이야기입니다 — 그 사람에게 이 파일은
여전히 처음 보는 파일입니다.

**아직 재지 않은 것**: 게임 exe. 띄우려면 156 MB 를 받아 실제로 설치해야 해서
이번에는 하지 않았습니다. 09-11 에는 게임 exe 도 함께 알림이 떴습니다.

### 임시 폴더에 자기를 풀지는 않습니다

별개로 "단일 exe 가 `%TEMP%` 에 자기를 푼다" 는 짐작이 있었는데, 그렇지 않습니다.

| 본 것 | 결과 |
| --- | --- |
| 실행 전후 `%LOCALAPPDATA%\Temp\.net\` | 생기지 않습니다 |
| 빈 폴더에 exe 만 두고 `--check` | `game/` **하나만** 생깁니다 |
| 받는 중 · 자기 갱신 임시 파일 | `.part`·`.new.exe` 둘 다 **런처 옆** |

.NET 6 이후 self-contained 단일 파일은 네이티브 라이브러리도 풀지 않고 번들에서
바로 읽습니다. **이것을 적어 두는 이유**: 백신 예외를 요청할 때 `%TEMP%` 를 들고 가면
**상관없는 경로를 예외 처리**하게 됩니다.
